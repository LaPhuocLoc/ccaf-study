試験について Exam Guide §1

この認定資格は何のため？

Claude Certified Architect – Foundations（コード CCAR-F）は、Claude で実際のプロダクトを作るときに妥当なトレードオフ（trade-off）の判断ができることを証明する資格です — 机上の理論の丸暗記ではありません。試験では4つの主要な「武器」の基礎知識が問われます：Claude Code、Claude Agent SDK、Claude API、Model Context Protocol (MCP)。

問題は知識を単純に問うのではなく、現実的な状況から組み立てられています：カスタマーサポート agent の構築、リサーチ用 multi-agent pipeline の構築、Claude Code の CI/CD への組み込み、開発者向け生産性ツールの作成、雑多なドキュメントからの構造化データ抽出など。理論に加えて、アーキテクチャの「センス」、正しい場所での設定、本番運用でのトレードオフの理解も求められます。

想定受験者 Exam Guide §27つのスキル

「標準的な」受験者は、Claude を使った本番アプリを自ら設計・デプロイした経験のある solution architect で、次のような実務経験を持っています：

  • Claude Agent SDK で agentic アプリを構築 — multi-agent orchestration、subagent delegation、tool integration、lifecycle hooks
  • チーム全体向けに Claude Code を設定 & カスタマイズ — CLAUDE.md、Agent Skills、MCP server、plan mode
  • MCP (Model Context Protocol) 準拠の tool & resource interface を設計し、backend システムに接続
  • 信頼できる structured output を得るための prompt 作成 — JSON schema、few-shot example、extraction pattern
  • 長いドキュメント、複数ターンの会話、agent 間の引き継ぎを通した context window の管理
  • Claude を CI/CD pipeline に組み込み、code review、test 生成、PR コメントを自動化
  • escalation & reliability の適切な判断 — エラー処理、human-in-the-loop、結果の自己評価

実務経験の目安：Claude API、Agent SDK、Claude Code、MCP を最低6か月使い込んでいること。この経験が足りなくても、理論をしっかり学んで問題演習をすれば合格できます — 問題は状況判断型で、コーディングは求められません。

Domain 1 · Agentic Architecture & Orchestration

試験で最も比重の大きいパート（27%）。基本の考え方：agent は stop_reason に基づいて自分で判断する、coordinator は subagent 間の唯一の「中継ハブ」である、そして100%の確実さが必要な箇所では prompt 頼みにせず必ず hook/prerequisite を使う。

Task Statement 1.1
タスクを自律実行する agentic loop の設計 & 実装
📚 押さえるべき知識
  • 基本の agentic loop：Claude に request を送る → stop_reason が "tool_use" か "end_turn" かを確認 → 要求された tool を実行 → 結果を次のループに返す
  • tool の結果は conversation history に append し、model がそれを「見て」次のステップを推論できるようにする
  • 明確に区別する：model が次に呼ぶ tool を自分で決める（model-driven）のと、決定木や固定の tool チェーンを事前にコードで組むのとはまったく別物
🛠️ できるべきこと
  • control flow を書く："tool_use" の間はループを続け、"end_turn" で停止
  • ループの合間に tool の結果を context に入れ、model が新しい情報で推論できるようにする
  • anti-pattern を避ける：自然言語を parse してループ停止を推測する、固定のループ回数上限を主な停止手段にする、「テキストの回答がある」ことを完了とみなす — どれも誤り
Task Statement 1.2
coordinator–subagent pattern による multi-agent の orchestration
📚 押さえるべき知識
  • hub-and-spoke アーキテクチャ：coordinator が中心となり、subagent 間のすべての通信、エラー処理、情報の調整を管理する
  • subagent は独立した context で動く — coordinator の会話履歴を自動では引き継がない
  • coordinator の責任：タスクの分解、割り当て、結果の集約、query の複雑さに応じてどの subagent を呼ぶかの判断
  • coordinator がタスクを狭く分割しすぎるリスク → リサーチの観点が抜け、テーマを網羅できない
🛠️ できるべきこと
  • 常に full pipeline を回すのではなく、query を分析して適切な subagent を選べる coordinator を設計する
  • subagent ごとのリサーチ範囲が重複しないように分ける（各 agent が別々の subtopic/情報源を担当）
  • refine ループを作る：coordinator が synthesis の output を見直して不足を洗い出し、より具体的な query で search/analysis に再依頼し、十分になるまで synthesis を再実行
  • subagent 間の通信はすべて coordinator を経由させる — 追跡しやすく、エラー処理を統一でき、情報の流れを制御できる
Task Statement 1.3
subagent の呼び出し、context の受け渡し、spawn の設定
📚 押さえるべき知識
  • Task tool が subagent を spawn する仕組み — coordinator の allowedTools に "Task" が含まれていないと subagent を呼べない
  • subagent の context は prompt で直接渡す必要がある — subagent は親の context を自動では引き継がず、呼び出し間で memory も共有しない
  • AgentDefinition には、subagent の種類ごとの description、system prompt、tool の制限が含まれる
  • Fork-based session を使うと、同じ分析 baseline から複数の異なる方向を探索できる
🛠️ できるべきこと
  • 前の agent の finding をすべて、次の subagent の prompt に直接入れる（例：web search の結果 + ドキュメント分析を synthesis agent に渡す）
  • context を渡すときは構造化フォーマットでコンテンツと metadata（出典 URL、ドキュメント名、ページ番号）を分離する — attribution を失わないため
  • coordinator の1つの response 内で複数の Task を発行して subagent を並列 spawn する（複数ターンに分散させない）
  • coordinator の prompt は機械的なステップ指示ではなく「目標 + 品質基準」の形で書く — subagent が柔軟に適応できるように
Task Statement 1.4
Multi-step workflow：いつ強制し、いつ引き継ぐか
📚 押さえるべき知識
  • workflow の順序を守らせる手段として、コードによる enforcement（hooks、prerequisite gate）と prompt での指示だけとはまったく別物
  • 100%の確実さが必須の処理（例：お金を扱う前の本人確認）では、prompt だけだと失敗率が0にはならない — 頼ってはいけない
  • 途中で escalate するときの handoff protocol には、顧客情報、根本原因の分析、推奨アクションが必要
🛠️ できるべきこと
  • コードで prerequisite を設定し、前のステップが完了するまで downstream の tool をブロックする（例：get_customer が検証済みの ID を返すまで process_refund をブロック）
  • 複数の問題を含む request を個別の項目に分け、共有 context 上で並行して調査し、1つの一貫した回答にまとめる
  • 人間に引き継ぐときは構造化された引き継ぎサマリー（customer ID、根本原因、返金額、推奨アクション）を作る — 人間は transcript を読めないため
Task Statement 1.5
Agent SDK hooks で tool call を intercept & データを正規化
📚 押さえるべき知識
  • PostToolUse pattern は tool の結果を intercept し、model が処理する前に変換する
  • 送出される tool call を intercept する hook で business rule を強制する（例：閾値を超える refund をブロック）
  • Hook = 確実な保証（deterministic）、prompt = 確率的 — 確実さが必要な箇所では hook を使う
🛠️ できるべきこと
  • PostToolUse hook を書き、異なる MCP tool から来る不揃いなデータ（Unix timestamp、ISO 8601、数値の status コードなど）を agent が処理する前に正規化する
  • policy 違反の操作（例：$500 を超える refund）をブロックし、別の workflow（例：人間への escalate）に redirect する hook を書く
  • business rule の絶対的な遵守が必要なときは、prompt ではなく hook を選べる
Task Statement 1.6
複雑な workflow のための task decomposition 戦略の設計
📚 押さえるべき知識
  • 固定の逐次 pipeline（prompt chaining）を使うべき場面と、中間結果に基づく柔軟な decomposition を使うべき場面
  • Prompt chaining：review を逐次ステップに分割する（例：各ファイルを個別に分析してから、cross-file の統合 pass を1回実行）
  • 適応的な調査計画 — 各ステップで見つかったことに基づいて subtask を動的に生成 — は open-ended なタスクで非常に有効
🛠️ できるべきこと
  • 適切な decomposition を選ぶ：多観点だが予測しやすい review には prompt chaining、open-ended な調査タスクには柔軟な decomposition
  • 大規模なコード review を、ファイルごとの local 分析 pass + cross-file 統合専用の pass に分けて、注意の「希釈」を防ぐ
  • open-ended なタスク（例：「legacy codebase に十分な test を追加する」）では、まず構造を把握し、優先度の高い領域を特定し、順序立てた計画を作り、新しい dependency が見つかったら計画を調整する
Task Statement 1.7
session state、resume、fork の管理
📚 押さえるべき知識
  • --resume <session-name> で名前付き session を resume し、以前の会話をそのまま続ける
  • fork_session で共通の分析 baseline から独立したブランチを作り、複数の方向を探索する
  • コードを修正した後に resume するときは、どのファイルが変わったかを agent に伝える — 古い情報を使わせない
  • 構造化サマリー付きで新しい session を始める方が、古くなった（stale）tool result を抱えたまま resume するより信頼できることが多い
🛠️ できるべきこと
  • --resume と session 名を使い、複数の作業セッションにまたがる調査を継続する
  • fork_session で並行ブランチを作る（例：同じ codebase 分析から2つの test 戦略や2つの refactor 方針を比較）
  • resume（古い context がまだ有用なとき）と、サマリー付きの新規開始（古い tool result が陳腐化したとき）を使い分けられる
  • resume 時は変更された特定のファイルだけを agent に伝えて該当箇所を re-analyze させる — 最初から探索し直させない

Domain 2 · Tool Design & MCP Integration

要点：tool の description は LLM が正しい tool を選ぶための拠り所 — 雑な description だと選択を誤ります。さらに：error response は構造化する、tool は役割に応じて配分する（1つの agent に18個の tool を詰め込まない）、MCP server を正しい scope で設定する。

Task Statement 2.1
明確で境界のはっきりした tool interface の設計
📚 押さえるべき知識
  • tool の説明（description）は LLM が tool を選ぶ主な手がかり — 雑な description = 似た tool の間で選択がぶれる
  • 良い description に必要なもの：input format、query の例、edge case、使う/使わない場面の境界
  • 曖昧・重複した description は「tool の取り違え」を招く（例：analyze_content と analyze_document の description がほぼ同じ）
  • system prompt の wording も tool の選択に影響する — 1つの「敏感な」キーワードが意図しない誤った連想を生むことがある
🛠️ できるべきこと
  • 目的、期待される input/output、類似 tool ではなくこの tool を使うべき場面を明確に区別した description を書く
  • 名前の変更 + description の書き直しで機能の重複をなくす（例：analyze_content を web 専用の description を持つ extract_web_results に改名）
  • 汎用 tool を、それぞれ明確な input/output contract を持つ複数の専用 tool に分割する（例：analyze_document を extract_data_points、summarize_content、verify_claim_against_source に分割）
  • よく書けた tool description を system prompt のキーワードがうっかり「上書き」していないか見直す
Task Statement 2.2
MCP tool の structured error response の設計
📚 押さえるべき知識
  • tool のエラーを agent に伝える MCP の isError フラグ pattern
  • 4種類のエラーを区別する：transient（timeout、service ダウン）、validation（不正な input）、business（policy 違反）、permission
  • 「Operation failed」のような汎用的なエラーを返すと、agent はどう対処すべきかわからない
  • retryable と non-retryable のエラーは別物 — 構造化 metadata を返せば無駄な retry を防げる
🛠️ できるべきこと
  • 構造化されたエラー metadata を返す：errorCategory（transient/validation/permission）、isRetryable boolean、わかりやすい説明
  • business rule 違反によるエラーには retriable: false フラグと、顧客にやさしい説明を付ける
  • 一時的（transient）なエラーは subagent がその場で処理し、自力で解決できないものだけを partial result + 試したこと付きで coordinator に上げる
  • 明確に区別する：本当のアクセスエラー（retry の判断が必要）と、正当な空の結果（query は成功したが一致なし）は別物
Task Statement 2.3
tool を役割に応じて配分 & tool choice の設定
📚 押さえるべき知識

  • 専門外の tool を持つ agent はそれを誤用しがち（例：synthesis agent が自分で web search してしまう）

🛠️ できるべきこと
  • 各 subagent の tool set を役割の範囲内に限定し、専門をまたいだ誤用を防ぐ
  • 汎用 tool をより制限された版に置き換える（例：fetch_url を、ドキュメント URL を validate する load_document に置き換え）
  • 高頻度のニーズには制限付きの cross-role tool を与え（例：synthesis agent 用の verify_fact tool）、複雑なケースは引き続き coordinator 経由で route する

  • tool_choice: "any" を設定し、model がテキストだけで答えず必ず tool を呼ぶようにする
Task Statement 2.4
MCP server を Claude Code & agent workflow に統合
📚 押さえるべき知識

🛠️ できるべきこと

  • 個人用/試験用の MCP server を ~/.claude.json（user-scope）に設定する

  • 自作よりも既存の community MCP server（例：Jira）を優先し、チーム固有の workflow の場合だけ server を自作する
  • コンテンツのカタログを MCP resource として expose し、agent が tool call で探らなくても利用可能なデータが「見える」ようにする
Task Statement 2.5
built-in tool（Read、Write、Edit、Bash、Grep、Glob）を適切に選んで使う
📚 押さえるべき知識
  • Grep = ファイルの中身を検索（関数名、error message、import 文など）
  • Glob = パスのパターンでファイルを検索（ファイル名、拡張子）

🛠️ できるべきこと
  • codebase 全体からコードの中身を探すには Grep を選ぶ（関数の呼び出し箇所、error message の場所など）
  • 名前のパターンでファイルを探すには Glob を選ぶ（例：**/*.test.tsx）
  • Edit が一意な anchor text を見つけられないときは、Read でファイル全体を読み込んでから Write
  • codebase の理解を段階的に積み上げる：まず Grep で entry point を探し、import をたどって Read し流れを trace — 最初から全ファイルを読むのではなく
  • wrapper module を経由した関数の使用箇所を trace する：まず export 名をすべて洗い出し、それぞれの名前で codebase 全体を検索

要点：CLAUDE.md の階層構造をしっかり理解する、plan mode と直接実行の使い分けを知る、そして pipeline をハングさせずに Claude Code を CI/CD に組み込む方法。

Task Statement 3.1
CLAUDE.md を正しい階層・scope で設定し、適切に module 化する
📚 押さえるべき知識

🛠️ できるべきこと

Task Statement 3.2
custom slash command と skill の作成 & 設定
📚 押さえるべき知識
  • project-scope の command は .claude/commands/（version control で共有）、user-scope は ~/.claude/commands/（個人用）
  • Skill は .claude/skills/ に置き、SKILL.md ファイルは frontmatter をサポート：context: fork、allowed-tools、argument-hint
  • context: fork は skill を独立した sub-agent で実行し、skill の output がメインの会話を「汚さない」ようにする
  • 個人向けの skill カスタマイズ：~/.claude/skills/ に別名で自分用の版を作り、チームメイトに影響を与えない
🛠️ できるべきこと
  • .claude/commands/ に project-scope の slash command を作り、version control 経由でチーム全体で共有する
  • context: fork で、output が冗長な skill（例：codebase 分析）や探索的な skill（例：複数方向のブレインストーミング）をメイン session から隔離する
  • frontmatter で allowed-tools を設定し、skill が使える tool を制限する（例：ファイル書き込みだけ許可して破壊的な操作を防ぐ）
  • argument-hint で、引数なしで skill を呼んだときに必要なパラメータの入力を促す
  • skill（必要なときに呼び出す、個別の workflow 向け）と CLAUDE.md（常に読み込まれる、プロジェクト共通の規約向け）を使い分けられる
Task Statement 3.3
path-specific rules で規約を条件付きで読み込む
📚 押さえるべき知識
  • .claude/rules/ 内のファイルは、YAML frontmatter に glob pattern の paths フィールドを持たせて rule を条件付きで有効化できる
  • path ベースの rule は pattern に一致するファイルを編集しているときだけ読み込まれる — 余計な context と token 消費を減らせる
  • 規約が多くの場所にまたがる場合（例：test ファイルが codebase 全体に点在）、glob pattern の rule はディレクトリ単位の CLAUDE.md より有利
🛠️ できるべきこと
  • .claude/rules/ に、path で scope を絞る YAML frontmatter 付きのファイルを作る（例：paths: ["terraform/**/*"]）— 該当ファイルの編集時だけ読み込まれる
  • rule で glob pattern を使い、ディレクトリに関係なくファイル種別ごとに規約を適用する（例：すべての test ファイルに **/*.test.tsx）
  • codebase 全体に散らばったファイルに規約を適用する必要があるときは、subdirectory の CLAUDE.md ではなく path-specific rule を選ぶ
Task Statement 3.4
plan mode と直接実行（direct execution）の使い分け
📚 押さえるべき知識
  • Plan mode は複雑なタスク向け：大規模な変更、複数の妥当なアプローチ、アーキテクチャの判断、多数のファイルの修正
  • Direct execution はシンプルで範囲が明確な作業向け（例：1つの関数に validate チェックを1つ追加）
  • Plan mode なら、実際の変更を commit する前に codebase を安全に探索 & 設計できる — 手戻りを防げる
  • Explore subagent は冗長な探索 output を隔離して要約を返し、メインの会話の context を守る
🛠️ できるべきこと
  • アーキテクチャに影響するタスクには plan mode を選ぶ（例：microservice の再構築、45以上のファイルに影響するライブラリ移行、異なるインフラを要する統合方式の選択）
  • 明確で scope がよくわかっている変更には direct execution を選ぶ（例：stack trace が明確な1ファイルの bug 修正、日付の validate 条件の追加）
  • 冗長な探索フェーズには Explore subagent を使い、複数フェーズのタスクの途中で context window を「使い果たす」のを防ぐ
  • 組み合わせる：plan mode で調査し、立てた計画に沿って direct execution で実装する（例：ライブラリ移行を計画してから実行）
Task Statement 3.5
iterative refinement で段階的に改善する
📚 押さえるべき知識

🛠️ できるべきこと
  • 言葉での説明では結果が一貫しないとき、2〜3個の具体的な input/output の例で変換の要件を明確にする
  • コードを書く前に、期待する挙動、edge case、性能要件を網羅した test を書き、test の失敗をもとに反復する
  • 不慣れな domain でコードを書く前に、interview pattern で設計上の考慮事項（例：cache invalidation の戦略、起こりうるエラーの種類）を引き出す
  • edge case を直すために、期待する input/output 付きの具体的な test case を渡す（例：migration script の null 値）
  • 互いに影響し合う複数の問題は1つの詳細な message にまとめ、独立した問題は順番に直す
Task Statement 3.6
Claude Code を CI/CD pipeline に統合
📚 押さえるべき知識
  • -p（または --print）フラグで、自動化 pipeline 内の Claude Code を non-interactive モードで実行する
  • --output-format json と --json-schema フラグで、CI での実行時に structured output を強制する

Domain 4 · Prompt Engineering & Structured Output

要点：基準が具体的なほど false positive は減る（「注意して」と言うだけでは無意味）、few-shot は一貫した output を得るための最強の武器、そして tool_use + JSON schema が structured output を強制する最も確実な方法。

Task Statement 4.1
明確な基準を持つ prompt を設計し、精度を上げて false positive を減らす
📚 押さえるべき知識
  • 具体的な基準は曖昧な指示に必ず勝る（例：「コメントが主張する挙動が実際のコードと矛盾する場合だけ flag する」は「コメントが正しいかチェックして」よりはるかに良い）
  • 「注意して」や「確信度の高い finding だけ報告して」のような漠然とした指示は、具体的な分類基準と比べて精度の改善につながらない
  • False positive rate は開発者の信頼を左右する：誤報の多い category が1つあると、正しく機能している他の category への信頼まで失われる
🛠️ できるべきこと
  • 具体的な review 基準を書く：報告すべきもの（bug、security）vs 無視するもの（細かい style、local pattern）— 「確信度」でフィルタするのではなく
  • 誤報の多い category は一時的に無効化して開発者の信頼を取り戻し、その間にその category の prompt を調整する
  • 各レベルの具体的なコード例付きで severity の基準を明確に定義し、一貫した分類を実現する
Task Statement 4.2
few-shot prompting で output の一貫性と品質を上げる
📚 押さえるべき知識
  • 文章による詳細な指示だけでは結果が安定しないとき、few-shot example は正しい format・正しい行動の output を得る最も効果的な手法
  • few-shot は曖昧なケースの扱い方を示すのに使う（例：あいまいな request に対する tool の選択、branch レベルの test coverage の gap）
  • few-shot は model が判断の「センス」を新しいケースに汎化するのを助ける — 与えたケースに機械的に一致させるだけではない
  • few-shot は extraction タスクでの hallucination を減らすのに効果的（例：非公式な単位の処理、多様なドキュメント構造）
🛠️ できるべきこと
  • 曖昧なケースを狙った 2〜4個の few-shot example を作り、他の妥当な選択肢ではなくその行動を選ぶ理由も添える
  • 期待する output format（location、issue、severity、修正提案）を正しく示す例を入れて一貫性を確保する
  • 許容できるコード pattern と本物のエラーを区別する例を入れ、汎化性能を保ちつつ false positive を減らす
  • さまざまなドキュメント構造（inline 引用 vs bibliography、methodology セクション vs 本文に埋め込まれた詳細）の正しい扱い方を示す例を使う
  • 異なる format のドキュメントから正しく抽出する例を追加し、必須フィールドが空/null で抽出される問題に対処する
Task Statement 4.3
tool use と JSON schema で structured output を強制
📚 押さえるべき知識
  • JSON schema 付きの tool_use は schema に準拠した output を得る最も確実な方法で、JSON の構文エラーを完全になくせる
  • tool_choice の区別："auto"（model は tool を呼ばずにテキストを返すこともある）、"any"（tool 呼び出しは必須だが、どの tool かは model が選ぶ）、特定 tool の強制
  • strict な JSON schema で防げるのは構文エラーだけで、意味的なエラーは防げない（例：line item の合計が total と合わない、値が間違ったフィールドに入る）
  • schema 設計：必須 vs optional フィールド、拡張しうる category には enum + "other" pattern + 詳細 string
🛠️ できるべきこと
  • JSON schema を input parameter とする extraction tool を定義し、tool_use response から structured data を取り出す
  • extraction schema が複数あり、ドキュメントの種類が不明なときは tool_choice: "any" を設定して structured output を確実に得る
  • tool_choice: {"type": "tool", "name": "extract_metadata"} で特定の tool を強制し、extraction のステップが enrichment より先に実行されるようにする
  • 元のドキュメントにその情報がない可能性があるときは schema のフィールドを optional/nullable にする — 必須フィールドを埋めるために model が値を「でっち上げる」のを防ぐ
  • 曖昧なケース用に "unclear" のような enum を追加し、拡張しうる category には "other" pattern + 詳細フィールドを使う
  • 厳格な output schema と並行して format 正規化の rule を prompt に入れ、不揃いな元データの format に対処する
Task Statement 4.4
validation、retry、feedback loop を構築して extraction の品質を上げる
📚 押さえるべき知識
  • エラーフィードバック付き retry：retry 時に具体的な validate エラーを prompt に入れ、model が正しい方向に自己修正できるようにする
  • 必要な情報が元のドキュメントにそもそも存在しない場合、retry は無意味（format/構造のエラーとは別物）
  • Feedback loop：どのコード構造が finding を引き起こしやすいか（detected_pattern フィールド）を追跡し、dismiss されやすい pattern を体系的に分析する
  • 意味的な validate エラー（数値の合計が合わない、フィールドの位置違い）と、schema の構文エラー（tool use によって排除済み）を区別する
🛠️ できるべきこと
  • 元のドキュメント、失敗した extraction の結果、具体的な validate エラーを付けて follow-up request を送り、model に自己修正させる
  • retry が無駄な場合（例：提供されていない外部ドキュメントにしか情報がない）と、retry で成功する場合（format エラー、output 構造のエラー）を見分ける
  • 構造化 finding に detected_pattern フィールドを追加し、開発者が finding を dismiss したときに false positive の pattern を分析できるようにする
  • 自己修正フローを設計する：calculated_total と stated_total の両方を抽出して数値のズレを検出し、元データが矛盾するときは boolean の conflict_detected を追加
Task Statement 4.5
効率的な batch processing 戦略の設計
📚 押さえるべき知識
  • Message Batches API：コスト 50%削減、最大24時間以内に処理、レイテンシの SLA 保証はなし
  • Batch は即時の結果を必要とせず遅延を許容できる workflow 向き（夜間の report、週次の audit、夜間の test 生成）— blocking な workflow（merge 前のチェック）には向かない
  • Batch API は1つの request 内での multi-turn tool calling をサポートしない（途中で tool を実行して結果を返すことはできない）
  • custom_id フィールドで batch 内の request/response の組を対応付ける
🛠️ できるべきこと
  • workflow のレイテンシ要件に API を合わせる：merge をブロックするチェックには同期 API、夜間/週次の分析には batch API
  • SLA の制約から batch の送信頻度を計算する（例：24時間で処理される batch で 30時間の SLA を守るには 4時間ごとの window）
  • batch の失敗への対処：失敗したドキュメントだけを（custom_id で特定して）適切な修正付きで再送する（例：context limit を超えるドキュメントを分割）
  • 大量の batch を流す前に小さなサンプルで prompt を調整し、初回の成功率を上げて再送のコストを減らす
Task Statement 4.6
複数 instance・複数 pass の review アーキテクチャ設計
📚 押さえるべき知識
  • self-review の限界：model は生成時の「推論の流れ」を保持したままなので、同じ session 内では自分の判断を疑いにくい
  • 独立した review instance（以前の推論を持ち込まない）は、「もう一度自己 review して」と指示したり extended thinking を使ったりするより、微妙なエラーをよく見つける
  • Multi-pass review：大規模な review を、ファイルごとの local 分析 pass + cross-file の統合 pass に分け、注意の希釈や互いに矛盾する finding を防ぐ
🛠️ できるべきこと
  • 生成されたばかりのコードの review には、生成側の推論の流れを持ち込まない独立した2つ目の Claude instance を使う
  • 多数ファイルの大規模 review を、ファイルごとの pass（local な issue）+ 別の統合 pass（cross-file の data flow 分析）に分ける
  • model が各 finding に確信度を自己申告する verification pass を実行し、確信度に応じて review を振り分ける

Domain 5 · Context Management & Reliability

要点：summarization で重要な数値を失わない、「lost in the middle」効果を理解する、いつ人間に escalate すべきかを知る、そして複数ソースを統合するときに provenance（情報の出所）を保つ。

Task Statement 5.1
長いやり取りでも重要な情報を保つための会話 context の管理
📚 押さえるべき知識
  • progressive summarization のリスク：数値、パーセンテージ、日付、顧客の期待が曖昧な要約に圧縮されてしまう
  • 「lost in the middle」効果 — model は長い input の最初と最後の情報はうまく扱えるが、中間にある finding を見落としやすい
  • tool の結果は context に蓄積し、関連度に見合わないほど token を消費する（例：5つで足りるのに order lookup のたびに 40以上のフィールド）
  • 会話の論理の流れを保つには、後続の API request で会話履歴全体を渡す必要がある
🛠️ できるべきこと
  • 取引の事実（金額、日付、注文番号、ステータス）を固定の「case facts」ブロックに抽出し、要約される履歴の外に置いて毎回の prompt に入れる
  • 複数の問題を扱う session では、構造化された issue データ（order ID、金額、ステータス）を抽出して別の context レイヤーに保存する
  • 冗長な tool output は context に蓄積する前に関連フィールドだけに削る（例：order lookup から返品に関係するフィールドだけを残す）
  • 統合用 input の冒頭に重要な finding の要約を置き、詳細な結果は明確な section header で整理して位置効果を軽減する
  • subagent の構造化 output に metadata（日付、出典、方法論の背景）を必ず含めさせ、downstream での正確な統合を支える
  • downstream の agent の context 予算が限られているときは、upstream の agent を修正し、冗長な内容 + 推論の連鎖ではなく構造化データ（主要な事実、引用、関連ポイント）を返させる
Task Statement 5.2
効果的な escalation pattern & 曖昧さへの対処の設計
📚 押さえるべき知識
  • 妥当な escalation のトリガー：顧客が人間の対応を求める、policy に例外/抜け穴がある（ケースが複雑というだけではない）、agent が行き詰まって前に進めない
  • 区別する：顧客がはっきり求めたら即 escalate vs 問題がシンプルで agent の範囲内なら自分での対応を申し出る
  • sentiment や agent が自己申告する確信度に基づく escalation は、ケースの本当の複雑さの代理指標として信頼できない
  • 複数の結果が同時に一致したら、heuristic で勝手に選ばず、識別情報を追加で尋ねる
🛠️ できるべきこと
  • 明確な escalation 基準を few-shot example 付きで system prompt に追加し、escalate すべき場合と自分で対応すべき場合を示す
  • 顧客の「人間と話したい」という要求には、事前の調査なしで即座に応じる
  • 顧客の不満は受け止めつつ、対応可能な問題なら解決を申し出て、顧客が要求を繰り返した場合にだけ escalate する
  • 顧客の具体的な要求について policy が曖昧、または何も定めていないときは escalate する（例：policy は社内の価格調整にしか触れていないのに、競合他社との price matching を求められた）
  • tool が複数の一致結果を返したら、heuristic で選ばずに識別情報を追加で尋ねるよう agent に指示する
Task Statement 5.3
multi-agent システムにおけるエラー伝播（error propagation）戦略の実装
📚 押さえるべき知識
  • 構造化されたエラー context（エラーの種類、試した query、partial result、代替案）があれば、coordinator は賢い復旧判断ができる
  • 区別する：アクセスエラー（timeout、retry の判断が必要）と、正当な空の結果（query は成功したが一致なし）は別物
  • 汎用的なエラーステータス（「search unavailable」）は、coordinator が必要とする貴重な情報を隠してしまう
  • どちらも anti-pattern：エラーを黙って握りつぶす（空の結果を成功扱いで返す）ことと、1つのエラーだけで workflow 全体を止めること
🛠️ できるべきこと
  • エラーの種類、試したこと、partial result、可能な代替案を含む構造化エラー context を返す — coordinator が賢く復旧できるように
  • エラー報告ではアクセスエラーと正当な空の結果を明確に区別し、coordinator が正しく判断できるようにする
  • 一時的なエラーは subagent がその場で復旧し、自力で解決できないものだけを、試したことと partial result 付きで上に上げる
  • synthesis の output にカバレッジの注記を付け、しっかり裏付けのある finding と、情報源にアクセスできず不足している領域を明示する
Task Statement 5.4
大規模 codebase を探索するときの効率的な context 管理
📚 押さえるべき知識
  • 長い session での context の劣化：model の回答が一貫しなくなり、以前に見つけた具体的なクラス名ではなく「よくある pattern」のような言い方をし始める
  • context の境界を越えて重要な finding を保存する scratchpad file の役割
  • Subagent delegation で冗長な探索 output を隔離し、main agent は高い視点での調整に専念する
  • crash recovery のための構造化 state の保存：各 agent が state を決まった場所に export し、coordinator が resume 時に manifest を読み込む
🛠️ できるべきこと
  • 具体的な問い（例：「test ファイルをすべて探す」「refund フローの dependency を trace する」）を調べる subagent を spawn し、main agent は高レベルの調整役を担う
  • agent に重要な finding を記録する scratchpad file を維持させ、後続の質問でそれを参照させて context の劣化を防ぐ
  • 次のフェーズの subagent を spawn する前に、探索フェーズの主要な finding を要約し、その要約を初期 context に入れる
  • 構造化 state（manifest）の export による crash recovery を設計し、coordinator が resume 時にそれを読み込んで agent の prompt に入れる
  • 冗長な探索 output で context がいっぱいになった長い探索 session では、/compact で context の負荷を減らす
Task Statement 5.5
human review workflow & 確信度の較正（confidence calibration）の設計
📚 押さえるべき知識
  • 全体の accuracy 指標（例：全体で 97%）は、特定のドキュメント種別やフィールドでの低い性能を隠してしまうことがある
  • Stratified random sampling で、確信度の高い extraction のエラー率を測定し、新しいエラー pattern を発見する
  • フィールドごとの confidence score をラベル付き validation セットで較正し、review が必要な箇所の振り分けに使う
  • 「確信度が高い」extraction を完全自動化する前に、ドキュメント種別・フィールド別の accuracy を確認する必要がある
🛠️ できるべきこと
  • 確信度の高い extraction に stratified random sampling を導入し、エラー率を継続的に測定して新しいエラー pattern を発見する
  • human review を減らす前に、ドキュメント種別・フィールド別に accuracy を分析し、すべてのセグメントで性能が一貫していることを確認する
  • model にフィールドごとの confidence score を出力させ、ラベル付き validation セットで review の閾値を較正する
  • confidence が低い extraction や、元ドキュメントが曖昧/矛盾している extraction を human review に回し、限られた reviewer のリソースを優先的に割り当てる
Task Statement 5.6
情報の出所（provenance）の保持 & 複数ソース統合時の不確実性への対処
📚 押さえるべき知識
  • claim と出典の対応付けを保持せずに finding を圧縮要約すると、出典の attribution が失われやすい
  • 構造化された claim–出典のマッピングは非常に重要 — synthesis agent は finding を結合するときにそれを保持し、正しくマージしなければならない
  • 信頼できる情報源どうしで数値が矛盾する場合の扱い：勝手に1つの値を選ばず、矛盾を出典付きで明記する
  • 時系列データ：構造化 output に公開日/収集日を必ず含め、時期の違いを矛盾と誤解しないようにする
🛠️ できるべきこと
  • subagent に構造化された claim–出典マッピング（URL、ドキュメント名、関連する抜粋）を出力させ、downstream の agent には統合の過程でそれをそのまま保持させる
  • しっかり確立された finding と議論の余地がある finding を明確なセクションで区別した report 構成にし、出典の記述と方法論の背景をそのまま保つ
  • 矛盾する値を明記した状態でドキュメント分析を完了させ、synthesis に入れる前にどう調停するかを coordinator に判断させる
  • subagent の構造化 output に公開日/データ収集日を含めさせ、時間軸に沿って正しく解釈できるようにする
  • 統合 output ではコンテンツの種類に応じて適切にレンダリングする — 財務データは表、ニュースは文章、技術的な finding は構造化リスト — すべてを1つの形式に押し込めない

1.1 The Agentic Loop Lifecycle — agentic loop のライフサイクル

本質的に、agentic システムは1つのループです。Claude は tools 付きの prompt を受け取り、tool を呼ぶかそのまま答えるかを判断し、このループは Claude が完了を知らせるまで繰り返されます。

How the Loop Works — loop の仕組み
User sends prompt with tool definitions
         ↓
    Claude responds
         ↓
  Check stop_reason
         ↓
┌──────────────────────────────────────┐
│ "tool_use"     → Execute tool        │
│                 → Return tool_result │
│                 → Send next request  │
│                 → Loop continues     │
│                                      │
│ "end_turn"     → Claude is done      │
│                 → Present final text │
│                 → Loop ends          │
│                                      │
│ "stop_sequence"→ Custom stop matched │
│                 → Loop ends          │
│                                      │
│ "pause_turn"   → Server-side tool    │
│                  loop hit its cap    │
│                 → Send response back │
│                 → Loop continues     │
│                                      │
│ "max_tokens"   → Hit token limit     │
│                 → May need continue  │
│                                      │
│ "refusal"      → Declined on safety  │
│                 → Inspect stop_details│
│                 → Loop ends           │
│                                      │
│ "model_context_window_exceeded"      │
│                → Hit context window  │
│                → Valid but truncated │
└──────────────────────────────────────┘
The stop_reason Values — stop_reason の値
値意味アクション
"tool_use"Claude が tool を呼び出したいtool を実行し、結果を返して loop を続ける
"end_turn"Claude が推論を終えた最終的な回答をテキストで提示する
"stop_sequence"output が stop_sequences に設定された文字列に一致したloop 終了；どの文字列に一致したかを確認
"pause_turn"Server-side tool loop（例：web_search）が内部のループ回数上限に達したresponse を送り返して続行する
"max_tokens"response が max_tokens の上限に達した続きを得るために request を送る必要があるかもしれない
"refusal"Claude が安全上の理由で回答を拒否したloop 終了；stop_details（下記参照）を確認し、言い換えるか request を別の経路に route する
"model_context_window_exceeded"生成が max_tokens に達する前に model の context window の上限に達したresponse は有効だが途中で切れている；input を減らすか続行する。Sonnet 4.5+ ではデフォルト
💡 refusal 時の stop_details（Opus 4.7+）

refusal の response には stop_details オブジェクトも付いてきます（beta header は不要）。stop_details.type は常に "refusal"；stop_details.category は違反した policy の category（例："cyber"、"bio"、"reasoning_extraction"、"frontier_llm"、または null — この category の集合は時間とともに拡張されてきました）；stop_details.explanation は人間が読むための説明文字列です（parse しようとしないこと）。他のすべての stop reason では stop_details は null になります。この category を使って、refusal の種類ごとに route や log を分けましょう。

Server-Side Refusal Fallbacks — refusal 時の server 側 fallback

refusal は exception ではなく HTTP 200 で返ってきます — stop_reason を先に確認せず content だけを読むコードは、空または一部だけの response を黙って処理してしまいます。Claude Opus 5 と Claude Fable 5 で動く本番 agent では、refusal をただ log に残すのではなく、server-side fallback を有効にして、refusal の category に応じて request が自動的に route し直されるようにしましょう。

response = client.messages.create(
    model="claude-opus-5",
    max_tokens=16000,
    betas=["server-side-fallback-2026-07-01"],
    fallbacks="default",          # server routes by refusal category
    messages=[...],
)

fallbacks="default" なら、model のリストを自分で管理する必要はありません。旧来の array 形式（betas=["server-side-fallback-2026-06-01"] + fallbacks=[{"model": "claude-opus-4-8"}]）も引き続き動作します。Server-side fallback は Claude API でのみ利用可能です — Bedrock、Vertex、Foundry では代わりに SDK の client 側の BetaRefusalFallbackMiddleware を使います。

loop のルール：content を読む前に必ず stop_reason を確認すること。refusal はその request に対する最終的な stop reason であり、retry できる tool のエラーではありません。

API Response Structure — API response の構造

Claude が tool を使いたいとき、response には text と tool_use ブロックの両方が含まれます：

{
  "id": "msg_01Aq9w938a90dw8q",
  "model": "claude-opus-5",
  "stop_reason": "tool_use",
  "role": "assistant",
  "content": [
    {
      "type": "text",
      "text": "I'll check the current weather in San Francisco for you."
    },
    {
      "type": "tool_use",
      "id": "toolu_01A09q90qw90lq917835lq9",
      "name": "get_weather",
      "input": { "location": "San Francisco, CA", "unit": "celsius" }
    }
  ]
}

content 配列には複数のブロックを入れられます — Claude は同じ response の中で、何をしているかの説明（text）と tool の呼び出し（tool_use）を同時に行えます。複数の tool_use ブロックを入れて、複数の tool を同時に呼ぶこともできます。

Returning Tool Results — tool の結果を返す

tool の結果は、Claude の request にある tool_use_id を正しく参照する必要があります：

{
  "role": "user",
  "content": [
    {
      "type": "tool_result",
      "tool_use_id": "toolu_01A09q90qw90lq917835lq9",
      "content": "15 degrees celsius, partly cloudy"
    }
  ]
}

複数の tool を同時に呼んだ場合は、同じ message 内に複数の tool_result ブロックを返し、それぞれを対応する tool_use_id に一致させます。

Error Results — エラー時の結果

tool の実行でエラーが起きたとき：

{
  "type": "tool_result",
  "tool_use_id": "toolu_01A09q90qw90lq917835lq9",
  "is_error": true,
  "content": "API timeout after 30 seconds"
}

is_error: true を設定すると、Claude は tool が失敗したことを理解し、復旧のための戦略を推論できます。

Model-Driven Decision Making — model 主導の意思決定

試験ではこれを理解しているかが問われます：どの tool を呼び、いつ止めるかを決めるのは Claude 自身です。決定木（decision tree）や固定の tool チェーンを事前に設定するのではありません。model が自分でどんな情報が必要かを推論し、適切な tool を選び、結果を処理し、次のステップを決めます。

これは、手順があらかじめ決められている従来の workflow automation とは本質的に異なります。

Anti-Patterns — 誤った選択肢（These Are Wrong Answers）
  1. 自然言語を parse して loop を止めるタイミングを判断する — 「Claude が『終わりました』と言ったら loop を抜ける」のようなもの。誤り。必ず stop_reason を確認すること。
  2. 任意のループ回数上限を主な停止手段にする — 「最大5回回したら止める」のようなもの。主な手段として使うなら誤り。安全のための cap は使ってよいが、loop を制御するのはあくまで stop_reason。
  3. response に text があるかどうかで完了とみなす — 「response に text があれば完了とする」のようなもの。誤り。response には text と tool_use ブロックが同時に含まれることがある。
🔭 公式 Exam Guide の範囲外 — task budgets（beta）

「ループ回数のハードな cap を使わずに agentic loop を制限するには？」という問いへの現代的な答えが task budget です。output_config.task_budget は Claude が見ることのできる token の上限を与えるので、Claude は自分でペース配分を考え、途中で打ち切られるのではなく「きれいに」作業を完了できます。これは、model がまったく認識していない response ごとのハードな上限である max_tokens とは別物です。

with client.beta.messages.stream(
    model="claude-opus-5", max_tokens=128000,
    betas=["task-budgets-2026-03-13"],
    output_config={"effort": "high",
                   "task_budget": {"type": "tokens", "total": 64000}},
    messages=[...], tools=[...],
) as stream:
    response = stream.get_final_message()

total の最小値は 20,000。Claude Opus 5、Fable 5、Sonnet 5、Opus 4.8/4.7 で利用可能です。stream で受け取るのを忘れずに — streaming しない request で大きな max_tokens を指定すると HTTP timeout になりやすいです。試験の anti-pattern はここでも有効：budget は loop のペースを保つのに役立つだけで、loop を終わらせるのは依然として stop_reason です。

Who Runs the Loop: Four Ways to Build an Agent — 誰が loop を回すのか：agent を作る4つの方法

選択肢を区別するには、互いに独立した2つの問いがあります：誰が harness を提供するか（loop + context 管理）と、誰が deployment インフラを提供するか（どこで動くか）。Tool Runner と Claude Agent SDK はどちらも harness だけを提供するため、とても混同しやすい — どちらも自分で host する必要があります。

Tool Runner ≠ Claude Agent SDK. Tool Runner は通常の Anthropic SDK（anthropic / @anthropic-ai/sdk）に組み込まれていて、自分が定義した tool で loop を回すだけです — built-in tool も filesystem も sandbox もありません。ターンごとの hook が用意されているので、approval gate、エラーの intercept（error interception）、結果の修正（例：cache_control の付与）、retry を実装できます。一方、Claude Agent SDK は Claude Code そのものをライブラリとしてパッケージしたものです。

Managed Agents（beta）は最も新しい surface で、管理された deployment まで提供する唯一のものです。必須の流れは Agent（一度作成し、version 管理されて保存される）→ Session（実行ごとに1つの session）。model、system、tools は agent レベルに置き、session レベルには決して置きません。各 session はその agent の workspace となる container を作り、イベントを stream で返します；こちらからは message と tool result を送ります。さらに scheduled deployments（cron で起動される session）、vault に保存され egress 時に差し替えられる credential、ドル建ての session budget、multiagent roster もサポートしています。Beta header：managed-agents-2026-04-01。Bedrock / Vertex / Foundry では利用できません — それらのプラットフォームでは通常の Claude API + tool use を使います。

どれを選ぶか：ニーズを満たせる範囲で最もシンプルなものにとどめましょう。単発の呼び出しや、コードで制御された workflow で大半のタスクは処理できます；agent を使うのは、タスクが本当に open-ended で model 自身の判断が必要なとき、得られる価値がレイテンシとコストに見合うとき、そしてエラーを捕捉できる（test、review、rollback）ときだけにしましょう。

1.2 Multi-Agent Orchestration — 複数 agent の調整

Hub-and-Spoke Architecture — ハブ＆スポーク型アーキテクチャ

multi-agent システムの標準 pattern は hub-and-spoke です：1つの調整役 agent（coordinator）が複数の専門 subagent を管理します。

                    ┌──────────────┐
                    │  Coordinator │
                    │    Agent     │
                    └──────┬───────┘
                           │
            ┌──────────────┼──────────────┐
            ↓              ↓              ↓
     ┌──────────┐   ┌──────────┐   ┌──────────┐
     │ Subagent │   │ Subagent │   │ Subagent │
     │  Search  │   │ Analysis │   │ Synthesis│
     └──────────┘   └──────────┘   └──────────┘
Coordinator Responsibilities — coordinator の責任

coordinator の役割：

  • Decompose — タスクを subtask に分解する
  • Delegate — 適切な subagent に仕事を割り当てる
  • Route — subagent 間のすべての通信を中継する（subagent 同士が直接やり取りすることはない）
  • Aggregate — subagent の結果を集約する
  • Handle errors — subagent が失敗したときのエラー処理
  • Evaluate — 統合結果の品質を評価し、不足があれば再度割り当てる
Subagent Isolation — subagent の隔離

重要な概念：subagent の context は完全に隔離されています。coordinator の会話履歴は引き継ぎません。subagent が必要とするものはすべて、その prompt に明示的に渡す必要があります。

つまり：

  • coordinator は、関連する context をすべて subagent に渡すタスク説明に入れなければならない
  • subagent はメイン会話のそれ以前の部分を参照できない
  • 各 subagent はまっさらな状態で起動し、coordinator が与えたものしか持たない
Dynamic Subagent Selection — subagent の動的な選択

すべての query がすべての subagent を必要とするわけではありません。coordinator は：

  • query が本当に何を必要としているかを評価する
  • 関連する subagent だけを呼ぶ
  • 何でも機械的に pipeline 全体に通さない

例：単一テーマのリサーチ質問で、焦点を絞った1回の search で十分なら、web search + document analysis + synthesis をすべて使う必要はありません。

Decomposition Risks — タスク分解のリスク

狭すぎる decomposition：試験ではこの点が念入りに問われます。例：coordinator が「creative industries」（クリエイティブ産業）のリサーチを頼まれたのに、visual arts 関連の subtask にしか分解せず、音楽、執筆、映画、デザインが抜け落ちてしまう。

対策：最初の分解をより広くし、明示的なカバレッジチェック（coverage check）のステップを加える。

Iterative Refinement Loops — 反復的な改善ループ

coordinator は統合結果を評価し、不足している箇所を特定します：

Coordinator → Subagents (round 1)
         ↓
   Evaluate results
         ↓
   Identify gaps
         ↓
Coordinator → Subagents (round 2, targeted)
         ↓
   Final synthesis

1.3 Subagent Spawning and Context Passing — subagent の生成と context の受け渡し

The Agent Tool — Agent tool

subagent は Agent tool で生成されます — Claude Code と Claude Agent SDK の両方で使われる正式（canonical）な名前です。coordinator が subagent を生成するには、許可された tool のリストに Agent が含まれている必要があり、Agent(worker, researcher) 構文で特定の種類の subagent だけにアクセスを絞ることもできます。

💡 名称についての注意

古いドキュメント（exam guide の文言も含む）では、これを Task tool と呼んでいます。Task はこの仕組みに対する Claude Code の元々の名前で、現在の Claude Code と SDK のドキュメントでは Agent という名前を使っています。試験問題で「Task tool」と出てきたら、これのことです。

💡 SDK の名称

この SDK は「Claude Code SDK」から Claude Agent SDK に改名されました。Python：pip install claude-agent-sdk。TypeScript：npm install @anthropic-ai/claude-agent-sdk。最上位の entry point：query() + ClaudeAgentOptions。

Context Must Be Explicit — context は明示的に渡す

この点は試験で非常に重点的に問われます：context は自動的には引き継がれません。coordinator が subagent を生成するときは、subagent が必要とするものをすべて prompt に入れなければなりません。

悪い例（Bad）：

"Analyze the customer's issue"
# Subagent has no idea who the customer is or what the issue is

良い例（Good）：

"Customer #12345 reported that their order #67890 (placed 2024-01-15,
total $149.99) arrived damaged. They are requesting a full refund.
Analyze the order history and return policy applicability."
Parallel Subagent Execution — subagent の並列実行

subagent を並列に実行するには、coordinator の同じ1つの response の中で複数の Agent tool 呼び出しを発行します。複数のターンに分散させてはいけません — そうすると逐次実行（sequential）になってしまいます。

{
  "content": [
    {
      "type": "tool_use",
      "name": "Agent",
      "input": { "prompt": "Search for recent papers on...", "subagent_type": "search" }
    },
    {
      "type": "tool_use",
      "name": "Agent",
      "input": { "prompt": "Analyze the document at...", "subagent_type": "analysis" }
    }
  ]
}

Claude Code では、同時に実行できる subagent の数が 20（CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS）、spawn の深さ（spawn depth）が 3（CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH）に制限されています；深さの上限に達すると、その subagent からは Agent tool が取り除かれます（それ以上 spawn できなくなる）。

AgentDefinition in the Claude Agent SDK — Claude Agent SDK の AgentDefinition
from claude_agent_sdk import query, ClaudeAgentOptions, AgentDefinition

async for message in query(
    prompt="Use the code-reviewer agent to review this codebase",
    options=ClaudeAgentOptions(
        allowed_tools=["Read", "Glob", "Grep", "Agent"],
        agents={
            "code-reviewer": AgentDefinition(
                description="Expert code reviewer for Python and TypeScript",
                prompt="Analyze code quality, identify bugs, suggest improvements.",
                tools=["Read", "Glob", "Grep"],
            ),
            "test-writer": AgentDefinition(
                description="Test generation specialist",
                prompt="Write comprehensive unit tests for the provided code.",
                tools=["Read", "Write", "Bash"],
            ),
        },
    ),
):
    print(message)

subagent の context 内から発行された message には parent_tool_use_id フィールドが付きます — このフィールドを使って、message を対応する subagent の実行に紐付けます。

Forks vs Fresh Subagents — fork と新規 subagent の比較

fork は、隔離された subagent とは正反対のトレードオフです：会話のすべて — 履歴、system prompt、tools、model — を引き継ぎ、prompt cache も共有するので、まったく新しい subagent を作るより安く済みます。メイン会話に返されるのは最終結果だけで、fork 内の tool 呼び出しは隔離されたままです。fork がさらに sub-fork を spawn することはできません。

新規 subagent（Fresh subagent）Fork
会話履歴引き継がれない — すべて明示的に渡す必要があるすべて引き継がれる
System prompt / toolsその subagent 独自のもの親 session と同一
Prompt cacheCold（キャッシュなし）親 session と共有（安い）
使いどころ明確で範囲が限定されたタスク；親に影響を与えたくない「ノイズの多い」探索共通の baseline から分岐する（divergent）ブランチ

Claude Code では /subtask <prompt> で fork を開始し、SDK/CLI では --fork-session で session を新しい ID で resume できます。fork_session は、この「共通の baseline から分岐する」という同じ考え方の、API レベルでの古い呼び名です。

Structured Context Passing — 構造化された context の受け渡し

Best practice：agent 間で context を渡すときは、コンテンツ（content）と metadata を分離する。

{
  "findings": [
    {
      "claim": "Revenue increased 15% YoY",
      "evidence": "Q4 earnings report, page 3",
      "source_url": "https://example.com/earnings",
      "document_name": "Q4 2024 Earnings Report",
      "publication_date": "2025-01-15"
    }
  ]
}

こうすることで出典情報（attribution）を保持でき、context を受け取った agent が情報源の質を評価できるようになります。

1.4 Workflow Enforcement and Handoff — workflow の強制と引き継ぎ

The Critical Distinction — 最も重要な区別

これは試験で最も重点的に問われる概念の1つです：

強制の種類（Enforcement）使いどころ保証レベル
Programmatic（hooks、前提条件）金銭/安全に関わる結果があるDeterministic — 100%保証
Prompt-based（指示のみ）「ベストエフォート」で許容できるProbabilistic — 失敗率は0ではない
Example: Financial Operations — 例：金融業務

状況：カスタマーサポート agent は、返金を処理する前に本人確認をしなければならない。

誤ったやり方（prompt ベース）：

"Always verify the customer's identity before processing any refund."

これは大半の場合は正しく動作しますが、失敗率は0ではありません。金融業務では「ほとんどの場合」では許容できません。

正しいやり方（programmatic）：

process_refund に対する PreToolUse hook が、get_customer が呼ばれて検証済みの customer ID を返したかどうかをチェックします。まだなら、hook は exit code 2 で refund をブロックします。

Handoff to Humans — 人間への引き継ぎ

agent が人間に escalate するとき、受け取る側は会話の transcript 全体にアクセスできないことがほとんどです。引き継ぎには構造化されたサマリーを付ける必要があります：

Customer: Jane Doe (#12345)
Issue: Damaged product received
Order: #67890, $149.99, placed 2024-01-15
Root cause: Shipping damage
Actions taken: Verified order, confirmed damage via photos
Recommended action: Full refund + replacement shipment
Refund amount: $149.99

1.6 Task Decomposition Strategies — タスク分解の戦略

Prompt Chaining (Fixed Sequential) — prompt の連鎖（固定の逐次処理）

予測可能で多観点のタスク、つまり必要なステップが最初からはっきりわかっているタスク向け：

Step 1: Analyze each file individually (local analysis)
Step 2: Cross-file integration pass (data flow, consistency)
Step 3: Generate final report

各ステップの output が次のステップの input になります。この順序はあらかじめ決まっています。

Dynamic Adaptive Decomposition — 動的・適応的な分解

open-ended な調査、つまり発見に応じて subtask が生まれるもの向け：

Initial query: "Why is the app slow?"
  → Profile CPU usage
    → Discovery: database queries are the bottleneck
      → Analyze query patterns
        → Discovery: N+1 queries in the user listing endpoint
          → Generate fix for specific queries

subtask は、各ステップで見つかったことに基づいて生成されます。

Multi-Pass Review Architecture — 複数 pass（multi-pass）の review アーキテクチャ

大きな PR のコード review 向け：

Pass 1 — ファイルごとの local 分析：

  • 各ファイルを独立して review する
  • すべてのファイルで一貫した review の深さ
  • local な問題（bug、style、type）を捕捉する

Pass 2 — ファイル横断（cross-file）の統合：

  • ファイル同士の相互作用を見る独立した pass
  • data flow、interface の不一致、ファイル間の一貫性の問題を捕捉する
  • 統合（integration）の観点に焦点を当てた別の prompt を使う

なぜ2つの pass が必要？大きな PR を1回（single-pass）だけで review すると：

  • 注意の希釈（attention dilution）— model は最初のほうのファイルに注意を割き、後半のファイルがおざなりになる
  • 結果が矛盾する（ファイル間で基準が一貫しない）
  • 統合の問題を見落とす（ファイル単体の review ではファイル横断の問題が見えない）

1.7 Session Management — session の管理

Resuming Sessions — session の再開

--resume <session-name> は、以前に名前を付けた会話を完全な context 付きで再開します。

resume すべきとき：

  • tool の結果がまだ有効な（古くなっていない）進行中の調査
  • 同じ session 内での反復的（iterative）な開発

最初からやり直すべきとき：

  • tool の結果が古くなった（ファイルが変更された、service が再起動した）
  • context が現在のタスクから大きく逸れてしまった
  • こうした場合は resume せず、以前の発見の構造化サマリーを渡す
Forking a Session — session の fork

--fork-session は既存の session を新しい ID で resume するので、元の session はそのまま手付かずで残り、各ブランチは互いに干渉することなく別々のアプローチを探索できます。対話型の session では、/subtask <prompt> が会話全体を引き継ぐ fork を生成し、その最終結果だけを返します（§1.3 を参照）。

ユースケース：同じ出発点から2つの異なる refactor 戦略を試す。

Moving a Session Between Surfaces — surface 間での session の移動

session はもはや特定のマシンに縛られていません。claude --cloud "<task>" は cloud session で作業を開始し、claude --teleport は web session を terminal に引き戻し、/desktop は現在の terminal session を desktop アプリに引き渡して visual diff を見られるようにします。Remote Control を使えば、実行中の local session をスマートフォンや別のブラウザから操作できます。これはアーキテクチャ上重要なポイントです：「session」は持ち運び可能（portable）な状態の単位なので、agent が失ってはいけないものは scrollback（画面の履歴）ではなく、ファイルか memory に置く必要があります。

Informing Resumed Sessions — resume した session への通知

ファイルが変更された後に session を resume するときは、何が変わったかを Claude に明示的に伝える必要があります：

"Since our last session, I've updated auth.py to use JWT tokens instead of
session cookies. Please re-analyze the authentication flow with these changes."

resume した session が変更に自動で気づくと思い込まないこと — 前の session の tool の結果は、古いファイル内容を反映したままかもしれません。

Domain 2 の補強

元の spec に忠実な MCP + tool が context を圧迫することについての実際の数値。

2.1 Tool Interface Design — tool の interface 設計

Tool Descriptions Are Everything — tool の description がすべて

tool の description は、Claude がどの tool を呼ぶかを決める主要な仕組みです。description は単なる参考ドキュメントではなく、選択の基準そのものです。

悪い description（選択が不安定になる）：

{
  "name": "search",
  "description": "Search for things"
}

良い description：

{
  "name": "search_knowledge_base",
  "description": "Search the internal knowledge base for support articles, FAQs, and troubleshooting guides. Use this when the customer asks a question that may have an existing documented answer. Input should be a natural language query describing the customer's issue. Returns matching articles ranked by relevance with titles, snippets, and article IDs."
}
What to Include in Tool Descriptions — description に含めるべきもの
  1. Purpose（目的） — この tool が何をするか、いつ使うべきか
  2. Input format（入力形式） — input がどうあるべきか、例付きで
  3. Output format（出力形式） — tool が何を返すか
  4. Edge cases（境界ケース） — input が不正なときや結果がないときにどうなるか
  5. Differentiation（差別化） — 類似の tool ではなく「この」tool を使うべきとき
The Full Tool Definition Schema — tool 定義の完全な schema
{
  "name": "get_weather",
  "description": "Get the current weather in a given location. Returns temperature, conditions, humidity, and wind speed. Use this when the user asks about current weather conditions. For forecasts, use get_forecast instead.",
  "input_schema": {
    "type": "object",
    "properties": {
      "location": {
        "type": "string",
        "description": "The city and state/country, e.g. 'San Francisco, CA' or 'London, UK'"
      },
      "unit": {
        "type": "string",
        "enum": ["celsius", "fahrenheit"],
        "description": "Temperature unit. Defaults to celsius if not specified."
      }
    },
    "required": ["location"]
  }
}

strict mode は、Claude が tool 用に生成する input が schema に正確に一致することを保証します：

{

  "strict": true,
  "input_schema": {
    "type": "object",
    "properties": {
      "vendor_name": { "type": "string" },
      "invoice_number": { "type": "string" },
      "total_amount": { "type": "number" },
      "currency": { "type": "string", "enum": ["USD", "EUR", "GBP"] }
    },
    "required": ["vendor_name", "invoice_number", "total_amount", "currency"],
    "additionalProperties": false
  }
}

strict mode を使うための要件：

  • additionalProperties: false を設定する必要がある
  • すべての property が required に含まれている必要がある
  • JSON Schema の一部のサブセットのみサポート（詳しくは Domain 4 を参照）
Anti-Pattern: Ambiguous Tool Overlap — Anti-pattern：曖昧に重複する2つの tool

description がほぼ同じ tool が2つあると、Claude は route を誤ります：

Tool 1: "analyze_content" — "Analyze content for insights"
Tool 2: "analyze_document" — "Analyze a document for insights"

Claude はこの2つの tool を確実には区別できません。対策：目的がはっきり区別できるように名前を変えるか、1つの tool に統合する。

2.2 Structured Error Responses — エラー response の構造

MCP Error Structure — MCP のエラー構造

tool が失敗したとき、エラー response は汎用的な文字列ではなく、明確な構造を持つべきです：

{
  "isError": true,
  "errorCategory": "transient",
  "isRetryable": true,
  "description": "Database connection timed out after 30 seconds. The query was for customer #12345's order history.",
  "partial_results": null,
  "attempted_action": "SELECT * FROM orders WHERE customer_id = 12345"
}
Error Categories — エラーの種類
種類Retryable?例Agent のアクション
Transient（一時的）はいTimeout、service の一時的な利用不可、rate limitbackoff 付きで retry
Validation（形式エラー）いいえ（input を変えない限り）email の形式が不正、必須フィールドの欠落input を直して retry
Business（業務ルール）いいえpolicy の上限を超える返金、凍結されたアカウントescalate するか user に伝える
Permission（権限）いいえアクセス権の不足、token の期限切れEscalate
What the Agent Should Do with Errors — agent はエラーをどう扱うべきか
  1. Transient エラー：subagent がローカルに recovery の仕組み（retry with backoff）を実装すべき。recovery が失敗した場合にだけ上に propagate する。
  2. Validation エラー：Claude はエラーを確認し、input を直して retry すべき。
  3. Business エラー：Claude は user に policy を説明するか、escalate すべき。
  4. Permission エラー：Claude は人間に escalate すべき。
Anti-Patterns (Wrong Answers) — 誤ったやり方
  1. 汎用的なエラーメッセージ："Operation failed" — 原因を隠し、賢い recovery を不可能にする。
  2. エラーを黙って隠す：search engine がダウンしているのに { "results": [] } を返す。実際は「search が実行できなかった」のに、「結果がなかった」ように見えてしまう。agent は本当は「検索できなかった」のに、自信満々に user に「何も見つかりませんでした」と伝えてしまう。
  3. 曖昧なステータスメッセージ：何を試したかの背景がない "search unavailable"。
  4. 1つのステップの失敗で workflow 全体を止める：partial results を使ったり代替案を試したりせず、1つのエラーだけで複数ステップの処理全体を止めてしまう。
Distinguishing Empty from Failed — 「空」と「失敗」の区別

これは試験によく出る具体的な概念です：

状況実際に起きていること正しい response
Search が status 200 で [] を返すquery は有効、一致する結果がない「その query に一致する結果は見つかりませんでした」
Search が timeout エラーを返すquery がそもそも実行されていない「検索できませんでした。もう一度試します」

この2つは別々に扱う必要があります。前者は情報、後者はエラーです。

2.3 Tool Distribution and tool_choice — tool の配分と tool_choice パラメータ

The 4-5 Tool Maximum — tool は最大 4〜5個

各 agent が持つ tool は最大 4〜5個にすべきです。1つの agent に18個の tool を与えると選択の信頼性が下がります — Claude が間違った tool を選んだり、不要な tool を呼んだり、どれを使うべきか推論するのに苦労したりします。

複雑なシステムでの解決策：tool を複数の専門 subagent に分散させる。

Instead of:
  One agent with 18 tools

Do:
  Coordinator with: Agent, AskUser
  Search subagent with: search_web, search_docs, search_db
  Analysis subagent with: analyze_text, extract_entities, summarize
  Action subagent with: send_email, create_ticket, update_record

これが試験での標準的な正解であり、その根底にある原則（1つの agent には1つの集中した仕事）は今も正しいです。ただし、Anthropic の docs にある現在の数値も知っておく価値があります。

🔭 Beyond the Exam Guide: Tool Search — 試験範囲外：Tool Search

Anthropic の現在のガイダンスでは、agent が利用できる tool がおよそ 30〜50個を超えると tool 選択の精度が下がるとされており、典型的な複数 server の MCP 構成（GitHub、Slack、Sentry、Grafana、Splunk）では、何かをする前から tool 定義だけで約 55k token の context を「消費」します。今の対策は「subagent に分割する」だけではありません — Claude API で GA（general availability）になった tool search tool です。

"tools": [
  { "type": "tool_search_tool_regex_20251119", "name": "tool_search_tool_regex" },
  { "name": "get_weather", "description": "...", "input_schema": { ... },
    "defer_loading": true }
]

仕組み：

  1. すべての tool の定義は全部、毎回の request で送ります。defer_loading が制御するのは何が context window に入るかであって、何が送信されるかではありません。
  2. defer されていない tool はすぐに context に読み込まれ、defer された tool は読み込まれません。
  3. Claude が別の tool を必要とすると、search tool を呼びます。API は tool_reference ブロックを返し、それを context 内でその場で完全な定義に展開します — system-prompt の prefix には一切手を触れないので、prompt caching はそのまま保たれます。
  4. 2つのバリエーションがあります：tool_search_tool_regex_20251119（Claude が Python の re.search() pattern を書く、最大200文字）と tool_search_tool_bm25_20251119（自然言語の query、最大500文字）。どちらも名前、description、パラメータ名、パラメータの description を検索対象にします。
ルール詳細
すべてを defer しない少なくとも1つの tool は defer_loading: false にする必要があり、通常は search tool 自体。さもないと：400 エラー「All tools cannot be deferred」
「hot set」を残す最もよく使う 3〜5個の tool は defer せずに残し、Claude が search の往復なしですぐ呼べるようにする
上限1 request あたり最大 10,000個の deferred tool；各 search はデフォルトで 5件の一致を返す（Claude は limit を 1〜10,000 で設定可能）
Cachedefer_loading: true の tool には cache_control を付けられない — 400 エラーになる。cache の breakpoint は defer されていない tool に置く
組み合わせstrict: true と併用可能；grammar は toolset 全体から構築される
MCP個々の tool に defer_loading を設定しない — mcp_toolset エントリの default_config で設定する

使うべきとき：tool が10個以上ある、tool 定義が 10k token を超える、toolset が大きくなるにつれて精度が下がる、あるいは複数の MCP server をまとめて使っているとき。使わないほうがよいとき：tool が10個未満、すべての tool がすべての request で使われる、あるいは定義の合計が約100 token 未満のとき。

2つの概念を整理しましょう：試験の「4〜5個の tool」は、判断の時点で model の前に提示されている tool の数の話です。tool search はその数を増やしません — その数を 3〜5 に保ったまま、背後のカタログを数千の tool まで膨らませられるようにするものです。

tool_choice Parameter — tool_choice パラメータ

Claude が tool とどう関わるかを制御します：

値挙動ユースケース

"any"Claude は必ずいずれかの tool を呼ぶ必要があるが、どれを呼ぶかは選べるstructured output を保証する

When to Use Each — それぞれの使いどころ

"auto" — ほとんどの会話。tool が必要かどうかを Claude が自分で決める。

"any" — structured output を保証する必要があるとき。例：複数の異なる extraction schema（invoice、receipt、contract）があり、Claude に適切な schema を選ばせたうえで、必ず structured data を返させたい。

特定 tool の強制 — 特定の tool を先に実行しなければならないとき。例：どの enrichment ステップよりも先に必ず extract_metadata を呼ぶ。

"none" — あるターンで文章（例：最後の要約ステップ）を生成する必要があるが、request から tool 定義を取り除きたくないとき。

# Force Claude to call a specific tool

    model="claude-opus-5",
    messages=[...],
    tools=[...],

)

What is MCP? — MCP とは？

Model Context Protocol は、AI model を外部のデータソースやツールに接続するためのオープン標準です。Claude が database、API、ファイルシステム、その他のサービスとやり取りするための統一された方法を提供します。

Project-Level Configuration (.mcp.json) — project レベルの設定

このファイルは project のルートに置き、version control に含めます：

{
  "mcpServers": {
    "shared-api": {
      "type": "http",
      "url": "https://example.com/mcp",
      "headers": { "Authorization": "Bearer ${API_TOKEN}" },
      "timeout": 600000
    },
    "postgres": {
      "command": "npx",
      "args": ["@modelcontextprotocol/server-postgres"],
      "env": {
        "DATABASE_URL": "${DATABASE_URL}"
      }
    }
  }
}

重要な詳細：

  • ${DATABASE_URL} — 環境変数の展開（environment variable expansion）。本物の secret は config ファイルに入れない。変数が未設定の可能性があるときは ${VAR:-default} を使う。
  • command + args — MCP server のプロセスを起動する方法（stdio transport）
  • timeout — server ごとの tool 実行 timeout（ミリ秒）；その server に限り MCP_TOOL_TIMEOUT を上書きする
  • 対話型 session（interactive session）では、Claude Code は .mcp.json の project scope の server を使う前に承認を求めます。一方、claude -p、Agent SDK の session、cloud で動く session ではそのプロンプトを表示できないため、確認なしで読み込みます — headless 実行から server を除外するには disabledMcpjsonServers または --setting-sources を使う
  • 一部の server 名は予約（reserved）されています：workspace、claude-in-chrome、computer-use、Claude Preview、Claude Browser — 使うと警告付きで無視される
Authentication for Remote Servers — リモート server の認証

HTTP と SSE の server は OAuth をサポートします — session 内で /mcp を実行する（または claude mcp add してから認証する）と、Claude Code がブラウザのフローと token の refresh を自動で処理します。OAuth をサポートしないサービスには、headers で static token を渡すか、credential の有効期限が短い場合は headersHelper（stdout の出力が header の値になる command）で接続時に token を生成します。WebSocket server は header での認証のみです。

Tool Search Is On by Default in Claude Code — Claude Code では Tool Search がデフォルトで有効

MCP の tool 定義はデフォルトで deferred です：session の開始時に読み込まれるのは tool 名と server instructions だけで、残りは必要に応じて Claude が search します。だから Claude Code は server ごとの tool 数に上限を設けていません — 実際の上限はあなたの context 予算だけです。

ENABLE_TOOL_SEARCH挙動
（未設定）すべての MCP tool が deferred、必要に応じて読み込み
true強制的に defer（proxy 経由でも beta header を送る）
auto / auto:Ndeferred 定義の合計が context window の 10%（または N%）未満なら事前に読み込み；その閾値を超えたら defer
false最初からすべての MCP tool を読み込む

Claude が毎ターンその server の tool を使う必要があるときは、server エントリに "alwaysLoad": true を設定して deferral の対象外にします。server の作者は良い server instructions を書くべきです — tool search が有効なとき、その instructions こそが Claude があなたの server を search するかどうかを判断する根拠になります。Claude Code は tool の description と server instructions をそれぞれ 2 KB で切り詰め（truncate）ます。

Output Limits — output の上限

Claude Code は MCP tool の output が 10,000 token を超えると警告し、デフォルトでは 25,000 token で自動的に切り詰め（truncate）ます。この上限は MAX_MCP_OUTPUT_TOKENS で引き上げられますが、警告の閾値は固定で変更できません。これこそが tool output の切り詰め（Domain 5）が重要である仕組み上の理由です — 「おしゃべりな」server は、自分の response の末尾を黙って失ってしまうことがあります。

  • type 文字列の version 管理。web_search_20260209 / web_fetch_20260209 には動的フィルタリング（dynamic filtering）が追加されており、Opus 4.6+ / Sonnet 4.6+ が必要；古い model では基本版の web_search_20250305 / web_fetch_20250910 を使う。_20260209 系と並べて code_execution を宣言しないこと — これらはすでに内部でコードを実行しており、実行環境が2つ同時にあると model が混乱する。
  • Web fetch は会話内にすでに出てきた URL しか fetch しない。crawler ではない。
  • server-tool のエラーは exception を raise しない。HTTP 200 で、result block 内にエラーオブジェクトを入れて返す（例：{"error_code": "max_uses_exceeded"}）。web search では、成功時の content は list、エラー時の content は object — index でアクセスする前にこれを分岐チェックする必要がある。これはまさに §2.2 の「空 vs エラー」の区別の API レイヤー版。
  • pause_turn は、server-side tool のループが内部上限に達したことを知らせる方法。その response を送り返せば続行する（Domain 1 §1.1 参照）。
  • Bash と text editor には schema がない。input_schema 付きで "bash" という名前の独自 custom tool を宣言すると、それは別の tool として扱われる。
  • Advisor tool：その model は request の最上位の model と同等以上の能力が必要（例：executor が claude-sonnet-5 → advisor は claude-opus-5 でなければならない）。無効な組み合わせは 400 エラーを返す。
Parallel Tool Use — tool の並列呼び出し

デフォルトでは、Claude は1つの assistant message で複数の tool_use ブロックを出せます。それらを並行して実行し、すべての tool_result ブロックを1つの user message にまとめて返しましょう。複数の message に分けると、Claude に並列 tool 呼び出しをやめるよう黙って「教えて」しまいます。エラーになった tool についても、is_error: true を付けて tool_result を必ず返す — 決して省略しないこと。

Programmatic Tool Calling — プログラムによる tool 呼び出し

Claude は、会話を経由するのではなく、code 実行 sandbox の中から直接あなたの custom tool を呼べます — 通常の経路だと context をあふれさせてしまう大きな結果を返す tool で便利です。{"type": "code_execution_20260120", "name": "code_execution"} を宣言し、その custom tool に "allowed_callers": ["code_execution_20260120"] を設定します。保留中の programmatic 呼び出しに応答するとき、user message には tool_result ブロックだけを含められます — テキストは不可。strict: true、disable_parallel_tool_use、強制された tool_choice、MCP tool とは互換性がありません。

MCP from the API Side: the MCP Connector — API 側から見た MCP：MCP Connector

defer_loading は、個々の tool 定義ではなく、mcp_toolset エントリの default_config（または configs で tool ごと）に一度だけ設定します。

3.1 CLAUDE.md Hierarchy — CLAUDE.md の階層構造

What is CLAUDE.md? — CLAUDE.md とは？

CLAUDE.md ファイルは、特定の文脈で Claude Code がどう振る舞うべきかを伝える指示ファイルです。.editorconfig や .eslintrc に似ていますが AI agent 向けで、coding standard、project の規約、使える tool の制限、workflow のルールを定義するのに使います。

Loading Order (Broader → More Specific) — 読み込み順（一般的 → 具体的）

Claude Code は CLAUDE.md ファイルを階層構造で読み込みます。より具体的なファイルほど、より一般的なファイルを上書き（override）します：

1. Managed Policy (org-wide, admin-controlled)
   └── /etc/claude-code/CLAUDE.md                           (Linux, WSL)
   └── /Library/Application Support/ClaudeCode/CLAUDE.md    (macOS)
   └── C:\Program Files\ClaudeCode\CLAUDE.md                (Windows)

2. User-Level (personal, NOT version-controlled)
   └── ~/.claude/CLAUDE.md

3. Project-Level (shared via version control)
   └── ./CLAUDE.md  or  ./.claude/CLAUDE.md

4. Local project (personal, gitignored)
   └── ./CLAUDE.local.md

5. Directory-Level (loaded on demand)
   └── ./src/api/CLAUDE.md (loaded when Claude reads files in src/api/)
   └── ./tests/CLAUDE.md (loaded when Claude reads files in tests/)

重要な違い：project レベルの CLAUDE.md は git に commit され、チーム全体で共有されます。user レベルは個人用でローカルのみ。CLAUDE.local.md は project ごとの個人用ファイルです（gitignore を忘れずに）。directory レベルの CLAUDE.md は、Claude がそのディレクトリで作業するときに動的に読み込まれます。

AGENTS.md Interop — AGENTS.md との連携

通常の session では、Claude Code は CLAUDE.md を読み、AGENTS.md は読みません — ただし /init は scaffold（project の骨組み作成）時に既存の AGENTS.md ファイルを読みます。repo ですでに他の coding agent 向けに AGENTS.md を使っているなら、それを import して情報源を1つに保ちましょう：

# CLAUDE.md
@AGENTS.md

## Claude-specific overrides
Use plan mode for changes under `src/billing/`.
@import Syntax — @import 構文

CLAUDE.md ファイルは他のファイルを import して、config を module 化して整理できます：

# Project Configuration

@docs/coding-standards.md
@docs/api-conventions.md
@~/.claude/my-personal-preferences.md

See @README.md for project overview.

パス解決のルール：

  • 相対パスは、import 文を含むファイルの場所を基準に解決される
  • @~/ はユーザーのホームディレクトリを指す
  • import の最大深さ：5階層（循環 import を防ぐため）
  • import されたファイルの中にも @import を含められる（深さの上限を超えない限り）
.claude/rules/ Directory — .claude/rules/ ディレクトリ

トピックごとの rule を、別々のファイルに整理するのに使います：

.claude/
  rules/
    testing.md       — Testing conventions
    api-design.md    — API endpoint patterns
    security.md      — Security requirements
    typescript.md    — TypeScript-specific rules

frontmatter なし：rule は session 開始時に無条件で読み込まれる。
frontmatter あり：rule はファイルパスに基づいて条件付きで読み込まれる。

Auto Memory — 自動メモリ

Claude Code は次の場所に memory を自動的に維持します：

~/.claude/projects/<project>/memory/MEMORY.md
  • 最初の200行 または 25 KB（先に達したほう）が session 開始時に読み込まれる
  • ローカルのマシンにのみ保存（version control には入れない）
  • 同じ git repo 内のすべての worktree は1つの memory ディレクトリを共有する
  • Claude は project の pattern、決定事項、好みをここに自動でメモする
  • Claude Code v2.1.59 以降が必要
  • autoMemoryEnabled: false でこの機能を無効化；autoMemoryDirectory で保存場所を変更
  • MEMORY.md の隣にあるトピック別ファイル（例：debugging.md、api-conventions.md）は必要に応じて読み込まれる — 200行の制限は MEMORY.md だけに適用される

When Path-Specific Rules Beat Directory CLAUDE.md — パス指定の rule がディレクトリ単位の CLAUDE.md より優れる場合

状況：testing の規約を、codebase 全体に散らばった test ファイルに適用する必要がある。

src/
  components/
    CLAUDE.md  ← Would need testing rules here
    Button.test.tsx
  api/
    CLAUDE.md  ← And here
    users.test.ts
  utils/
    CLAUDE.md  ← And here
    format.test.ts

.claude/

    testing.md  ← One file with paths: ["**/*.test.*"]

  • testing の規約の情報源が1つだけになる
  • test ファイルがあるすべての場所に適用される（後から作られる新しいディレクトリも含む）
  • CLAUDE.md ファイルをあちこちのディレクトリに複製する必要がない

3.4 Plan Mode vs Direct Execution — Plan mode と直接実行

Plan mode は現在、より大きな permission-mode システムの中の1つのモードにすぎません。--permission-mode <mode> で特定のモードから開始したり、対話型 session で Shift+Tab を押してモードを切り替えたりできます。

4.1 Explicit Criteria — 明確な基準

The Problem with Vague Instructions — 曖昧な指示の問題点

曖昧な指示は、model が実行のたびに異なる解釈をするため、一貫しない結果を生みます。

悪い（曖昧）：

"Be conservative when flagging issues."
"Only report high-confidence findings."
"Use your best judgment on severity."

良い（明確）：

"Flag a comment as outdated ONLY when the claimed behavior directly
contradicts the actual code behavior. Do NOT flag comments that are
merely incomplete or could be more detailed."
Explicit Criteria Structure — 明確な基準の構造

model が下す判断の種類ごとに、次を定義します：

  1. What qualifies — その判断を発動させる具体的な条件
  2. What doesn't qualify — 発動させるべきでない境界ケース
  3. Examples — その境界を示す具体的な input/output の組
Flag as SECURITY ISSUE when:
  - User input is passed to SQL queries without parameterization
  - User input is rendered in HTML without escaping
  - Credentials are hardcoded in source files

Do NOT flag:
  - ORM queries (already parameterized)
  - Rendering user input in server-side templates with auto-escaping
  - Credentials loaded from environment variables
False Positive Impact — false positive の影響

ある category の false positive 率が高いと、正確に機能している category も含め、すべての category への信頼が下がります。開発者は正しいものも含めて、すべての警告を無視し始めます。

解決策：ある category の false positive 率が高いときは、いったんそれを無効化し、criteria prompt を改善してから再度有効化する。ノイズの多い1つの category に、正確な category の価値を損なわせないこと。

4.2 Few-Shot Prompting — 例示による prompting

When to Use Few-Shot — few-shot を使うべきとき
  • 文章での指示では十分に正確にできない曖昧な状況
  • format や推論のスタイルを具体的に示す必要があるタスク
  • extraction（データ抽出）タスクでの hallucination の削減
  • edge case の扱い方を示す
How Many Examples — 例はいくつ使うべきか

目的のはっきりした 2〜4個の例がスイートスポット（sweet spot）です。少なすぎると pattern を網羅できないことがあり、多すぎると context を消費し、model がその例自体に overfit することもあります。

What Good Examples Include — 良い例に含めるべきもの

各例で示すべきこと：

  1. Input — model が受け取るもの
  2. Output — model が生成すべきもの
  3. Reasoning — なぜその output が正しいのか（何をするかだけでなく、その理由）
Example 1:
Input: "// Returns the user's full name"
Code: function getName(user) { return user.firstName; }
Output: {
  "issue": "Comment claims full name but function only returns firstName",
  "severity": "medium",
  "location": "line 1",
  "reasoning": "The comment says 'full name' but the code returns only
    firstName, not firstName + lastName. This is a factual contradiction."
}

Example 2:
Input: "// Validates the input"
Code: function validate(input) { return input.length > 0 && input.length < 100; }
Output: null
Reasoning: "The comment says 'validates input' and the function does validate
  input. The comment is vague but not wrong — it doesn't claim specific
  validation rules that contradict the implementation."
Few-Shot Enables Generalization — few-shot は model の汎化を助ける

良い例は、個別のケースだけでなく pattern を model に教えます。model は丸暗記ではなく、各例の背後にある理屈を理解することで、新しい状況へ汎化できるようになるべきです。

4.3 Structured Output via tool_use — tool_use による structured output

The Problem — 問題

Claude に構造化データ（JSON）を返させたいとき、自由形式（free-form）のテキスト生成では次のようなことが起こりえます：

  • 形式が壊れた（malformed）JSON
  • 必須フィールドの欠落
  • 想定外のフィールド名
  • 誤ったデータ型
Solution 1: tool_use with Schema — 解決策1：schema 付きの tool_use

期待する output の構造を表す tool を定義します：

{
  "name": "extract_invoice_data",
  "description": "Extract structured data from an invoice document",
  "input_schema": {
    "type": "object",
    "properties": {
      "vendor_name": {
        "type": "string",
        "description": "The company or person who issued the invoice"
      },
      "invoice_number": {
        "type": "string",
        "description": "The unique invoice identifier"
      },
      "line_items": {
        "type": "array",
        "items": {
          "type": "object",
          "properties": {
            "description": { "type": "string" },
            "quantity": { "type": "number" },
            "unit_price": { "type": "number" },
            "total": { "type": "number" }
          },
          "required": ["description", "quantity", "unit_price", "total"]
        }
      },
      "total_amount": { "type": "number" },
      "currency": {
        "type": "string",
        "enum": ["USD", "EUR", "GBP", "other"]
      }
    },
    "required": ["vendor_name", "invoice_number", "line_items", "total_amount", "currency"]
  }
}

tool_choice: {"type": "tool", "name": "extract_invoice_data"} を使って Claude にこの tool を必ず呼ばせ、structured output を確実に得ます。

Solution 2: Strict Mode — 解決策2：Strict Mode

tool 定義に "strict": true を追加すると、schema への完全な準拠が保証されます：

{
  "name": "extract_invoice_data",
  "strict": true,
  "input_schema": {
    "type": "object",
    "properties": { ... },
    "required": ["vendor_name", "invoice_number", "line_items", "total_amount", "currency"],
    "additionalProperties": false
  }
}

strict mode の要件：

  • additionalProperties: false を設定する必要がある
  • すべての property を required に列挙する必要がある
Solution 3: output_config (Direct JSON Output) — 解決策3：output_config（JSON を直接出力）

tool_use を使う代わりに、JSON の output を直接要求することもできます。使うパラメータは output_config.format です。旧来の top-level パラメータ output_format は deprecated です — 新しいコードでは使わないこと — また、旧来の beta header structured-outputs-2025-11-13 も不要になりました：

response = client.messages.create(
    model="claude-opus-5",
    messages=[{"role": "user", "content": "Extract data from this invoice: ..."}],
    output_config={
        "format": {
            "type": "json_schema",
            "schema": {
                "type": "object",
                "properties": {
                    "vendor_name": { "type": "string" },
                    "total_amount": { "type": "number" }
                },
                "required": ["vendor_name", "total_amount"],
                "additionalProperties": false
            }
        }
    }
)
💡 SDK helper

client.messages.parse()（Python/TypeScript）はこの pattern をあらかじめパッケージしたものです — Pydantic model か Zod schema を渡すだけで、output_config.format を自動で送り、あなたの schema で response を validate し、response.parsed_output で parse 済みのオブジェクトを返してくれます。structured outputs を扱うときは、JSON を手作業で parse するよりこちらを優先しましょう。

Schema Compliance vs Semantic Correctness — schema への準拠 vs 意味的な正しさ

試験で重要な概念：structured output は schema compliance（正しいデータ型、必須フィールドがそろっている、有効な enum）は保証しますが、semantic correctness（意味・内容の正しさ）は保証しません。

Schema compliance: ✅ "total_amount": 150.00（型は正しく、フィールドも存在する）
Semantic error: ❌ "total_amount": 150.00 なのに line items の合計は 175.00

こうした意味的なエラーを捕まえるには、別途 validation のロジックが必要です。

Schema Design Patterns — schema 設計の pattern

Required vs Optional Fields（必須フィールドと任意フィールド）：

{
  "purchase_order_number": {
    "type": ["string", "null"],
    "description": "PO number if present on the invoice, null if not found"
  }
}

元のドキュメントにその情報が含まれていない可能性があるときは、nullable なフィールドを使います。すべてを required にすると、Claude はデータを捏造せざるを得なくなることがあります。

"other" 付きの enum：

{
  "document_type": {
    "type": "string",
    "enum": ["invoice", "receipt", "contract", "purchase_order", "other"]
  },
  "document_type_detail": {
    "type": ["string", "null"],
    "description": "If document_type is 'other', describe the document type"
  }
}

"unclear" 付きの enum：

{
  "payment_status": {
    "type": "string",
    "enum": ["paid", "unpaid", "partial", "unclear"]
  }
}

選択肢として "unclear" を加えると、情報がはっきりしないときに Claude が当て推量するのを防げます。

JSON Schema Limitations in Strict Mode — Strict Mode における JSON Schema の制限

Strict mode は JSON Schema のサブセットのみサポートします：

Supported（サポートされる）NOT Supported（サポートされない）
type (object, array, string, integer, number, boolean, null)minimum, maximum, multipleOf
properties, requiredminLength, maxLength
enum, constpattern (regex), patternProperties
items（array 用）oneOf, if/then/else
anyOf, allOf, $ref/$defs再帰的な schema（Recursive schemas）
additionalProperties: false（すべての object で必須）false 以外の値に設定した additionalProperties

以前の structured outputs のバージョンでは anyOf/allOf はサポートされていませんでしたが、現在はサポートされています。Python と TypeScript の SDK は、送信前にサポートされない制約を schema から自動で取り除き（strip）、代わりに client 側でそれらを validate します。

実務上の意味：数値の範囲（numeric range）、文字列の長さ、regex pattern、複雑な条件付き schema の validate は、schema の中ではなく、あなたの validation コードで処理する必要があります。

4.4 Validation-Retry Loops — validate して retry するループ

The Pattern — 実装 pattern
max_retries = 3

for iteration in range(max_retries):
    response = extract_data(document, prompt)
    errors = validate(response)

    if not errors:
        return response  # Success

    # Append specific errors to prompt for next attempt
    prompt += f"""
    Your previous extraction had these validation errors:
    {json.dumps(errors, indent=2)}

    Please correct these specific issues and try again.
    """

raise ExtractionError(f"Failed after {max_retries} attempts: {errors}")
What Validation Catches — validation で捕まえられるもの

Schema validation（確実に捕まえられる）：

  • 必須フィールドの欠落
  • データ型の誤り
  • 無効な enum 値
  • 形式の誤った日付や email

Semantic validation（独自のロジックが必要）：

  • line item の合計が total と合わない
  • 未来であってはならない日付が未来になっている
  • 参照されたエンティティが存在しない
  • フィールド間の矛盾
Self-Correction Patterns — 自己修正の pattern

計算値 vs 記載値（Calculated vs Stated）：

{
  "stated_total": 150.00,
  "calculated_total": 175.00,
  "conflict_detected": true,
  "conflict_note": "Stated total ($150) doesn't match sum of line items ($175)"
}

記載された値と自分で計算した値の両方を抽出することで、ズレを自動的に検出できます。

When Retries Don't Work — retry が無意味なとき

情報が元のドキュメントにそもそも存在しない場合、retry は効果がありません。請求書に PO 番号がなければ、何回 retry しても出てきません。

解決策：retry を繰り返すのではなく、nullable/optional なフィールドを使い、欠けているデータには null を許容する。

Tracking False Positives — false positive の追跡

どのコード構造が finding を引き起こしたかを追跡するために、detected_pattern フィールドを追加します：

{
  "issue": "Potential SQL injection",
  "detected_pattern": "string concatenation in query",
  "file": "users.py",
  "line": 42
}

これにより、よく dismiss される pattern を分析できます — 開発者が「string concatenation in query」の finding を何度も dismiss しているなら、その pattern の criteria prompt を調整し直す必要があるかもしれません。

4.6 Multi-Pass Review — 独立した複数回の review

The Self-Review Problem — 自己 review の問題

Claude がコードを生成し、同じ session でそれを自分で review すると、生成時の推論の文脈（reasoning context）がそのまま残っています。なぜそう判断したのかを「覚えている」ので、その判断自体を疑う可能性が低くなります。

これを reasoning context bias（推論の文脈を保持していることによるバイアス）と呼びます。

The Solution: Independent Review Instances — 解決策：独立した review instance を使う
Session 1: Claude generates code
                    ↓
            (completely separate session)
                    ↓
Session 2: Claude reviews the code
           (no knowledge of why decisions were made)
Multi-Pass Architecture for Large PRs — 大きな PR 向けの複数 pass アーキテクチャ

Pass 1 — ファイルごとの local 分析：

  • 各ファイルを独立して review する
  • すべてのファイルで review の深さを一貫させる
  • 捕捉できるもの：bug、style の問題、型エラー、セキュリティの脆弱性
  • ファイルごとに別々の prompt

Pass 2 — ファイル横断の統合（Cross-file integration）：

  • ファイル同士の相互作用を review する
  • 統合の問題に焦点を当てた別の prompt
  • 捕捉できるもの：データフロー（data flow）の問題、interface の不一致、module 間の境界でのエラー処理の欠落
  • Pass 1 の結果を文脈として受け取る
Why Not Single-Pass? — なぜ1回だけの review ではダメなのか

大きな PR（10ファイル以上）では、1回だけの review（single-pass）には次の問題があります：

  1. Attention dilution（注意の希釈） — model は最初のほうのファイルに集中し、後半のファイルへの注意が薄れる
  2. Inconsistent standards（基準の不一致） — ファイルによって review の質がばらつく
  3. Missing integration issues（統合の問題の見落とし） — 1回の pass でファイルを1つずつ review するだけでは、ファイル横断の問題が見えない

Assistant Prefill Is Gone — Assistant Prefill は廃止された

response の形式を強制するために最後の assistant ターンを prefill すると、Fable 5、Opus 5、Sonnet 5、そして 4.6/4.7/4.8 系すべてで 400 エラーが返ります。代わりに structured outputs（output_config.format）か system prompt での指示を使いましょう。これで、多くの古いドキュメントがいまだに推奨している prompt engineering のテクニックが1つ終わりを迎えました。

Mid-Conversation System Messages — 会話の途中の system message

Claude Opus 5、Opus 4.8、Fable 5 では（Sonnet 5 は対象外、beta header 不要）、top-level の system フィールドを編集する代わりに、messages 配列に {"role": "system", "content": "..."} を追加できます。これは prompt-injection に対して安全な operator 用のチャネルであり、— キャッシュ済みの prefix に触れないので — 最も安いチャネルでもあります。制約：user の message（または server-tool use で終わる assistant の message）の後に続く必要があり、messages[0] にはできず、最後の message であるか、後ろに assistant のターンが続く必要があります。

4.8 Prompt Caching — prompt のキャッシュ

Caching は prompt の *構造* の問題なので、運用手順書（ops runbook）ではなくこのセクションに属します。

Prefix match（prefix の一致）：cache は正確な prefix（接頭部分）に基づいて一致します。prefix のどこか1バイトでも変わると、それ以降のすべてが無効になります。レンダリング順は tools → system → messages なので、request 間で tool のリストの順序が変わると、system prompt とその後ろの会話全体の cache が無効になります。

設計のルール：安定した内容（固定の system prompt、順序が決まった tool のリスト）を先に置き、変わりやすい内容（timestamp、request ごとの ID、実際の質問）は最後の cache_control breakpoint の後に置く。

Mechanic（仕組み）Detail（詳細）
Breakpoints1 request あたり最大4つ（cache_control: {"type": "ephemeral"}）
Minimum prefix（最小 prefix）約1024 token — それより短い prefix は黙って cache されない
Verification（確認）usage.cache_read_input_tokens。連続する複数の request でこれが 0 なら、何かが prefix を無効にしている
Pre-warming（事前のウォームアップ）max_tokens: 0 で output を生成せずに cache エントリを温める

黙って cache を無効にするもの — チェックリスト：system prompt 内の datetime.now()、key の順序が非決定的（non-deterministic）な JSON の serialize、request ごとに変わる tool のセット、prefix に挿入された session ID やユーザー名、会話の途中での speed（fast mode）の切り替え。

tool search との関係：deferred（読み込みを遅延した）tool は system prompt の prefix から除外され、discover された tool は inline で挿入されるので、defer_loading は cache を *そのまま保ちます*。defer_loading: true の tool は同時に cache_control を持てません — breakpoint は defer されていない tool に置きましょう。

5.1 Conversation Context Management — 会話の context 管理

The Context Window Is Finite — context window は有限

Claude の context window には上限があります。すべての message、すべての tool result、そして system prompt が token を消費します。会話が長くなるほど、古い情報が圧縮されたり、完全に抜け落ちたりして品質が劣化しやすくなります。

現在のサイズ — 「1M tokens」は問題の形を変えただけで、問題そのものを消したわけではありません：

ModelContext windowMax output
Claude Fable 5 / Opus 5 / Sonnet 51M tokens128k
Claude Opus 4.8 / 4.7 / 4.6, Sonnet 4.61M tokens128k
Claude Haiku 4.5200k tokens64k

1M の window に伴う2つの罠：

  1. window が大きくても無料ではない。その中のすべての token は毎ターン課金され、下で説明する「lost in the middle」効果は context が長くなるほど悪化します。「できるから」という理由で 1M の window を埋め尽くすのは、お金がかかるうえに品質も下げます。
  2. token の数え方が変わった。Opus 4.7 で新しい tokenizer が導入され、Opus 4.8、Opus 5、Fable 5 に引き継がれています：同じテキストでも 4.7 より前の model に比べて token 数が約30%多くなります。古い model で調整した budget、chunk サイズ、閾値（threshold）はすべて messages.count_tokens で再計測（re-baseline）する必要があります — tiktoken は絶対に使わないこと。
Progressive Summarization Risks — 段階的な要約のリスク

context が圧縮されると（/compact や自動圧縮によって）、システムはそれまでの会話を要約します。これにはリスクが伴います：

要約で失われやすいもの：

  • 正確な数値（$149.99 が「約 $150」になる）
  • 具体的な日付（2024-01-15 が「1月中旬」になる）
  • 正確なパーセンテージ（23.7% が「約24%」になる）
  • Order number、customer ID、参照コード
  • 正確なエラーメッセージと stack trace

解決策：Case Facts Block

重要な取引データを、要約を経ても生き残る、常に保持される構造化ブロック（structured block）に抽出します：

CASE FACTS (do not summarize):
- Customer ID: #12345
- Order: #67890
- Order date: 2024-01-15
- Total: $149.99
- Issue: Damaged product on arrival
- Refund requested: Full refund ($149.99)
The "Lost in the Middle" Effect — 「lost in the middle」効果

model は長い input の最初と最後を、中間よりもはるかに確実に処理します。大きな context の中間にある情報は見落とされやすくなります。

軽減策：

  1. 重要な発見の要約を、統合用 input（aggregated input）の冒頭に置く
  2. 明確な section header でナビゲーションの構造（navigation structure）を作る
  3. 重要な情報を長いドキュメントの中間部分から遠ざける
  4. 大量の内容を詰め込まざるを得ない場合は「bookend」する — 重要な部分を両端に置く
Tool Output Trimming — tool output の削減

tool の結果は非常に冗長になりがちです。顧客の注文を調べるコマンドが、5つしか必要ないのに40個のフィールドを返すこともあります。

Bad：40個のフィールドをそのまま返し、context を無駄に消費する。

Good：Claude に返す前に、関連するフィールドだけに削る：

5.3 Error Propagation — エラーの伝播

Structured Error Context — 構造化されたエラー context

エラーが起きたら、十分な context を付けて伝播させます：

{
  "failure_type": "timeout",
  "service": "knowledge_base_search",
  "attempted_query": "return policy for electronics over $500",
  "timeout_duration_ms": 30000,
  "partial_results": null,
  "alternative_approaches": [
    "Try searching with simpler terms",
    "Check the FAQ section directly",
    "Ask the customer for the specific product"
  ],
  "is_retryable": true,
  "retry_after_ms": 5000
}

これにより、Claude が賢い復旧（recovery）の判断を自分で下すのに十分な情報が得られます。

Anti-Patterns — 避けるべき pattern

1. Generic error messages（汎用的なエラーメッセージ）：

{ "error": "Operation failed" }

何がなぜ失敗したのかわからないため、Claude は賢く復旧できません。

2. Silent suppression（エラーを黙って隠す）：

{ "results": [] }  // Returned when the search engine was actually down

Claude は、本当は「検索できなかった」のに、自信を持ってユーザーに「その件に関する情報は見つかりませんでした」と伝えてしまいます。この2つは本質的にまったく異なる状況です。

3. Workflow termination（workflow 全体を止める）：

Step 1: Get customer info → Success
Step 2: Search knowledge base → Timeout
Step 3: ABORT ENTIRE WORKFLOW

より良い方法：部分的な結果（partial results）で続行し、欠けている部分を記録し、代替案を提案する。

Access Failure vs Empty Result — アクセスエラー vs 空の結果
SituationHTTP StatusMeaningAgent Response
有効な検索、一致なし200 + 空の配列関連するコンテンツが存在しない「一致する記事は見つかりませんでした」
Search service がダウン503 / timeout検索が実行されなかった「現在検索できません。別の方法を試します」
Subagent Error Recovery — subagent でのエラー復旧

subagent は一時的なエラー（transient failures）に対して local recovery（ローカルでの復旧）を自分で実装すべきです：

Subagent: Search for "return policy"
  → Timeout
  → Retry with backoff (local recovery)
  → Success on second attempt
  → Return results to coordinator

subagent が自力で解決できないエラーだけを伝播（propagate）させます。伝播させるときは次を含める必要があります：

  • 何を試したか
  • どんな部分的な結果が得られたか
  • 具体的なエラーは何か
  • retry できるかどうか

5.4 Large Codebase Context Management — 大規模 codebase の context 管理

Context Degradation in Extended Sessions — 長い session での context の劣化

長い session では、Claude の信頼性が劣化します：

  • 以前に見つけた具体的なコードではなく「典型的な pattern」を引用する
  • 同じコードについて一貫しない回答をする
  • 以前の発見を忘れる
  • 確認し直すのではなく推測で進め始める
Mitigation Strategies — 軽減策

1. Scratchpad Files

発見をファイルに保存し、context の圧縮を経ても残るようにします：

# scratchpad.md
## Auth System Findings
- Entry point: src/auth/middleware.ts:23
- Uses JWT with RS256
- Token expiry: 1 hour
- Refresh token: 7 days
- Role check: src/auth/roles.ts:45
- Known issue: No token revocation mechanism

context が圧縮されたら、Claude は scratchpad を読み直してそれらの発見を取り戻せます。

2. Subagent Delegation

冗長な探索（verbose exploration）を subagent に隔離します：

Main context: Clean, focused on the task
  ↓
Explore subagent: Reads 50 files, searches codebase extensively
  ↓
Returns: Concise summary of findings
  ↓
Main context: Receives only the summary, stays clean

3. /compact Proactive Use

長い session では、context が勝手に劣化する前に自分から compact しましょう。構造化されたサマリーで能動的に compact するほうが、auto-compression に予測できない形で情報を失わせるより優れています。

長時間実行される multi-agent workflow 向け：

5.5 Human Review Workflows — 人間による review の workflow

Stratified Random Sampling — 層化ランダムサンプリング

output 全体から均等にランダムサンプリングするだけではいけません。リスクの度合いや category で層別（stratify）しましょう：

Category A (high-risk): Sample 20% of outputs
Category B (medium-risk): Sample 10% of outputs
Category C (low-risk): Sample 5% of outputs

これにより、人間の review の労力を、エラーが起きる可能性が最も高い領域に集中させられます。

Field-Level Confidence Scores — フィールドごとの confidence スコア

抽出（extraction）全体に1つの confidence スコアを付けるのではなく、フィールドごとに confidence を付けます：

{
  "vendor_name": { "value": "Acme Corp", "confidence": 0.99 },
  "total_amount": { "value": 149.99, "confidence": 0.95 },
  "purchase_order": { "value": "PO-2024-001", "confidence": 0.72 },
  "tax_id": { "value": "12-3456789", "confidence": 0.45 }
}

Calibration（較正）：confidence スコアは、ラベル付き（labeled）の validation データセットに基づいて較正する必要があります。confidence 0.9 は、そのフィールドが約90%の確率で正しいことを意味しなければなりません。較正されていなければ、これらの confidence の数値はまったく意味を持ちません。

Accuracy by Document Type — ドキュメント種別ごとの精度

隠れたエラー pattern（hidden failure pattern）：

Overall accuracy: 97% ← Looks great!

Breakdown:
  Standard invoices: 99.5% ← Excellent
  Handwritten notes: 45%  ← Terrible
  Foreign language docs: 62% ← Bad

集計指標（aggregate metric）は、特定のドキュメント種別での低い性能を隠してしまうことがあります。精度は必ずドキュメント種別ごと・フィールドごとに分解して見ましょう。

Per-Document-Type Reporting — ドキュメント種別ごとのレポート

ドキュメント種別ごと、かつその中のフィールドごとに accuracy を報告します：

Standard Invoices:
  vendor_name: 99.8%
  total_amount: 99.2%
  line_items: 97.5%
  tax_id: 94.1%

Handwritten Notes:
  vendor_name: 85.0%
  total_amount: 42.0% ← Critical failure
  line_items: 38.0% ← Critical failure

これにより、集計値の陰に隠れることなく、システムが本当に改善を必要としている箇所がはっきり見えます。

5.6 Information Provenance — 情報の出所（provenance）

Claim-Source Mappings — claim と出典の対応付け

subagent が発見（findings）を出すときは、構造化された provenance を出力すべきです：

{
  "claim": "Revenue increased 15% year-over-year in Q4 2024",
  "evidence": "Q4 earnings report, page 3, paragraph 2",
  "source_url": "https://example.com/earnings/q4-2024",
  "document_name": "Q4 2024 Earnings Report",
  "publication_date": "2025-01-15",
  "source_type": "primary"
}
Handling Conflicting Data — 矛盾するデータの扱い

情報源どうしが一致しないときは、黙って適当な値を選ぶのではなく、その矛盾を注記（annotate the conflict）します：

{
  "field": "Q4 revenue",
  "values": [
    {
      "value": "$2.3B",
      "source": "Company press release (2025-01-15)",
      "note": "Preliminary figures"
    },
    {
      "value": "$2.28B",
      "source": "SEC filing (2025-02-28)",
      "note": "Audited figures"
    }
  ],
  "resolution": "SEC filing is the authoritative source (audited)",
  "conflict_type": "minor_discrepancy"
}

Anti-pattern：情報源間の不一致を注記せずに、黙って1つの値を選ぶこと。潜在的なデータ品質の問題が隠れてしまいます。

Temporal Data — 時点付きのデータ

時間的な混乱（temporal confusion）を避けるため、公開日とデータの収集日を添付しましょう：

{
  "claim": "Unemployment rate is 3.7%",
  "data_as_of": "2024-11-01",
  "source_published": "2024-12-06",
  "retrieved_on": "2025-01-10"
}

日付がないと、読み手は異なる月の2つの失業率の数値を矛盾していると考えてしまうかもしれません — 実際にはどちらもそれぞれの時点では正しいのに。

Synthesis Output Quality — 統合 output の品質

リサーチの統合（research synthesis）を作成するとき：

  1. 確実性のレベル（certainty levels）を区別する：
    • "Well-established（明確に確立されている）: Revenue grew 15% (confirmed by SEC filing and two analyst reports)"
    • "Contested（議論がある）: Market share estimates range from 12% to 18% depending on methodology"
    • "Single-source（単一の情報源のみ）: Only one report mentions the planned acquisition"
  2. 情報源の特徴づけを保つ（preserve source characterization）：
    • 情報源の言っていることをひとまとめにしたり、言い換えたりしない
    • 元の claim に忠実に引用または言い換える
    • 情報源自体が述べている注意事項や条件（caveats/qualifications）を記録する
  3. コンテンツの種類に合った見せ方をする：
    • 財務データ → 出典の attribution 付きの表
    • ニュース/出来事 → 時系列の文章（chronological prose）
    • 技術仕様 → 構造化リスト
    • 議論のある claim → 並べて比較（side-by-side comparison）

5.8 Bounding and Recovering Long Runs — 長時間の実行の制限と復旧

Task Budgets vs max_tokens

max_tokens は model から見えない上限で、これに達すると output が途中で切れます。task budget（output_config.task_budget、beta task-budgets-2026-03-13、最小 20,000）は model に見える上限なので、model は自分でペースを調整し、きれいに作業を完了させます。Claude Opus 5、Fable 5、Sonnet 5、Opus 4.8/4.7 で利用可能。この budget は、現在のターンで Claude が生成するものと読む tool result の両方を数えます — 送り返す履歴全体ではありません。通常のループでは remaining は設定しないままにしておき、履歴を自分で書き換えたり compact したりして、server がそれまでの消費量を推測できなくなった場合にだけ値を渡します。

Managed Agents の session budgets はまったく別の概念です：プラットフォームが session に強制する、金額建て（dollar-denominated）のハードな上限です。一方 task budget はあくまで助言的（advisory）で、token 建てです。

Refusals Are a Reliability Concern, Not Just a Safety One — refusal は安全性だけでなく信頼性の問題

refusal（回答拒否）も HTTP 200 で、stop_reason: "refusal" と stop_details.category を伴って返ってきます。stop_reason を確認せずに content だけを読むコードは、refusal を空だが成功した回答として扱ってしまいます — これは失敗した検索を「結果なし」とみなすのと同じ種類の bug です（§5.3）。本番の経路では server-side fallback（betas=["server-side-fallback-2026-07-01"]、fallbacks="default"）を有効にして、request が放置されるのではなく category に応じて再ルーティング（re-route）されるようにしましょう。Domain 1 §1.1 も参照してください。

🧩 「Building Effective Agents」の6つの定番 pattern

Anthropic の基礎となるブログ記事（2024年12月）— Domain 1 全体のアイデアの源である可能性が高いものです。根本的な区別：Workflow = あらかじめ決められた固定の経路をコードでたどる；Agent = model が環境からのフィードバックに基づいて自分で経路を決める。

Prompt Chaining

タスクを逐次的な LLM ステップに分け、後のステップが前のステップの output を処理する。途中に「チェックゲート」（gate）を置く。レイテンシと引き換えに精度を得る。

Routing

まず input を分類し、専門の prompt/model に route する（例：簡単な質問 → Haiku、難しい質問 → Sonnet/Opus）。

Parallelization

Sectioning — タスクを分割して並列実行。Voting — 同じタスクを複数回実行して多数決/照合をとる。

Orchestrator–Workers

1つの orchestrator が input に応じてタスクを動的に分割し（固定の Prompt Chaining とは違う）、worker に割り当ててから統合する。これが coordinator–subagent pattern の源流。

Evaluator–Optimizer

1つの LLM が output を生成し、別の LLM が採点 + フィードバックし、それを繰り返す — 評価基準が明確で、改善が本当に価値を生むときに向いている。

Autonomous Agents

開かれたループで、agent が自分で計画 + 行動し、tool/コードの結果を「ground truth」として進捗を自己評価し、停止条件に達するまで続ける。

この記事の黄金律：「複雑さを増やすのは、それが本当に結果を改善するときだけ」— そして Agent-Computer Interface (ACI)：tool description はジュニア開発者向けの docstring のように丁寧に書くこと。人間のエンジニアでさえどの tool を使うべきか迷うなら、AI にそれ以上を期待してはいけないからです。

    Claude Agent SDK
    stop_reason

    model は毎ターンの後に "tool_use" または "end_turn" を返す — これが、agentic loop が続けるか止めるかを判断するための唯一信頼できるシグナル。回答のテキストから推測したり、ループ回数を数えたりしないこと。

    Task tool / allowedTools

    coordinator が subagent を spawn する唯一の仕組み。allowedTools に "Task" がないと、coordinator はお手上げで誰も呼べない。

    Hooks (PostToolUse, tool call interception)

    ルールを100%確実に（deterministic）強制する唯一の方法 — データの正規化や、policy 違反の tool call のブロック。prompt で強制できるのは確率的にだけで、絶対ではない。

    Coordinator–subagent (hub-and-spoke)

    coordinator は唯一の中継ハブ — 調整、結果の集約、エラー処理を担う。subagent の context は分離されており、親から何も自動では引き継がない。

    fork_session / --resume

    fork で共通の baseline から並行ブランチを作る；名前付きの resume で以前の session をそのまま続ける。resume したら、どのファイルが変わったかを伝えるのを忘れずに — agent に古い情報を使わせない。

    MCP · Tool Design
    tool の説明 (tool description)

    LLM が tool を選ぶ唯一の拠り所。雑な description = 似た tool 同士で選択を誤る。tool の選択ミスがあるとき、ほぼ常にこれが正しい「最初の一手」。

    isError flag

    tool のエラーを agent に伝える MCP の pattern。category（transient/validation/business/permission）+ retryable フラグを付ける必要がある — 汎用的な「Operation failed」を返しても役に立たない。

    .mcp.json / MCP resources

    project-scope の MCP server 設定で、secret を漏らさないよう ${GITHUB_TOKEN} のような環境変数をサポート。MCP resources はコンテンツのカタログを expose し、手探りの tool call を減らす。

    tool_choice

    "auto"（model はテキストを返すこともある）、"any"（tool の呼び出しは必須、どれを呼ぶかは model が選ぶ）、または特定の1つの tool を強制。structured output を保証したり、extraction の順序を強制したりするのに使う。

    Claude Code Configuration
    CLAUDE.md hierarchy

    3階層：user-level（自分専用、共有されない）、project-level（git で共有、チーム全体に適用）、directory-level。典型的なミス：指示を user-level に置いて、なぜチームメイトに効かないのかと首をかしげる。

    .claude/rules/

    YAML frontmatter の paths（glob pattern）を持つ rule ファイル — 一致するファイルを編集するときだけ読み込まれる。規約が多くの場所にまたがる場合（例：test ファイル）、subdirectory ごとの CLAUDE.md より断然有利。

    .claude/commands/ vs .claude/skills/

    project-scope の command = version control 経由でチーム全体に共有。Skill は context: fork（隔離して実行、メインの context を汚さない）、allowed-tools、argument-hint をサポート。

    Plan mode vs direct execution

    Plan mode は大規模なアーキテクチャのタスクや、妥当なアプローチが複数ある場合に。Direct execution は明確で scope が小さい作業に。Explore subagent は冗長な探索ステップを隔離するのに役立つ。

    /memory / /compact

    /memory はどの memory file が読み込まれているかを確認する（おかしな挙動の debug）。/compact は長い探索 session で context が過負荷になったときに圧縮する。

    CI/CD · Claude Code CLI
    -p / --print

    Claude Code を non-interactive で実行。CI/CD pipeline では必須 — このフラグがないと input 待ちで job が無期限にハングする。

    --output-format json / --json-schema

    CI で機械可読な output を強制し、自由記述のテキストを parse する代わりに、PR へ inline comment を自動投稿できるようにする。

    Structured Output · Batch
    JSON Schema (nullable, enum + other)

    ドキュメントに情報がないときに model が値をでっち上げないよう、optional/nullable のフィールドにする。拡張しうる category には enum + "other" + 詳細 string。

    Message Batches API / custom_id

    50% 安いが処理は最大24時間、レイテンシの SLA なし — すぐに結果を待つ必要のない workflow にだけ向く。custom_id で request/response を対応付ける。

    Validation-retry loop

    具体的な validate エラーを付けて retry すれば model は自己修正できる — ただし、情報が元の資料にそもそも存在しない場合は無意味（format/構造のエラーとは別物）。

    Few-shot prompting

    一貫した output + 曖昧なケースの処理のための最強の武器。model が判断の「センス」を汎化するのを助け、与えたケースに機械的に一致させるだけではない。

    明確な基準 (false positive を減らす)

    具体的な基準は、漠然とした「注意して」に必ず勝る。問題で「false positive を減らす最も効果的な方法」を問われたら、たいていこれが正解。

    Multi-pass review

    大規模な review をファイルごとの local pass + 別の cross-file 統合 pass に分け、注意の希釈や互いに矛盾するフィードバックを防ぐ。

    Context Management · Reliability
    "Lost in the middle"

    model は長い input の最初と最後はうまく処理するが、中間の finding を見落としやすい。重要な要約を冒頭に置き、明確な section header を使ってこの効果を軽減する。

    Escalation の基準

    escalate するのは：顧客が直接求めたとき、policy に抜け穴/例外があるとき、agent がお手上げのとき。sentiment も自己申告の confidence も、ケースの複雑さの信頼できる代理指標ではない。

    Structured error context

    エラーには、エラーの種類 + 試したこと + partial result + 代替案を付ける必要がある。エラーを握りつぶしたり（空を成功とみなす）、1つのエラーだけで workflow 全体を止めたりしないこと。

    Confidence calibration

    全体の accuracy は、特定のフィールド/ドキュメント種別での低い性能を隠すことがある。完全に自動化する前に、セグメントごとに確認する必要がある。

    Claim-source mapping (provenance)

    複数ソースを統合するとき、出典の attribution を一貫して保持する。数値が矛盾する場合は、勝手に1つを選ばず、出典付きで明記する。

    MCP — Tools / Resources / Prompts

    MCP spec の3つの基本 primitive で、「誰が制御するか」で分かれる：Tools = model が自分で呼ぶ、Resources = アプリが取得を決める、Prompts = ユーザーが自分から呼び出したときだけ実行される。

    「Building Effective Agents」の6つの pattern

    Prompt Chaining、Routing、Parallelization、Orchestrator-Workers、Evaluator-Optimizer、Autonomous Agents — Domain 1 全体のアイデアの源である可能性が高い。

    "Context rot" & Case Facts Block

    context が長くなるほど、正確に思い出す能力は徐々に落ちていく — 「最小の token セットで最大のシグナル」という原則。Case Facts Block は、重要な数値を要約される部分から切り出す pattern。

    CLAUDE.md — 連結される、上書きではない

    4階層（managed → user → project → local）はすべて連結（concatenate）され、後の階層が前の階層を上書きするわけではない。system prompt の中ではなく、system prompt の後の user message として送られる。
