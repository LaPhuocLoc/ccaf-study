試験について Exam Guide §1

この認定資格は何のため？

Claude Certified Architect – Foundations（試験コード CCAR-F）は、Claude を使って実際のシステムを作るときに、妥当なトレードオフの判断ができることを証明する資格です — 理論の丸暗記ではありません。試験では、4つの主要な「武器」の基礎知識が問われます：Claude Code、Claude Agent SDK、Claude API、Model Context Protocol (MCP)。

問題は知識をそのまま問うのではなく、現実的な状況をもとに作られています：カスタマーサポート用エージェントの構築、リサーチ用マルチエージェント・パイプラインの構築、Claude Code の CI/CD への組み込み、開発者向け生産性ツールの作成、雑多なドキュメントからの構造化データ抽出など。理論に加えて、アーキテクチャの「センス」、適切な場所での設定、本番運用でのトレードオフの理解も求められます。

想定受験者 Exam Guide §27つのスキル

「標準的な」受験者は、Claude を使った本番アプリケーションを自ら設計・デプロイした経験のあるソリューションアーキテクトで、次のような実務経験を持っています：

  • Claude Agent SDK でエージェント型（agentic）アプリを構築 — マルチエージェントのオーケストレーション、subagent への作業の委任、ツール連携、ライフサイクル hooks
  • チーム全体向けに Claude Code を設定・カスタマイズ — CLAUDE.md、Agent Skills、MCP サーバー、plan mode
  • MCP（Model Context Protocol）に準拠したツールとリソースのインターフェースを設計し、バックエンドのシステムと接続
  • 信頼できる構造化出力（structured output）を得るためのプロンプト設計 — JSON schema、few-shot の例、情報抽出のパターン
  • 長いドキュメント、複数ターンの会話、エージェント間の引き継ぎを通したコンテキストウィンドウ（context window）の管理
  • Claude を CI/CD パイプラインに組み込み、コードレビュー、テスト生成、プルリクエストへのコメントを自動化
  • エスカレーションと信頼性（reliability）に関する適切な判断 — エラー処理、human-in-the-loop（人間による確認）、結果の自己評価

実務経験の目安：Claude API、Agent SDK、Claude Code、MCP を最低6か月使い込んでいること。この経験が足りなくても、理論をしっかり学んで問題演習を重ねれば合格できます — 問題は状況判断型で、コードを書く必要はありません。

Domain 1 · Agentic Architecture & Orchestration

試験で最も比重の大きいパートです（27%）。基本の考え方：エージェントは stop_reason を見て自分で判断する、coordinator は subagent 同士をつなぐ唯一の「中継役」である、そして100%確実でなければならない箇所では、プロンプトに頼らず必ず hook や前提条件のチェック（prerequisite）を使う。

Task Statement 1.1
タスクを自律的に進める agentic loop の設計と実装
📚 押さえるべき知識
  • 基本の agentic loop：Claude にリクエストを送る → stop_reason が "tool_use" か "end_turn" かを確認 → 要求されたツールを実行 → 結果を次のループに渡す
  • ツールの実行結果は会話履歴に追加し、モデルがそれを「見て」次のステップを考えられるようにする
  • 区別すること：次に呼ぶツールをモデル自身が決める方式（model-driven）と、決定木や固定のツール呼び出し順をあらかじめコードで組む方式は、まったくの別物
🛠️ できるべきこと
  • 制御フローを書く："tool_use" の間はループを続け、"end_turn" で止める
  • ループの各回でツールの結果をコンテキストに入れ、モデルが新しい情報をもとに判断できるようにする
  • アンチパターンを避ける：自然言語の応答を解析してループの終了を推測する、固定のループ回数上限を主な停止手段にする、「テキストの回答が含まれている」ことを完了とみなす — どれも誤り
Task Statement 1.2
coordinator–subagent パターンによるマルチエージェントの取りまとめ（orchestration）
📚 押さえるべき知識
  • hub-and-spoke 型のアーキテクチャ：coordinator が中心となり、subagent 間のすべてのやり取り、エラー処理、情報の受け渡しを管理する
  • subagent は独立したコンテキストで動く — coordinator の会話履歴を自動では引き継がない
  • coordinator の役割：タスクの分解、作業の割り当て、結果の集約、そして質問（クエリ）の複雑さに応じてどの subagent を呼ぶかの判断
  • coordinator がタスクを狭く分けすぎるリスク → 調査の観点が抜け落ち、テーマ全体をカバーできない
🛠️ できるべきこと
  • 毎回すべての subagent に順番に通すのではなく、クエリを分析して必要な subagent だけを選ぶ coordinator を設計する
  • subagent ごとの調査範囲が重ならないように分ける（各エージェントが別々のサブトピックや情報源を担当）
  • 改善のループを作る：coordinator が統合（synthesis）結果を見直して不足を洗い出し、より具体的なクエリで検索担当・分析担当に再依頼し、十分になるまで統合をやり直す
  • subagent 間のやり取りはすべて coordinator を経由させる — 追跡しやすく、エラー処理を統一でき、情報の流れを管理できる
Task Statement 1.3
subagent の呼び出し・コンテキストの受け渡し・起動（spawn）の設定
📚 押さえるべき知識
  • Task ツールが subagent を起動（spawn）する仕組み — coordinator の allowedTools に "Task" が含まれていないと subagent を呼べない
  • subagent に必要なコンテキストはプロンプトで直接渡す必要がある — subagent は親のコンテキストを自動では引き継がず、呼び出しをまたいでメモリも共有しない
  • AgentDefinition には、subagent の種類ごとに説明文（description）、システムプロンプト、使えるツールの制限が含まれる
  • fork ベースのセッションを使うと、同じ分析結果（ベースライン）から複数の異なる方向を探れる
🛠️ できるべきこと
  • 前のエージェントの調査結果をすべて、次の subagent のプロンプトに直接入れる（例：Web 検索の結果とドキュメント分析の結果を synthesis エージェントに渡す）
  • コンテキストを渡すときは、構造化された形式で本文とメタデータ（出典 URL、ドキュメント名、ページ番号）を分ける — 出典情報（attribution）を失わないため
  • coordinator の1回の応答の中で複数の Task 呼び出しを出し、subagent を並列に起動する（複数のターンに分けない）
  • coordinator のプロンプトは、機械的な手順の指示ではなく「目標 + 品質の基準」の形で書く — subagent が状況に合わせて柔軟に動けるように
Task Statement 1.4
複数ステップのワークフロー：いつ強制し、いつ人に引き継ぐか
📚 押さえるべき知識
  • ワークフローの順序を守らせる方法として、コードによる強制（hooks、前提条件のゲート）と、プロンプトでの指示だけに頼る方法はまったく別物
  • 100%確実でなければならない処理（例：お金を動かす前の本人確認）では、プロンプトだけでは失敗率がゼロにならない — 頼ってはいけない
  • 途中で人に引き継ぐ（エスカレーションする）ときの引き継ぎ手順（handoff protocol）には、顧客情報、根本原因の分析、推奨する対応が必要
🛠️ できるべきこと
  • コードで前提条件（prerequisite）を設定し、前のステップが終わるまで後続のツールをブロックする（例：get_customer が本人確認済みの ID を返すまで process_refund をブロック）
  • 複数の問題を含む問い合わせは項目ごとに分け、共有のコンテキスト上で並行して調べ、1つのまとまった回答に統合する
  • 人に引き継ぐときは、構造化された引き継ぎサマリー（顧客 ID、根本原因、返金額、推奨する対応）を作る — 担当者は会話ログ（transcript）を読めないため
Task Statement 1.5
Agent SDK の hooks でツール呼び出しを制御し、データを正規化する
📚 押さえるべき知識
  • PostToolUse hook はツールの結果を途中で受け取り（intercept）、モデルが処理する前に変換する
  • 実行される前のツール呼び出しを止める hook で、業務ルールを強制する（例：上限額を超える返金をブロック）
  • hook = 確実に保証される（deterministic）、プロンプト = 確率的 — 確実さが必要な箇所では hook を使う
🛠️ できるべきこと
  • PostToolUse hook を書き、MCP ツールごとにバラバラなデータ形式（Unix タイムスタンプ、ISO 8601、数値のステータスコードなど）を、エージェントが処理する前にそろえる
  • ポリシー違反の操作（例：$500 を超える返金）をブロックし、別のワークフロー（例：人への引き継ぎ）に振り向ける hook を書く
  • 業務ルールを絶対に守らせる必要があるときは、プロンプトではなく hook を選べる
Task Statement 1.6
複雑なワークフローのためのタスク分解（task decomposition）戦略の設計
📚 押さえるべき知識
  • 順番の決まったパイプライン（prompt chaining）を使うべき場面と、途中の結果に応じて柔軟に分解する方法を使うべき場面
  • Prompt chaining：レビューを順番のステップに分ける（例：まず各ファイルを個別に分析し、その後ファイル横断の統合チェックを1回行う）
  • 適応的な調査計画 — 各ステップで分かったことに応じてサブタスクを生み出す — は、答えの決まっていない（open-ended）タスクで特に有効
🛠️ できるべきこと
  • 適切な分解方法を選ぶ：観点は多いが流れが予測できるレビューには prompt chaining、答えの決まっていない調査タスクには柔軟な分解
  • 大規模なコードレビューは、ファイルごとのローカル分析 + ファイル横断の統合チェックに分けて、注意力の「分散」を防ぐ
  • 答えの決まっていないタスク（例：「レガシーなコードベースに十分なテストを追加する」）では、まず全体の構造を把握し、優先度の高い領域を特定し、順序立てた計画を作り、新しい依存関係が見つかったら計画を見直す
Task Statement 1.7
セッションの状態・再開（resume）・分岐（fork）の管理
📚 押さえるべき知識
  • --resume <session-name> で名前付きのセッションを再開し、以前の会話をそのまま続ける
  • fork_session で共通の分析結果から独立したブランチを作り、複数の方向を探る
  • コードを修正した後にセッションを再開するときは、どのファイルが変わったかをエージェントに伝える — 古い情報のまま作業させない
  • 構造化されたサマリー付きで新しいセッションを始めるほうが、古くなった（stale）ツール結果を抱えたまま再開するより確実なことが多い
🛠️ できるべきこと
  • --resume とセッション名を使い、何回かに分けた作業にまたがる調査を続ける
  • fork_session で並行するブランチを作る（例：同じコードベースの分析から、2つのテスト戦略や2つのリファクタリング方針を比べる）
  • 再開（以前のコンテキストがまだ有効なとき）と、サマリー付きの新規開始（以前のツール結果が古くなったとき）を使い分けられる
  • 再開するときは、変更された特定のファイルだけをエージェントに伝えて該当箇所を再分析させる — 最初から探索し直させない

Domain 2 · Tool Design & MCP Integration

要点：ツールの説明文（description）は、LLM が正しいツールを選ぶための拠り所です — 雑な説明文だと選択を誤ります。さらに、エラー応答は構造化する、ツールは役割に応じて割り当てる（1つのエージェントに18個も詰め込まない）、MCP サーバーを正しいスコープで設定する、の3点も重要です。

Task Statement 2.1
明確で境界のはっきりしたツールインターフェースの設計
📚 押さえるべき知識
  • ツールの説明文（description）は、LLM がツールを選ぶ主な手がかり — 雑な説明文だと、似たツールの間で選択がぶれる
  • 良い説明文に必要なもの：入力の形式、クエリの例、例外的なケース（edge case）、使う場面と使わない場面の境界
  • あいまい・重複した説明文は「ツールの取り違え」を招く（例：analyze_content と analyze_document の説明文がほぼ同じ）
  • システムプロンプトの言い回しもツール選択に影響する — ある1つのキーワードが、意図しない誤った連想を生むことがある
🛠️ できるべきこと
  • 目的、期待される入力と出力、似たツールではなくこのツールを使うべき場面を、はっきり書き分けた説明文を書く
  • 名前の変更 + 説明文の書き直しで機能の重複をなくす（例：analyze_content を、Web 専用の説明文を持つ extract_web_results に改名）
  • 汎用ツールを、それぞれ入出力の取り決め（contract）が明確な専用ツールに分ける（例：analyze_document を extract_data_points、summarize_content、verify_claim_against_source に分割）
  • システムプロンプト内のキーワードが、せっかく丁寧に書いたツールの説明文をうっかり「上書き」していないか見直す
Task Statement 2.2
MCP ツールの構造化されたエラー応答の設計
📚 押さえるべき知識
  • ツールのエラーをエージェントに伝える、MCP の isError フラグの仕組み
  • 4種類のエラーを区別する：一時的なエラー（transient：タイムアウト、サービス停止）、入力エラー（validation：不正な入力）、業務エラー（business：ポリシー違反）、権限エラー（permission）
  • 「Operation failed」のような汎用的なエラーを返すと、エージェントはどう対処すべきかわからない
  • 再試行（リトライ）できるエラーとできないエラーは別物 — 構造化されたメタデータを返せば、無駄なリトライを防げる
🛠️ できるべきこと
  • 構造化されたエラーのメタデータを返す：errorCategory（transient/validation/permission）、isRetryable（真偽値）、わかりやすい説明
  • 業務ルール違反によるエラーには、retriable: false フラグと、顧客にもわかる説明を付ける
  • 一時的なエラーは subagent がその場で対処し、自力で解決できないものだけを、途中までの結果（partial result）と試したこと付きで coordinator に上げる
  • 区別する：本当のアクセスエラー（リトライするかの判断が必要）と、正常な空の結果（検索は成功したが該当なし）は別物
Task Statement 2.3
役割に応じたツールの割り当てと tool_choice の設定
📚 押さえるべき知識
  • エージェントにツールを与えすぎる（例：4〜5個ではなく18個）と、選択肢が増えて判断が複雑になり、ツール選択の信頼性が下がる
  • 専門外のツールを持つエージェントは、それを誤用しがち（例：synthesis エージェントが自分で Web 検索してしまう）
  • ツールの利用範囲を絞る（scoped tool access）：エージェントには役割に必要なツールだけを与え、頻繁に必要になるものに限って、役割をまたぐツールを少しだけ追加する
  • tool_choice の設定："auto"、"any"、または特定のツールを強制（{"type": "tool", "name": "..."}）
🛠️ できるべきこと
  • 各 subagent のツールを役割の範囲内に限定し、専門外のツールの誤用を防ぐ
  • 汎用的なツールを、用途を絞ったものに置き換える（例：fetch_url を、ドキュメントの URL を検証する load_document に置き換える）
  • 頻繁に必要になるものには、制限付きで役割をまたぐツールを与え（例：synthesis エージェント用の verify_fact ツール）、複雑なケースは引き続き coordinator 経由で処理する
  • tool_choice で特定のツールを強制して先に実行させ（例：情報を付け足す enrichment 系ツールより先に extract_metadata を強制）、後続のステップは次のターンで処理する
  • tool_choice: "any" を設定して、モデルがテキストだけで答えずに必ずツールを呼ぶようにする
Task Statement 2.4
MCP サーバーを Claude Code とエージェントのワークフローに組み込む
📚 押さえるべき知識
  • MCP サーバーのスコープ：チームで共有するツールはプロジェクト単位（.mcp.json）、個人用・お試し用のサーバーはユーザー単位（~/.claude.json）
  • .mcp.json では環境変数（例：${GITHUB_TOKEN}）を使い、秘密情報を git にコミットせずに認証情報を管理する
  • 設定済みのすべての MCP サーバーのツールは接続時に検出され、エージェントが同時に使える
  • MCP のリソース（resources）はコンテンツの一覧（issue の要約、ドキュメントの構成、データベースのスキーマなど）を公開するための仕組み — エージェントがツール呼び出しで「探し回る」回数を減らせる
🛠️ できるべきこと
  • チームで共有する MCP サーバーは .mcp.json（project スコープ）に設定し、認証トークンには環境変数を使う
  • 個人用・お試し用の MCP サーバーは ~/.claude.json（user スコープ）に設定する
  • MCP ツールの説明文に機能と出力をより詳しく書き、エージェントが高機能な MCP ツールではなく組み込みツール（Grep など）を「手軽さで」選んでしまわないようにする
  • 自作よりも既存のコミュニティ製 MCP サーバー（例：Jira）を優先し、チーム独自のワークフローの場合だけサーバーを自作する
  • コンテンツの一覧を MCP リソースとして公開し、エージェントがツール呼び出しで探さなくても、使えるデータが「見える」ようにする
Task Statement 2.5
組み込みツール（Read、Write、Edit、Bash、Grep、Glob）の使い分け
📚 押さえるべき知識
  • Grep = ファイルの中身を検索（関数名、エラーメッセージ、import 文など）
  • Glob = パスのパターンでファイルを検索（ファイル名、拡張子）
  • Read/Write はファイル全体を読み書きする；Edit は一意なテキストにマッチさせて、狙った箇所だけを修正する
  • マッチするテキストが一意でないために Edit が失敗したときは、Read + Write がより確実な代替手段
🛠️ できるべきこと
  • コードベース全体からコードの中身を探すときは Grep を選ぶ（関数の呼び出し箇所、エラーメッセージの場所など）
  • 名前のパターンでファイルを探すときは Glob を選ぶ（例：**/*.test.tsx）
  • Edit が一意な目印（アンカー）となる文字列を見つけられないときは、Read でファイル全体を読み込んでから Write で書き直す
  • コードベースの理解を少しずつ積み上げる：まず Grep で入口（エントリーポイント）を探し、import をたどりながら Read して処理の流れを追う — 最初から全ファイルを読むのではなく
  • ラッパーモジュールを経由した関数の使用箇所を追う：まず export されている名前をすべて洗い出し、それぞれの名前でコードベース全体を検索する

Domain 3 · Claude Code Configuration & Workflows

要点：CLAUDE.md の階層構造をしっかり理解すること、plan mode と直接実行（direct execution）の使い分けを知ること、そしてパイプラインを入力待ちで止めずに Claude Code を CI/CD に組み込む方法。

Task Statement 3.1
CLAUDE.md を正しい階層・スコープで設定し、適切にファイルを分割する
📚 押さえるべき知識
  • CLAUDE.md の3つの階層：ユーザー単位（~/.claude/CLAUDE.md）、プロジェクト単位（.claude/CLAUDE.md またはルートの CLAUDE.md）、ディレクトリ単位（各サブフォルダ内のファイル）
  • ユーザー単位の設定はその人にだけ適用される — バージョン管理（git）を通じてチームに共有されることはない
  • @import 構文で外部ファイルを参照し、CLAUDE.md をすっきり保つ（例：パッケージごとの規約ファイルを import する）
  • .claude/rules/ ディレクトリは、巨大な1つの CLAUDE.md の代わりになる — トピックごとにファイルを分ける
🛠️ できるべきこと
  • 設定の階層にまつわる問題を突き止める（例：新しいメンバーに指示が効かないのは、その指示がプロジェクト単位ではなくユーザー単位に書かれているから）
  • @import を使い、各パッケージの CLAUDE.md に、関係する規約ファイルだけを取り込む（メンテナーの知見に基づいて選ぶ）
  • 巨大な CLAUDE.md を .claude/rules/ 内のトピック別ファイルに分ける（例：testing.md、api-conventions.md、deployment.md）
  • /memory コマンドで、どのメモリファイルが読み込まれているかを確認する — セッションによって挙動が違うときに役立つ
Task Statement 3.2
カスタムのスラッシュコマンドと skill の作成・設定
📚 押さえるべき知識
  • プロジェクト単位のコマンドは .claude/commands/（バージョン管理で共有）、ユーザー単位のコマンドは ~/.claude/commands/（個人用）
  • skill は .claude/skills/ に置き、SKILL.md の frontmatter（ファイル冒頭の設定欄）で次を指定できる：context: fork、allowed-tools、argument-hint
  • context: fork は skill を独立した subagent で実行し、skill の出力でメインの会話が散らからないようにする
  • skill を個人向けにカスタマイズするときは、~/.claude/skills/ に別名で自分用の版を作り、チームメイトに影響を与えないようにする
🛠️ できるべきこと
  • .claude/commands/ にプロジェクト単位のスラッシュコマンドを作り、バージョン管理を通じてチーム全体で共有する
  • context: fork を使い、出力が長い skill（例：コードベースの分析）や探索的な skill（例：複数案のブレインストーミング）をメインのセッションから切り離す
  • frontmatter の allowed-tools で skill が使えるツールを制限する（例：ファイルの書き込みだけを許可し、破壊的な操作を防ぐ）
  • argument-hint で、引数なしで skill が呼ばれたときに、必要なパラメータの入力を促す
  • skill（必要なときに呼び出す、個別のワークフロー向け）と CLAUDE.md（常に読み込まれる、プロジェクト共通の規約向け）を使い分けられる
Task Statement 3.3
パス指定のルール（path-specific rules）で規約を条件付きで読み込む
📚 押さえるべき知識
  • .claude/rules/ 内のファイルは、YAML frontmatter の paths フィールドに glob パターンを書くことで、ルールを条件付きで有効にできる
  • パス指定のルールは、パターンに一致するファイルを編集しているときだけ読み込まれる — 不要なコンテキストとトークンの消費を減らせる
  • 規約があちこちのファイルに関わる場合（例：テストファイルがコードベース全体に散らばっている）、glob パターンのルールはディレクトリ単位の CLAUDE.md より有利
🛠️ できるべきこと
  • .claude/rules/ に、パスで対象を絞る YAML frontmatter 付きのファイルを作る（例：paths: ["terraform/**/*"]）— 該当するファイルを編集するときだけ読み込まれる
  • ルールに glob パターンを使い、置き場所に関係なく、ファイルの種類ごとに規約を適用する（例：すべてのテストファイルに **/*.test.tsx）
  • コードベース全体に散らばったファイルに規約を適用したいときは、サブディレクトリの CLAUDE.md ではなく、パス指定のルールを選ぶ
Task Statement 3.4
plan mode と直接実行（direct execution）の使い分け
📚 押さえるべき知識
  • plan mode は複雑なタスク向け：大規模な変更、妥当なアプローチが複数ある、アーキテクチャの判断が必要、多数のファイルを修正する
  • 直接実行は、シンプルで範囲が明確な作業向け（例：1つの関数に入力チェックを1つ追加する）
  • plan mode なら、実際に変更を加える前にコードベースを安全に調べて設計できる — 手戻りを防げる
  • Explore subagent は長くなりがちな探索の出力を切り離し、要約だけを返して、メインの会話のコンテキストを守る
🛠️ できるべきこと
  • アーキテクチャに影響するタスクには plan mode を選ぶ（例：マイクロサービスの再構成、45以上のファイルに影響するライブラリの移行、必要なインフラが異なる連携方式の選択）
  • 明確で範囲がはっきりしている変更には直接実行を選ぶ（例：スタックトレースから原因が明らかな1ファイルのバグ修正、日付の入力チェックの追加）
  • 長い探索のフェーズには Explore subagent を使い、複数フェーズのタスクの途中でコンテキストウィンドウを「使い切って」しまうのを防ぐ
  • 組み合わせる：plan mode で調査し、立てた計画に沿って直接実行で実装する（例：ライブラリの移行を計画してから実行する）
Task Statement 3.5
反復的な改善（iterative refinement）で少しずつ良くしていく
📚 押さえるべき知識
  • 言葉での説明が人によって違う意味に取られるとき、具体的な入力/出力の例は、期待する変換を伝える最も効果的な方法
  • テスト駆動の反復（test-driven iteration）：先にテストを書き、テストの失敗結果を Claude に見せながら少しずつ改善する
  • インタビュー形式（interview pattern）：実装に取りかかる前に、こちらが見落としているかもしれない点を Claude に質問してもらう
  • 複数の問題を1つのメッセージにまとめるべき場合（互いに関連するエラー）と、1つずつ順に直すべき場合（独立したエラー）
🛠️ できるべきこと
  • 言葉での説明では結果が安定しないとき、2〜3個の具体的な入力/出力の例で、変換の要件をはっきりさせる
  • コードを書く前に、期待する動作、例外的なケース（edge case）、性能の要件をカバーするテストを書き、テストの失敗をもとに改善を繰り返す
  • 慣れない分野でコードを書く前に、interview pattern で設計上の検討事項（例：キャッシュを無効化する方針、起こりうるエラーの種類）を洗い出す
  • 例外的なケースを直すために、期待する入力/出力付きの具体的なテストケースを渡す（例：データ移行スクリプトでの null 値）
  • 互いに影響し合う複数の問題は1つの詳しいメッセージにまとめ、独立した問題は1つずつ順に直す
Task Statement 3.6
Claude Code を CI/CD パイプラインに組み込む
📚 押さえるべき知識
  • -p（または --print）フラグで、自動化パイプラインの中で Claude Code を非対話モード（non-interactive）で実行する
  • --output-format json と --json-schema フラグで、CI で実行するときに構造化された出力を強制する
  • CLAUDE.md は、CI から呼ばれた Claude Code にプロジェクトの前提知識（テストの規約、fixture、レビューの基準）を渡す手段
  • セッションの分離：コードを生成した Claude のセッション自身にレビューさせるより、独立した別のインスタンスにレビューさせるほうが効果が高い
🛠️ できるべきこと
  • CI では -p フラグ付きで Claude Code を実行し、対話入力の待ちでパイプラインが止まる（ハングする）のを防ぐ
  • --output-format json と --json-schema で機械が読める形式の指摘を出力し、PR のインラインコメントとして自動で投稿する
  • 新しいコミットの後にレビューを再実行するときは、前回のレビューの指摘をコンテキストに入れ、新しい問題や未対応の問題だけを報告するよう指示する — 同じコメントの重複を防ぐ
  • 既存のテストファイルをコンテキストに入れ、テスト生成で既存のテストと同じシナリオを提案させないようにする
  • テストの規約、価値のあるテストの基準、利用できる fixture を CLAUDE.md に明記し、生成されるテストの質を上げて、意味の薄いテストを減らす

Domain 4 · Prompt Engineering & Structured Output

要点：基準が具体的なほど誤検知（false positive）は減る（「注意して」と言うだけでは効果がない）、few-shot は出力を安定させる最強の武器、そして tool_use + JSON schema が構造化出力（structured output）を強制する最も確実な方法。

Task Statement 4.1
明確な基準を持つプロンプトを設計し、精度を上げて誤検知（false positive）を減らす
📚 押さえるべき知識
  • 具体的な基準は、あいまいな指示に必ず勝る（例：「コメントが説明する動作が実際のコードと矛盾する場合だけ指摘する」は、「コメントが正しいかチェックして」よりはるかに良い）
  • 「注意して」「確信度の高い指摘だけ報告して」のような漠然とした指示は、具体的な分類基準に比べて精度の改善につながらない
  • 誤検知の多さは開発者の信頼を左右する：誤報の多いカテゴリが1つあるだけで、正しく機能している他のカテゴリまで信頼されなくなる
🛠️ できるべきこと
  • 具体的なレビュー基準を書く：報告すべきもの（バグ、セキュリティ）と無視してよいもの（細かなスタイル、そのプロジェクト特有の書き方）を分ける — 「確信度」でふるい分けるのではなく
  • 誤報の多いカテゴリは一時的に無効にして開発者の信頼を取り戻し、その間にそのカテゴリのプロンプトを調整する
  • 重大度（severity）の基準を、レベルごとの具体的なコード例とともに明確に定義し、分類がぶれないようにする
Task Statement 4.2
few-shot prompting で出力の一貫性と品質を上げる
📚 押さえるべき知識
  • 文章での詳しい指示だけでは結果が安定しないとき、few-shot の例（入出力の見本）は、正しい形式・正しい振る舞いの出力を得る最も効果的な手法
  • few-shot は、判断の分かれるケースの扱い方を示すのに使う（例：あいまいな依頼に対するツールの選び方、分岐（branch）単位で見たテストカバレッジの抜け）
  • few-shot は、モデルが判断の「センス」を新しいケースに応用するのを助ける — 見本のケースに機械的に当てはめるだけではない
  • few-shot は、情報抽出タスクでのハルシネーション（事実と異なる出力）を減らすのにも効果的（例：くだけた単位の表記、多様なドキュメント構成）
🛠️ できるべきこと
  • 判断の分かれるケースを狙った 2〜4個の few-shot の例を作り、他の妥当な選択肢ではなくその対応を選ぶ理由も添える
  • 期待する出力形式（場所、問題点、重大度、修正案）を正しく示す例を入れ、出力の一貫性を確保する
  • 許容できるコードのパターンと本物の問題を見分ける例を入れ、応用力を保ちながら誤検知を減らす
  • さまざまなドキュメント構成（本文中の引用 vs 参考文献リスト、調査手法（methodology）のセクション vs 本文に埋め込まれた詳細）の正しい扱い方を示す例を使う
  • 形式の異なるドキュメントから正しく抽出する例を追加し、必須フィールドが空（null）のまま抽出される問題に対処する
Task Statement 4.3
tool use と JSON schema で構造化出力を強制する
📚 押さえるべき知識
  • JSON schema 付きの tool_use は、スキーマに沿った出力を得る最も確実な方法で、JSON の構文エラーを完全になくせる
  • tool_choice の違い："auto"（モデルはツールを呼ばずにテキストで答えることもある）、"any"（ツールの呼び出しは必須だが、どのツールかはモデルが選ぶ）、特定ツールの強制
  • 厳格な（strict）JSON schema で防げるのは構文エラーだけで、意味の誤りは防げない（例：明細の合計が総額と合わない、値が別のフィールドに入っている）
  • スキーマの設計：必須フィールドと任意（optional）フィールドの区別、今後増えうるカテゴリには enum + "other" + 詳細を書く文字列フィールド
🛠️ できるべきこと
  • JSON schema を入力パラメータとする抽出用ツールを定義し、tool_use の応答から構造化データを取り出す
  • 抽出スキーマが複数あり、ドキュメントの種類が事前にわからないときは、tool_choice: "any" を設定して必ず構造化出力を得る
  • tool_choice: {"type": "tool", "name": "extract_metadata"} で特定のツールを強制し、情報を付け足す（enrichment）ステップより先に抽出のステップが実行されるようにする
  • 元のドキュメントにその情報がない可能性があるときは、スキーマのフィールドを optional/nullable にする — 必須フィールドを埋めるためにモデルが値を「作り上げる」のを防ぐ
  • 判断がつかないケース用に "unclear" のような選択肢を enum に加え、今後増えうるカテゴリには "other" + 詳細フィールドを使う
  • 厳格な出力スキーマと合わせて、形式をそろえるルールをプロンプトに書き、元データの形式のばらつきに対処する
Task Statement 4.4
検証・リトライ・フィードバックの仕組みで抽出の品質を上げる
📚 押さえるべき知識
  • エラー内容を伝えるリトライ：リトライするときに具体的な検証エラーをプロンプトに入れ、モデルが正しい方向に自己修正できるようにする
  • 必要な情報が元のドキュメントにそもそも存在しない場合、リトライしても意味がない（形式や構造のエラーとは別物）
  • フィードバックの仕組み：どんなコードの書き方が指摘を引き起こしやすいか（detected_pattern フィールド）を記録し、却下（dismiss）されやすいパターンを体系的に分析する
  • 意味の誤りによる検証エラー（数値の合計が合わない、値のフィールド違い）と、スキーマの構文エラー（tool use で解消済み）を区別する
🛠️ できるべきこと
  • 元のドキュメント、失敗した抽出結果、具体的な検証エラーを添えて追加のリクエストを送り、モデルに自己修正させる
  • リトライしても無駄な場合（例：提供されていない別の資料にしか情報がない）と、リトライで直る場合（形式のエラー、出力構造のエラー）を見分ける
  • 構造化した指摘に detected_pattern フィールドを加え、開発者が指摘を却下したときに、誤検知のパターンを分析できるようにする
  • 自己修正の流れを設計する：calculated_total（計算した合計）と stated_total（記載された合計）の両方を抽出して数値のズレを見つけ、元データが矛盾しているときは真偽値の conflict_detected を立てる
Task Statement 4.5
効率的なバッチ処理（batch processing）戦略の設計
📚 押さえるべき知識
  • Message Batches API：コストは 50%削減、処理は最大24時間以内、応答時間（レイテンシ）の保証（SLA）はなし
  • バッチは、すぐに結果が要らず待ち時間を許容できるワークフロー向き（夜間のレポート、週次の監査、夜間のテスト生成）— 結果を待たないと先に進めない処理（マージ前のチェック）には向かない
  • Batch API は、1つのリクエストの中での複数ターンのツール呼び出しをサポートしない（途中でツールを実行して結果を返すことはできない）
  • custom_id フィールドで、バッチ内のリクエストとレスポンスを対応付ける
🛠️ できるべきこと
  • ワークフローが求める応答時間に合わせて API を選ぶ：マージをブロックするチェックには同期 API、夜間や週次の分析には Batch API
  • SLA の制約からバッチの送信間隔を計算する（例：処理に最大24時間かかるバッチで 30時間の SLA を守るには、4時間ごとに送信する）
  • バッチの失敗への対処：失敗したドキュメントだけを（custom_id で特定して）必要な修正を加えて再送する（例：コンテキストの上限を超えるドキュメントを分割する）
  • 大量のバッチを流す前に、小さなサンプルでプロンプトを調整し、1回目の成功率を上げて再送のコストを減らす
Task Statement 4.6
複数インスタンス・複数パスのレビュー構成の設計
📚 押さえるべき知識
  • 自己レビューの限界：モデルは生成したときの「考えの流れ」をそのまま持っているので、同じセッションの中では自分の判断を疑いにくい
  • 独立したレビュー用インスタンス（以前の推論を持ち込まない）は、「もう一度自分でレビューして」と指示したり extended thinking を使ったりするよりも、細かな問題をよく見つける
  • Multi-pass review：大規模なレビューを、ファイルごとのローカル分析 + ファイル横断の統合チェックに分け、注意力の分散や互いに矛盾する指摘を防ぐ
🛠️ できるべきこと
  • 生成したばかりのコードのレビューには、生成側の考えの流れを持ち込まない、独立した2つ目の Claude インスタンスを使う
  • 多数のファイルにまたがる大規模レビューを、ファイルごとのパス（そのファイル内の問題）+ 別の統合パス（ファイル間のデータの流れの分析）に分ける
  • モデルが各指摘に確信度を付ける確認用のパスを実行し、確信度に応じてレビューの振り分けを変える

Domain 5 · Context Management & Reliability

要点：要約の過程で重要な数値を失わないこと、「lost in the middle」効果を理解すること、人に引き継ぐ（エスカレーションする）べきタイミングを知ること、そして複数の情報源を統合するときに情報の出所（provenance）を保つこと。

Task Statement 5.1
長いやり取りでも重要な情報を失わないための会話コンテキストの管理
📚 押さえるべき知識
  • 段階的な要約（progressive summarization）のリスク：数値、パーセンテージ、日付、顧客の要望が、あいまいな要約に丸められてしまう
  • 「lost in the middle」効果 — モデルは長い入力の最初と最後の情報はうまく扱えるが、中ほどにある情報を見落としやすい
  • ツールの結果はコンテキストにたまり続け、必要以上にトークンを消費する（例：必要なのは5項目なのに、注文を調べるたびに40以上のフィールドが返ってくる）
  • 会話の流れを保つには、次の API リクエストでも会話履歴全体を送る必要がある
🛠️ できるべきこと
  • 取引に関する事実（金額、日付、注文番号、ステータス）を固定の「case facts」ブロックに書き出し、要約される履歴とは別にして、毎回のプロンプトに入れる
  • 複数の問題を扱うセッションでは、問題ごとの構造化データ（注文 ID、金額、ステータス）を抽出して、別のコンテキスト層に保存する
  • 冗長なツールの出力は、コンテキストにたまる前に必要なフィールドだけに絞る（例：注文検索の結果から、返品に関係するフィールドだけを残す）
  • 統合用の入力の冒頭に重要な発見の要約を置き、詳細な結果ははっきりした見出しで整理して、位置による見落としを減らす
  • subagent の構造化出力には必ずメタデータ（日付、出典、調査方法の前提）を含めさせ、後続の工程での正確な統合を支える
  • 後続のエージェントが使えるコンテキストに限りがあるときは、前段のエージェントを修正し、長い文章や推論の過程ではなく構造化データ（主な事実、引用、関連ポイント）を返させる
Task Statement 5.2
効果的なエスカレーション（人への引き継ぎ）と、あいまいさへの対処の設計
📚 押さえるべき知識
  • エスカレーションすべき妥当なきっかけ：顧客が人の対応を求めている、ポリシーに例外や想定外の穴がある（ケースが複雑というだけではない）、エージェントが行き詰まって前に進めない
  • 区別する：顧客がはっきり求めたらすぐにエスカレーション vs 問題がシンプルでエージェントの対応範囲内なら、まず自分での解決を提案する
  • 感情（sentiment）の強さや、エージェントが自己申告する確信度に基づくエスカレーションは、ケースの本当の複雑さを測る指標として信頼できない
  • 複数の結果が同時に当てはまったら、経験則（heuristic）で勝手に選ばず、本人を特定する情報を追加で尋ねる
🛠️ できるべきこと
  • 明確なエスカレーション基準を few-shot の例とともにシステムプロンプトに追加し、エスカレーションすべき場合と自分で対応すべき場合を示す
  • 顧客から「人と話したい」と求められたら、先に調査したりせず、すぐに応じる
  • 顧客の不満は受け止めつつ、対応できる問題なら解決を提案し、顧客が重ねて求めた場合にだけエスカレーションする
  • 顧客の具体的な要望についてポリシーがあいまい、または何も定めていないときはエスカレーションする（例：ポリシーは自社内の価格調整にしか触れていないのに、競合他社との価格合わせ（price matching）を求められた）
  • ツールが複数の一致結果を返したら、経験則で選ばずに、本人を特定する情報を追加で尋ねるようエージェントに指示する
Task Statement 5.3
マルチエージェントシステムでのエラーの伝え方（error propagation）の実装
📚 押さえるべき知識
  • 構造化されたエラー情報（エラーの種類、試したクエリ、途中までの結果、代わりの手段）があれば、coordinator は賢く復旧の判断ができる
  • 区別する：アクセスエラー（タイムアウトなど、リトライするかの判断が必要）と、正常な空の結果（検索は成功したが該当なし）は別物
  • 汎用的なエラーステータス（「search unavailable」など）は、coordinator が必要とする大事な情報を隠してしまう
  • どちらもアンチパターン：エラーを黙って握りつぶす（空の結果を成功として返す）ことと、1つのエラーだけでワークフロー全体を止めること
🛠️ できるべきこと
  • エラーの種類、試したこと、途中までの結果、考えられる代替手段を含む構造化されたエラー情報を返す — coordinator が賢く復旧できるように
  • エラー報告では、アクセスエラーと正常な空の結果をはっきり区別し、coordinator が正しく判断できるようにする
  • 一時的なエラーは subagent がその場で復旧し、自力で解決できないものだけを、試したことと途中までの結果を添えて上に報告する
  • 統合結果にカバー範囲の注記を付け、しっかり裏付けのある発見と、情報源にアクセスできずに抜けている領域を明示する
Task Statement 5.4
大規模なコードベースを探索するときの効率的なコンテキスト管理
📚 押さえるべき知識
  • 長いセッションでのコンテキストの劣化：モデルの回答がぶれ始め、以前に見つけた具体的なクラス名ではなく、「よくあるパターン」のような一般論を言い始める
  • コンテキストの区切りを越えて重要な発見を残しておく、スクラッチパッド（scratchpad）ファイルの役割
  • subagent への委任で長い探索の出力を切り離し、メインのエージェントは全体を見渡した調整に専念する
  • クラッシュからの復旧のための構造化された状態の保存：各エージェントが状態を決まった場所に書き出し、coordinator は再開時にマニフェスト（一覧ファイル）を読み込む
🛠️ できるべきこと
  • 具体的な問い（例：「テストファイルをすべて探す」「返金フローの依存関係を追う」）を調べる subagent を起動し、メインのエージェントは全体の調整役を担う
  • エージェントに重要な発見を記録するスクラッチパッドファイルを維持させ、後の質問でそれを参照させて、コンテキストの劣化を防ぐ
  • 次のフェーズの subagent を起動する前に、探索フェーズの主な発見を要約し、その要約を最初のコンテキストに入れる
  • 構造化された状態（マニフェスト）の書き出しによるクラッシュ復旧を設計し、coordinator が再開時にそれを読み込んでエージェントのプロンプトに入れる
  • 長い探索の出力でコンテキストがいっぱいになった長時間のセッションでは、/compact でコンテキストを圧縮する
Task Statement 5.5
人によるレビューの流れと、確信度の較正（confidence calibration）の設計
📚 押さえるべき知識
  • 全体の正答率（例：全体で97%）は、特定のドキュメントの種類やフィールドでの低い性能を隠してしまうことがある
  • 層化ランダムサンプリング（stratified random sampling）で、確信度の高い抽出結果のエラー率を測り、新しいエラーのパターンを見つける
  • フィールドごとの確信度スコアを、正解ラベル付きの検証用データで較正し、人のレビューが必要な箇所の振り分けに使う
  • 「確信度が高い」抽出を完全に自動化する前に、ドキュメントの種類別・フィールド別の正答率を確認する必要がある
🛠️ できるべきこと
  • 確信度の高い抽出結果に層化ランダムサンプリングを導入し、エラー率を継続的に測って新しいエラーのパターンを見つける
  • 人のレビューを減らす前に、ドキュメントの種類別・フィールド別に正答率を分析し、すべての区分で性能が安定していることを確かめる
  • モデルにフィールドごとの確信度スコアを出力させ、正解ラベル付きの検証用データでレビューの閾値を較正する
  • 確信度の低い抽出結果や、元のドキュメントがあいまい・矛盾している抽出結果を人のレビューに回し、限られたレビュー担当者の時間を優先的に使う
Task Statement 5.6
情報の出所（provenance）の保持と、複数の情報源を統合するときの不確かさへの対処
📚 押さえるべき知識
  • 主張（claim）と出典の対応を残さずに調査結果を要約すると、出典情報（attribution）が失われやすい
  • 主張と出典の構造化された対応表はとても重要 — synthesis エージェントは、結果を統合するときにそれを保持し、正しくまとめなければならない
  • 信頼できる情報源どうしで数値が食い違うときの扱い：勝手に1つの値を選ばず、食い違いがあることを出典付きで明記する
  • 時点のあるデータ：構造化出力に公開日や収集日を必ず含め、時期の違いを矛盾と取り違えないようにする
🛠️ できるべきこと
  • subagent に主張と出典の構造化された対応表（URL、ドキュメント名、関連する抜粋）を出力させ、後続のエージェントには統合の過程でそれをそのまま保持させる
  • しっかり裏付けのある発見と議論の余地がある発見をセクションで分けたレポート構成にし、出典の説明や調査方法の前提もそのまま残す
  • 食い違う値を明記した状態でドキュメント分析を完了させ、統合に入る前に、どう扱うかを coordinator に判断させる
  • subagent の構造化出力に公開日やデータの収集日を含めさせ、時間の流れに沿って正しく解釈できるようにする
  • 統合結果では、内容の種類に合った形で表示する — 財務データは表、ニュースは文章、技術的な発見は構造化されたリスト — すべてを1つの形式に押し込めない
📖このドメインは2つの層に分かれています：「補強」（Exam Guide の内容を詳しくしたもの — 安心して学べる）と「🔭 範囲外」（より新しい機能 — 視野を広げるために知っておくとよいが、暗記は不要）。

値意味対応
"tool_use"Claude がツールを呼び出したいツールを実行し、結果を返してループを続ける
"end_turn"Claude が回答を終えた最終的な回答（テキスト）をユーザーに示す
"stop_sequence"出力が stop_sequences に設定した文字列に一致したループ終了；どの文字列に一致したかを確認する
"pause_turn"サーバー側で動くツール（例：web_search）のループが、内部の繰り返し回数の上限に達した応答をそのまま送り返して続行する
"max_tokens"応答が max_tokens の上限に達した続きを得るために、もう一度リクエストが必要な場合がある
"refusal"Claude が安全上の理由で回答を拒否したループ終了；stop_details（下記参照）を確認し、言い換えるか、リクエストを別の経路に回す
"model_context_window_exceeded"max_tokens に達する前に、モデルのコンテキストウィンドウの上限に達した応答は有効だが途中で切れている；入力を減らすか、続きを生成する。Sonnet 4.5 以降ではデフォルトの挙動
💡 refusal のときの stop_details（Opus 4.7 以降）

refusal の応答には stop_details オブジェクトも付いてきます（beta ヘッダーは不要）。stop_details.type は常に "refusal"、stop_details.category は違反したポリシーの分類（例："cyber"、"bio"、"reasoning_extraction"、"frontier_llm"、または null — この分類は時間とともに増えてきました）、stop_details.explanation は人が読むための説明文です（プログラムで解析しようとしないこと）。他のすべての停止理由では、stop_details は null になります。この分類を使って、拒否の種類ごとに処理の振り分けやログの記録を変えましょう。

Server-Side Refusal Fallbacks — 拒否されたときのサーバー側の代替処理（fallback）

refusal は例外（exception）ではなく、HTTP 200 で返ってきます — stop_reason を先に確認せずに content だけを読むコードは、空、または一部だけの応答を、気づかずにそのまま処理してしまいます。Claude Opus 5 や Claude Fable 5 で動く本番のエージェントでは、拒否をログに残すだけで終わらせず、サーバー側の fallback を有効にして、拒否の分類に応じてリクエストが自動で別の経路に回されるようにしましょう。

response = client.messages.create(
    model="claude-opus-5",
    max_tokens=16000,
    betas=["server-side-fallback-2026-07-01"],
    fallbacks="default",          # server routes by refusal category
    messages=[...],
)

fallbacks="default" なら、切り替え先のモデルの一覧を自分で管理する必要はありません。以前の配列形式（betas=["server-side-fallback-2026-06-01"] + fallbacks=[{"model": "claude-opus-4-8"}]）も引き続き動作します。サーバー側の fallback は Claude API でのみ使えます — Bedrock、Vertex、Foundry では、代わりに SDK のクライアント側の BetaRefusalFallbackMiddleware を使います。

ループのルール：content を読む前に、必ず stop_reason を確認すること。refusal はそのリクエストに対する最終的な停止理由であり、リトライで直るツールのエラーではありません。

API Response Structure — API の応答の構造

Claude がツールを使いたいとき、応答にはテキストと tool_use ブロックの両方が含まれます：

{
  "id": "msg_01Aq9w938a90dw8q",
  "model": "claude-opus-5",
  "stop_reason": "tool_use",
  "role": "assistant",
  "content": [
    {
      "type": "text",
      "text": "I'll check the current weather in San Francisco for you."
    },
    {
      "type": "tool_use",
      "id": "toolu_01A09q90qw90lq917835lq9",
      "name": "get_weather",
      "input": { "location": "San Francisco, CA", "unit": "celsius" }
    }
  ]
}

content 配列には複数のブロックが入ります — Claude は1つの応答の中で、何をしようとしているかの説明（text）とツールの呼び出し（tool_use）を同時に行えます。tool_use ブロックを複数入れて、複数のツールを一度に呼ぶこともできます。

Returning Tool Results — ツールの結果を返す

ツールの結果には、Claude のリクエストにあった tool_use_id を正しく指定する必要があります：

{
  "role": "user",
  "content": [
    {
      "type": "tool_result",
      "tool_use_id": "toolu_01A09q90qw90lq917835lq9",
      "content": "15 degrees celsius, partly cloudy"
    }
  ]
}

複数のツールを同時に呼んだ場合は、1つのメッセージの中に複数の tool_result ブロックを入れて返し、それぞれを対応する tool_use_id に合わせます。

Error Results — エラーのときの結果

ツールの実行でエラーが起きたとき：

{
  "type": "tool_result",
  "tool_use_id": "toolu_01A09q90qw90lq917835lq9",
  "is_error": true,
  "content": "API timeout after 30 seconds"
}

is_error: true を付けると、Claude はツールが失敗したことを理解し、どう立て直すかを考えられます。

Model-Driven Decision Making — モデル主導の意思決定

試験で問われるのは、これを理解しているかどうかです：どのツールを呼び、いつ止めるかを決めるのは Claude 自身です。決定木や固定のツール呼び出し順を事前に組むのではありません。モデルが自分で必要な情報を考え、適切なツールを選び、結果を処理して、次のステップを決めます。

これは、手順があらかじめ決められている従来のワークフロー自動化とは根本的に違います。

Anti-Patterns — アンチパターン（試験では誤答）
  1. 自然言語の応答を解析してループを止めるタイミングを決める — 「Claude が『終わりました』と言ったらループを抜ける」のようなやり方。誤り。必ず stop_reason を確認すること。
  2. 任意のループ回数上限を主な停止手段にする — 「最大5回で止める」のようなやり方。主な手段として使うなら誤り。安全のための上限を設けるのは構わないが、ループを制御するのはあくまで stop_reason。
  3. 応答にテキストがあるかどうかで完了とみなす — 「応答にテキストがあれば完了」のようなやり方。誤り。応答にはテキストと tool_use ブロックが同時に含まれることがある。
🔭 公式 Exam Guide の範囲外 — task budget（beta）

「ループ回数の上限に頼らずに agentic loop の長さを制限するには？」という問いへの、今の答えが task budget です。output_config.task_budget は、Claude 自身に見えるトークンの上限を与えるので、Claude は自分でペース配分をし、途中で打ち切られることなく「きれいに」作業を終えられます。これは、モデルからはまったく見えない、応答ごとの上限である max_tokens とは別物です。

with client.beta.messages.stream(
    model="claude-opus-5", max_tokens=128000,
    betas=["task-budgets-2026-03-13"],
    output_config={"effort": "high",
                   "task_budget": {"type": "tokens", "total": 64000}},
    messages=[...], tools=[...],
) as stream:
    response = stream.get_final_message()

total の最小値は 20,000。Claude Opus 5、Fable 5、Sonnet 5、Opus 4.8/4.7 で使えます。ストリーミングで受け取るのを忘れずに — ストリーミングしないリクエストで大きな max_tokens を指定すると、HTTP のタイムアウトになりやすくなります。試験のアンチパターンはここでも同じです：budget はループのペースを保つための仕組みにすぎず、ループを終わらせるのはあくまで stop_reason です。

Who Runs the Loop: Four Ways to Build an Agent — 誰がループを回すのか：エージェントを作る4つの方法

選択肢を見分けるには、互いに独立した2つの問いを考えます：誰が harness（ループ + コンテキスト管理の仕組み）を提供するかと、誰が実行環境（どこで動かすか）を提供するかです。Tool Runner と Claude Agent SDK は、どちらも harness だけを提供するのでとても混同しやすい — どちらも実行環境は自分で用意する必要があります。

アプローチ自分で書くものHarness と実行環境使えるツール
Manual loop (client.messages.create)while stop_reason == "tool_use" のループharness は自作；実行環境も自前自分で定義したツールのみ
Tool Runner (client.beta.messages.tool_runner)ツールの関数だけSDK がループを提供；実行環境は自前自分で定義したツールのみ
Managed Agents (beta, /v1/agents + /v1/sessions)エージェントの設定 + 自分のツールの結果Anthropic がループを提供し、さらにセッションごとに専用のサンドボックスを用意ホスト型の bash / ファイル / コード実行、加えて Skills、MCP、自分のツール
Claude Agent SDK (claude-agent-sdk)プロンプト + オプションClaude Code の harness + 組み込みツール；実行環境は自前Read/Write/Edit/Bash/Glob/Grep/WebSearch/WebFetch + MCP + subagents

Tool Runner ≠ Claude Agent SDK。Tool Runner は通常の Anthropic SDK（anthropic / @anthropic-ai/sdk）に含まれていて、自分で定義したツールでループを回すだけです — 組み込みツールも、ファイルシステムも、サンドボックスもありません。ターンごとの hook が用意されているので、承認のゲート、エラーの捕捉、結果の加工（例：cache_control の付与）、リトライを実装できます。一方、Claude Agent SDK は Claude Code そのものをライブラリとして使えるようにしたものです。

Managed Agents（beta）は最も新しい提供形態で、管理された実行環境まで提供する唯一の選択肢です。必ず Agent（一度作成し、バージョン管理されて保存される）→ Session（実行ごとに1つ）という流れになります。model、system、tools は Agent 側で設定し、Session 側で設定することはありません。各 Session はそのエージェントの作業場所となるコンテナを作り、イベントをストリーミングで返します；こちらからはメッセージとツールの結果を送ります。ほかにも、スケジュール実行（cron で起動するセッション）、vault に保存されて外部への送信時に差し込まれる認証情報、ドル建てのセッション予算、複数エージェントの編成（multiagent roster）に対応しています。beta ヘッダー：managed-agents-2026-04-01。Bedrock / Vertex / Foundry では使えません — それらの環境では、通常の Claude API + tool use を使います。

どれを選ぶか：要件を満たせる範囲で、いちばんシンプルなものにしましょう。単発の呼び出しや、コードで流れを制御するワークフローで、大半のタスクは処理できます。エージェントを使うのは、タスクが本当に open-ended でモデル自身の判断が必要なとき、得られる価値が待ち時間とコストに見合うとき、そして誤りを検出できる（テスト、レビュー、ロールバック）ときに限りましょう。

1.2 Multi-Agent Orchestration — 複数のエージェントを取りまとめる
Hub-and-Spoke Architecture — ハブ＆スポーク型のアーキテクチャ

マルチエージェントシステムの定番パターンは hub-and-spoke です：1つの取りまとめ役のエージェント（coordinator）が、複数の専門の subagent を管理します。

                    ┌──────────────┐
                    │  Coordinator │
                    │    Agent     │
                    └──────┬───────┘
                           │
            ┌──────────────┼──────────────┐
            ↓              ↓              ↓
     ┌──────────┐   ┌──────────┐   ┌──────────┐
     │ Subagent │   │ Subagent │   │ Subagent │
     │  Search  │   │ Analysis │   │ Synthesis│
     └──────────┘   └──────────┘   └──────────┘
Coordinator Responsibilities — coordinator の役割

coordinator の仕事：

  • Decompose（分解） — タスクをサブタスクに分ける
  • Delegate（委任） — 適切な subagent に仕事を割り振る
  • Route（中継） — subagent 間のやり取りをすべて中継する（subagent 同士が直接やり取りすることはない）
  • Aggregate（集約） — subagent の結果をまとめる
  • Handle errors（エラー処理） — subagent が失敗したときに対処する
  • Evaluate（評価） — 統合結果の質を評価し、不足があれば仕事を割り振り直す
Subagent Isolation — subagent の隔離

重要な概念：subagent のコンテキストは完全に切り離されています。coordinator の会話履歴は引き継がれません。subagent が必要とする情報は、すべてそのプロンプトで明示的に渡す必要があります。

つまり：

  • coordinator は、関係するコンテキストをすべて subagent への作業指示に含めなければならない
  • subagent は、メインの会話のそれまでのやり取りを参照できない
  • 各 subagent はまっさらな状態で起動し、coordinator が渡したものしか持っていない
Dynamic Subagent Selection — subagent を状況に応じて選ぶ

すべての問い合わせに、すべての subagent が必要なわけではありません。coordinator は：

  • その問い合わせに本当に何が必要かを見極める
  • 関係する subagent だけを呼ぶ
  • 何でも機械的にパイプライン全体に通さない

例：1つのテーマについてのリサーチで、的を絞った検索1回で十分なら、Web 検索 + ドキュメント分析 + 統合をすべて使う必要はありません。

Decomposition Risks — タスク分解のリスク

狭すぎる分解：試験ではこの点がよく問われます。例：coordinator が「creative industries」（クリエイティブ産業）について調べるよう頼まれたのに、視覚芸術（visual arts）に関するサブタスクにしか分けず、音楽、執筆、映画、デザインが抜け落ちてしまう。

対策：最初の分解を広めに取り、網羅できているかを確かめるステップ（coverage check）を明示的に入れる。

Iterative Refinement Loops — 繰り返して改善するループ

coordinator は統合結果を評価し、足りない部分を特定します：

Coordinator → Subagents (round 1)
         ↓
   Evaluate results
         ↓
   Identify gaps
         ↓
Coordinator → Subagents (round 2, targeted)
         ↓
   Final synthesis

1.3 Subagent Spawning and Context Passing — subagent の起動とコンテキストの受け渡し
The Agent Tool — Agent ツール

subagent は Agent ツールで起動します — これは Claude Code と Claude Agent SDK の両方で使われる正式な名前です。coordinator が subagent を起動するには、使用を許可するツールの一覧に Agent が含まれている必要があります。Agent(worker, researcher) のように書けば、起動できる subagent の種類を絞ることもできます。

💡 名前についての注意

古いドキュメント（Exam Guide の文言も含む）では、これを Task ツールと呼んでいます。Task はこの仕組みに対する Claude Code の元々の名前で、現在の Claude Code と SDK のドキュメントでは Agent という名前になっています。試験問題に「Task tool」と出てきたら、これのことです。

💡 SDK の名前

この SDK は「Claude Code SDK」から Claude Agent SDK に名前が変わりました。Python：pip install claude-agent-sdk。TypeScript：npm install @anthropic-ai/claude-agent-sdk。最上位の入口となる API：query() + ClaudeAgentOptions。

Context Must Be Explicit — コンテキストは明示的に渡す

この点は試験で特によく問われます：コンテキストは自動では引き継がれません。coordinator が subagent を起動するときは、subagent に必要なものをすべてプロンプトに入れなければなりません。

悪い例（Bad）：

"Analyze the customer's issue"
# Subagent has no idea who the customer is or what the issue is

良い例（Good）：

"Customer #12345 reported that their order #67890 (placed 2024-01-15,
total $149.99) arrived damaged. They are requesting a full refund.
Analyze the order history and return policy applicability."
Parallel Subagent Execution — subagent の並列実行

subagent を並列に動かすには、coordinator の1回の応答の中で複数の Agent ツール呼び出しを出します。複数のターンに分けてはいけません — そうすると順番に1つずつ（逐次）実行されてしまいます。

{
  "content": [
    {
      "type": "tool_use",
      "name": "Agent",
      "input": { "prompt": "Search for recent papers on...", "subagent_type": "search" }
    },
    {
      "type": "tool_use",
      "name": "Agent",
      "input": { "prompt": "Analyze the document at...", "subagent_type": "analysis" }
    }
  ]
}

Claude Code では、同時に動かせる subagent は最大 20（CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS）、subagent がさらに subagent を起動できる深さは最大 3（CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH）に制限されています。深さの上限に達した subagent からは Agent ツールが外され、それ以上は起動できなくなります。

AgentDefinition in the Claude Agent SDK — Claude Agent SDK の AgentDefinition
from claude_agent_sdk import query, ClaudeAgentOptions, AgentDefinition

async for message in query(
    prompt="Use the code-reviewer agent to review this codebase",
    options=ClaudeAgentOptions(
        allowed_tools=["Read", "Glob", "Grep", "Agent"],
        agents={
            "code-reviewer": AgentDefinition(
                description="Expert code reviewer for Python and TypeScript",
                prompt="Analyze code quality, identify bugs, suggest improvements.",
                tools=["Read", "Glob", "Grep"],
            ),
            "test-writer": AgentDefinition(
                description="Test generation specialist",
                prompt="Write comprehensive unit tests for the provided code.",
                tools=["Read", "Write", "Bash"],
            ),
        },
    ),
):
    print(message)

subagent のコンテキストの中から出されたメッセージには parent_tool_use_id フィールドが付きます — このフィールドで、メッセージがどの subagent の実行によるものかを判別します。

Forks vs Fresh Subagents — fork と新しい subagent の違い

fork は、切り離された subagent とは正反対のトレードオフです：会話のすべて — 履歴、システムプロンプト、ツール、モデル — を引き継ぎ、プロンプトキャッシュも共有するので、まったく新しい subagent を作るより安く済みます。メインの会話に返ってくるのは最終結果だけで、fork の中でのツール呼び出しは切り離されたままです。fork の中からさらに fork を作ることはできません。

新しい subagent（fresh subagent）Fork
会話履歴引き継がれない — 必要なものはすべて明示的に渡すすべて引き継がれる
システムプロンプト / ツールその subagent 独自のもの親セッションと同じ
プロンプトキャッシュなし（ゼロから）親セッションと共有（安い）
使いどころ範囲がはっきりしたタスク；親の会話を散らかしたくない、出力の多い探索同じ出発点（ベースライン）から分岐させて比べたいとき

Claude Code では /subtask <prompt> で fork を始められます。SDK/CLI では --fork-session を使うと、セッションを新しい ID で再開できます。fork_session は、この「共通の出発点から分岐する」という考え方の、API レベルでの以前の呼び名です。

Structured Context Passing — 構造化されたコンテキストの受け渡し

ベストプラクティス：エージェント間でコンテキストを渡すときは、本文（content）とメタデータを分けておく。

{
  "findings": [
    {
      "claim": "Revenue increased 15% YoY",
      "evidence": "Q4 earnings report, page 3",
      "source_url": "https://example.com/earnings",
      "document_name": "Q4 2024 Earnings Report",
      "publication_date": "2025-01-15"
    }
  ]
}

こうすることで出典情報（attribution）を保持でき、受け取ったエージェントが情報源の信頼性を判断できるようになります。

1.4 Workflow Enforcement and Handoff — ワークフローの強制と人への引き継ぎ
The Critical Distinction — 最も重要な区別

これは試験で最もよく問われる考え方の1つです：

強制の方法使いどころ保証の強さ
Programmatic（コードによる強制：hooks、前提条件のチェック）お金や安全に関わる結果があるDeterministic（確定的）— 100%保証される
Prompt-based（プロンプトでの指示のみ）「できる限り守れば良い」レベルで許されるProbabilistic（確率的）— 失敗する可能性が残る
Example: Financial Operations — 例：お金を扱う処理

状況：カスタマーサポートのエージェントは、返金を処理する前に本人確認をしなければならない。

誤ったやり方（プロンプトに頼る）：

"Always verify the customer's identity before processing any refund."

これは大半のケースではうまく動きますが、失敗の可能性はゼロではありません。お金を扱う処理では、「たいていは大丈夫」では許されません。

正しいやり方（コードで強制する）：

process_refund に対する PreToolUse hook で、get_customer がすでに呼ばれ、本人確認済みの顧客 ID を返しているかをチェックします。まだなら、hook は終了コード 2 を返して返金をブロックします。

Handoff to Humans — 人への引き継ぎ

エージェントが人にエスカレーションするとき、引き継いだ担当者は会話ログ（transcript）全体を見られないのが普通です。引き継ぎには構造化されたサマリーを付ける必要があります：

Customer: Jane Doe (#12345)
Issue: Damaged product received
Order: #67890, $149.99, placed 2024-01-15
Root cause: Shipping damage
Actions taken: Verified order, confirmed damage via photos
Recommended action: Full refund + replacement shipment
Refund amount: $149.99

PreToolUse Hooks (Current JSON Shape) — PreToolUse hook（現在の JSON の形）

各 matcher は hooks の配列を持ちます（以前の単数形のフィールド hook は廃止されました）。hook は async（非同期）で実行でき、権限ルール（if）で対象を絞り込めて、画面に表示される statusMessage を設定できます。

{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "process_refund",
        "hooks": [
          {
            "type": "command",
            "if": "Bash(git *)",
            "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/check-refund-authorization.sh",
            "timeout": 600,
            "statusMessage": "Verifying refund authorization...",
            "shell": "bash"
          },
          {
            "type": "mcp_tool",
            "server": "compliance",
            "tool": "check_refund_policy",
            "input": { "amount": "${tool_input.amount}" },
            "timeout": 60
          }
        ]
      }
    ]
  },
  "disableAllHooks": false
}

判断を返す出力の形（以前と同じ）：

{
  "hookSpecificOutput": {
    "hookEventName": "PreToolUse",
    "permissionDecision": "deny",
    "permissionDecisionReason": "Customer identity not yet verified",
    "additionalContext": "Call get_customer first to verify identity"
  }
}

permissionDecision の値："allow"（許可）、"deny"（拒否）、"ask"（ユーザーに確認）。

PostToolUse Hooks — PostToolUse hook

ツールの結果を、Claude が処理する前に加工します。次のような用途に便利です：

  • タイムスタンプ、日付の形式、ステータスコードをそろえる（正規化）
  • 結果から機密データを取り除く
  • 結果にメタデータを付け加える

ツール自体がエラーになった場合は、代わりに PostToolUseFailure が呼ばれます — リトライやエラーの診断はそこで行います。

Hooks in Skills and Subagents — skill や subagent の中の hook

現在は、SKILL.md の frontmatter の hooks: フィールドで、hook の有効範囲をその skill が動いている間だけに限定できます。subagent も独自の hook の定義を持てます。これにより、プロジェクト全体の設定を散らかさずに、局所的なルールを強制できます（例：git commit の前に必ず cargo fmt を実行させる commit skill）。

1.6 Task Decomposition Strategies — タスク分解の戦略
Prompt Chaining (Fixed Sequential) — prompt chaining（順番の決まった処理）

流れが予測でき、観点が複数あるタスク、つまり必要なステップが最初からはっきりしているタスク向け：

Step 1: Analyze each file individually (local analysis)
Step 2: Cross-file integration pass (data flow, consistency)
Step 3: Generate final report

各ステップの出力が、次のステップの入力になります。順番はあらかじめ決まっています。

Dynamic Adaptive Decomposition — 状況に応じた柔軟な分解

答えの決まっていない（open-ended）調査、つまり分かったことに応じて次のサブタスクが生まれるもの向け：

Initial query: "Why is the app slow?"
  → Profile CPU usage
    → Discovery: database queries are the bottleneck
      → Analyze query patterns
        → Discovery: N+1 queries in the user listing endpoint
          → Generate fix for specific queries

サブタスクは、各ステップで分かったことをもとに生まれます。

Multi-Pass Review Architecture — 複数回に分けたレビュー（multi-pass review）の構成

大きな PR のコードレビュー向け：

Pass 1 — ファイルごとのローカル分析：

  • 各ファイルを独立してレビューする
  • すべてのファイルを同じ深さでレビューする
  • そのファイル内の問題（バグ、スタイル、型）を見つける

Pass 2 — ファイル横断（cross-file）の統合チェック：

  • ファイル同士のつながりを見る、別のパス
  • データの流れ、インターフェースの食い違い、ファイル間の一貫性の問題を見つける
  • 連携（integration）の観点に絞った、別のプロンプトを使う

なぜ2回に分けるのか？大きな PR を1回（single-pass）でレビューすると：

  • 注意力の分散（attention dilution）— モデルは最初のほうのファイルに注意を向け、後半のファイルがおろそかになる
  • 結果が食い違う（ファイルによって基準がばらつく）
  • 連携の問題を見落とす（ファイル単体を見るだけでは、ファイルをまたぐ問題は見えない）

1.7 Session Management — セッションの管理
Resuming Sessions — セッションの再開

--resume <session-name> は、名前を付けた以前の会話を、コンテキストごと再開します。

再開すべきとき：

  • ツールの結果がまだ有効な（古くなっていない）、進行中の調査
  • 同じセッションの中で繰り返し改善していく開発

最初からやり直すべきとき：

  • ツールの結果が古くなった（ファイルが変更された、サービスが再起動した）
  • コンテキストが今のタスクから大きくずれてしまった
  • こうした場合は、再開するのではなく、それまでの発見を構造化したサマリーを渡して新しく始める
Forking a Session — セッションの分岐（fork）

--fork-session は、既存のセッションを新しい ID で再開します。そのため元のセッションはそのまま残り、各ブランチは互いに影響し合うことなく別々のアプローチを試せます。対話型のセッションでは、/subtask <prompt> で会話全体を引き継いだ fork を作り、その最終結果だけを受け取れます（§1.3 を参照）。

使いどころ：同じ出発点から、2つの異なるリファクタリング方針を試す。

Moving a Session Between Surfaces — 利用環境をまたいだセッションの移動

セッションは、もう特定のマシンに縛られていません。claude --cloud "<task>" はクラウド上のセッションで作業を始め、claude --teleport は Web のセッションをターミナルに引き戻し、/desktop は今のターミナルのセッションをデスクトップアプリに渡して、差分を画面で確認できるようにします。Remote Control を使えば、手元で動いているセッションをスマートフォンや別のブラウザから操作できます。これはアーキテクチャ上の大事なポイントです：「セッション」は持ち運べる状態のまとまりなので、エージェントが失ってはいけない情報は、画面の履歴（scrollback）ではなく、ファイルやメモリに残しておく必要があります。

Informing Resumed Sessions — 再開したセッションに変更を伝える

ファイルが変わった後にセッションを再開するときは、何が変わったかを Claude にはっきり伝える必要があります：

"Since our last session, I've updated auth.py to use JWT tokens instead of
session cookies. Please re-analyze the authentication flow with these changes."

再開したセッションが変更に自動で気づくと思い込まないこと — 前のセッションのツールの結果は、古いファイルの内容のままかもしれません。

2.1 Tool Interface Design — ツールのインターフェース設計
Tool Descriptions Are Everything — ツールの説明文がすべて

ツールの説明文（description）は、Claude がどのツールを呼ぶかを決める主な手がかりです。説明文はただの参考資料ではなく、選択の基準そのものです。

悪い説明文（選択が不安定になる）：

{
  "name": "search",
  "description": "Search for things"
}

良い説明文：

{
  "name": "search_knowledge_base",
  "description": "Search the internal knowledge base for support articles, FAQs, and troubleshooting guides. Use this when the customer asks a question that may have an existing documented answer. Input should be a natural language query describing the customer's issue. Returns matching articles ranked by relevance with titles, snippets, and article IDs."
}
What to Include in Tool Descriptions — 説明文に書くべきこと
  1. Purpose（目的） — このツールが何をするか、いつ使うべきか
  2. Input format（入力の形式） — どんな入力を渡すべきか（例を添えて）
  3. Output format（出力の形式） — ツールが何を返すか
  4. Edge cases（例外的なケース） — 入力が不正なときや、結果がないときにどうなるか
  5. Differentiation（使い分け） — 似たツールではなく「このツール」を使うべきとき
The Full Tool Definition Schema — ツール定義の完全な形
{
  "name": "get_weather",
  "description": "Get the current weather in a given location. Returns temperature, conditions, humidity, and wind speed. Use this when the user asks about current weather conditions. For forecasts, use get_forecast instead.",
  "input_schema": {
    "type": "object",
    "properties": {
      "location": {
        "type": "string",
        "description": "The city and state/country, e.g. 'San Francisco, CA' or 'London, UK'"
      },
      "unit": {
        "type": "string",
        "enum": ["celsius", "fahrenheit"],
        "description": "Temperature unit. Defaults to celsius if not specified."
      }
    },
    "required": ["location"]
  }
}
Strict Mode

strict mode を使うと、Claude がツールに渡す入力が、スキーマに完全に一致することが保証されます：

{
  "name": "extract_invoice",
  "strict": true,
  "input_schema": {
    "type": "object",
    "properties": {
      "vendor_name": { "type": "string" },
      "invoice_number": { "type": "string" },
      "total_amount": { "type": "number" },
      "currency": { "type": "string", "enum": ["USD", "EUR", "GBP"] }
    },
    "required": ["vendor_name", "invoice_number", "total_amount", "currency"],
    "additionalProperties": false
  }
}

strict mode を使うための条件：

  • additionalProperties: false を指定する
  • すべてのプロパティを required に含める
  • 使えるのは JSON Schema の機能の一部だけ（詳しくは Domain 4 を参照）
Anti-Pattern: Ambiguous Tool Overlap — アンチパターン：役割があいまいに重なった2つのツール

説明文がほぼ同じツールが2つあると、Claude は呼び分けを間違えます：

Tool 1: "analyze_content" — "Analyze content for insights"
Tool 2: "analyze_document" — "Analyze a document for insights"

Claude はこの2つを確実には見分けられません。対策：目的がはっきり区別できる名前に変えるか、1つのツールにまとめる。

2.2 Structured Error Responses — 構造化されたエラー応答
MCP Error Structure — MCP のエラーの形

ツールが失敗したときのエラー応答は、ありきたりな文字列ではなく、はっきりした構造を持たせるべきです：

{
  "isError": true,
  "errorCategory": "transient",
  "isRetryable": true,
  "description": "Database connection timed out after 30 seconds. The query was for customer #12345's order history.",
  "partial_results": null,
  "attempted_action": "SELECT * FROM orders WHERE customer_id = 12345"
}
Error Categories — エラーの種類
種類リトライできる？例エージェントの対応
Transient（一時的なエラー）はいタイムアウト、サービスの一時停止、レート制限間隔を空けながらリトライ（backoff）
Validation（入力エラー）いいえ（入力を直さない限り）メールアドレスの形式が不正、必須フィールドの不足入力を直してからリトライ
Business（業務ルールのエラー）いいえポリシーの上限を超える返金、凍結されたアカウントエスカレーションするか、ユーザーに事情を伝える
Permission（権限エラー）いいえアクセス権がない、トークンの期限切れエスカレーション
What the Agent Should Do with Errors — エージェントはエラーをどう扱うべきか
  1. 一時的なエラー：subagent がその場で立て直す仕組み（間隔を空けたリトライ）を持つべき。それでも復旧できなかったときだけ、上に報告する。
  2. 入力エラー：Claude はエラーの内容を確認し、入力を直してからリトライすべき。
  3. 業務ルールのエラー：Claude はユーザーにポリシーを説明するか、エスカレーションすべき。
  4. 権限エラー：Claude は人にエスカレーションすべき。
Anti-Patterns (Wrong Answers) — アンチパターン（試験では誤答）
  1. ありきたりなエラーメッセージ："Operation failed" — 原因が隠れてしまい、賢く立て直すことができなくなる。
  2. エラーを黙って隠す：検索エンジンが止まっているのに { "results": [] } を返す。本当は「検索できなかった」のに、「結果がなかった」ように見えてしまう。その結果エージェントは、ユーザーに自信満々で「何も見つかりませんでした」と伝えてしまう。
  3. あいまいなステータスメッセージ：何を試したのかがわからない "search unavailable"。
  4. 1つのステップの失敗でワークフロー全体を止める：途中までの結果を使ったり別の手段を試したりせず、1つのエラーだけで複数ステップの処理全体を止めてしまう。
Distinguishing Empty from Failed — 「結果が空」と「失敗」の区別

試験によく出る具体的なポイントです：

状況実際に起きていること正しい返答
検索がステータス 200 で [] を返す検索は正常に行われたが、該当するものがない「その条件に一致する結果は見つかりませんでした」
検索がタイムアウトのエラーを返す検索がそもそも実行されていない「検索できませんでした。もう一度試します」

この2つは別々に扱う必要があります。前者は「情報」、後者は「エラー」です。

2.3 Tool Distribution and tool_choice — ツールの割り当てと tool_choice パラメータ
The 4-5 Tool Maximum — ツールは最大 4〜5個

1つのエージェントに持たせるツールは最大 4〜5個にすべきです。1つのエージェントに18個も与えると選択の信頼性が下がります — Claude が間違ったツールを選んだり、不要なツールを呼んだり、どれを使うべきか判断に迷ったりします。

複雑なシステムでの解決策：ツールを複数の専門 subagent に分けて持たせる。

Instead of:
  One agent with 18 tools

Do:
  Coordinator with: Agent, AskUser
  Search subagent with: search_web, search_docs, search_db
  Analysis subagent with: analyze_text, extract_entities, summarize
  Action subagent with: send_email, create_ticket, update_record

これが試験での標準的な正解で、その根本にある原則（1つのエージェントには、1つの絞り込んだ仕事）は今でも正しいものです。ただし、Anthropic のドキュメントにある最新の数値も知っておく価値があります。

🔭 Beyond the Exam Guide: Tool Search — 試験範囲外：Tool Search

Anthropic の現在のガイダンスでは、エージェントが使えるツールがおよそ 30〜50個を超えると、ツール選択の精度が下がるとされています。また、よくある複数サーバーの MCP 構成（GitHub、Slack、Sentry、Grafana、Splunk）では、何もしないうちからツールの定義だけで約 55k トークンのコンテキストを消費します。今の対策は「subagent に分割する」だけではありません — Claude API で正式提供（GA）された tool search tool です。

"tools": [
  { "type": "tool_search_tool_regex_20251119", "name": "tool_search_tool_regex" },
  { "name": "get_weather", "description": "...", "input_schema": { ... },
    "defer_loading": true }
]

仕組み：

  1. すべてのツールの定義は、毎回のリクエストで全部送ります。defer_loading が決めるのは、どれをコンテキストウィンドウに入れるかであって、何を送るかではありません。
  2. 読み込みを後回しにしない（defer しない）ツールはすぐにコンテキストに読み込まれ、defer したツールは読み込まれません。
  3. Claude が別のツールを必要とすると、検索用のツールを呼びます。API は tool_reference ブロックを返し、それをコンテキストの中でその場で完全な定義に展開します — システムプロンプトの先頭部分には一切手を加えないので、プロンプトキャッシュはそのまま有効です。
  4. 2つの種類があります：tool_search_tool_regex_20251119（Claude が Python の re.search() 用のパターンを書く、最大200文字）と、tool_search_tool_bm25_20251119（自然な文章で検索する、最大500文字）。どちらもツール名、説明文、パラメータ名、パラメータの説明文を検索します。
ルール詳細
すべてを defer しない少なくとも1つのツール（通常は検索用のツール自体）は defer_loading: false にする必要がある。そうしないと 400 エラー「All tools cannot be deferred」になる
よく使うツールは残す（hot set）いちばんよく使う 3〜5個のツールは defer せずに残し、Claude が検索の往復なしですぐ呼べるようにする
上限1回のリクエストで defer できるツールは最大 10,000個；1回の検索でデフォルト 5件を返す（Claude が limit で 1〜10,000 の範囲で指定できる）
キャッシュdefer_loading: true のツールに cache_control は付けられない — 400 エラーになる。キャッシュの区切り（breakpoint）は defer していないツールに置く
併用strict: true と一緒に使える；出力の文法（grammar）はツールセット全体から作られる
MCP個々のツールに defer_loading を設定しない — mcp_toolset エントリの default_config で設定する

使うべきとき：ツールが10個以上ある、ツール定義が 10k トークンを超える、ツールが増えるにつれて精度が落ちてきた、複数の MCP サーバーをまとめて使っている。使わなくてよいとき：ツールが10個未満、すべてのツールを毎回のリクエストで使う、定義の合計が約100トークン未満。

2つの考え方を整理しましょう：試験の「4〜5個のツール」は、判断する瞬間にモデルの目の前にあるツールの数の話です。tool search はその数を増やしません — 目の前の数は 3〜5個に保ったまま、裏にあるカタログを数千個まで広げられるようにする仕組みです。

tool_choice Parameter — tool_choice パラメータ

Claude がツールをどう使うかを制御します：

値挙動使いどころ
"auto"（デフォルト）Claude はツールを呼んでも、テキストで答えてもよいツールを使うかどうかを任せる、通常の会話
"any"Claude は必ずどれかのツールを呼ぶが、どれを呼ぶかは自分で選ぶ必ず構造化出力を得たいとき
{"type": "tool", "name": "specific_tool"}Claude は必ずこのツールを呼ぶ特定の処理を必ず最初に実行させたいとき
"none"Claude はツールを呼べない；テキストでのみ答えるツールの定義はコンテキストに残したまま、テキストで答えさせたいとき

どの tool_choice の値にも "disable_parallel_tool_use": true を付けられ、Claude が1回の応答で呼べるツールを1つに制限できます（デフォルトでは、複数の tool_use ブロックを同時に出せます）。

When to Use Each — それぞれの使いどころ

"auto" — ほとんどの会話。ツールが必要かどうかは Claude が自分で決める。

"any" — 構造化出力を必ず得たいとき。例：抽出用のスキーマが複数（請求書、領収書、契約書）あり、Claude に合うスキーマを選ばせたうえで、必ず構造化データを返させたい。

特定のツールを強制 — 特定のツールを必ず最初に実行したいとき。例：情報を付け足す（enrichment）どのステップよりも先に、必ず extract_metadata を呼ぶ。

"none" — あるターンで文章を書かせたい（例：最後のまとめのステップ）が、リクエストからツールの定義を外したくないとき。

# Force Claude to call a specific tool
response = client.messages.create(
    model="claude-opus-5",
    messages=[...],
    tools=[...],
    tool_choice={"type": "tool", "name": "extract_metadata"}
)

2.4 MCP Server Configuration — MCP サーバーの設定
What is MCP? — MCP とは？

Model Context Protocol（MCP）は、AI モデルを外部のデータやツールにつなぐためのオープンな標準規格です。Claude がデータベース、API、ファイルシステムなどのサービスとやり取りするための、共通の方法を提供します。

│  └─────┬────┘  └─────┬────┘       │

CLI からサーバーを追加する：

# Remote HTTP server, shared with the team
claude mcp add --transport http --scope project shared-api https://example.com/mcp

# Remote server with a static auth header
claude mcp add --transport http secure-api https://api.example.com/mcp \
  --header "Authorization: Bearer $TOKEN"

# Local stdio server — everything after -- is passed to the server untouched
claude mcp add airtable --env AIRTABLE_API_KEY=YOUR_KEY -- npx -y @example/mcp-server

# Paste a config block written for another MCP client
claude mcp add-json example '{"type":"http","url":"https://mcp.example.com/mcp"}'
Project-Level Configuration (.mcp.json) — プロジェクト単位の設定

このファイルはプロジェクトのルートに置き、バージョン管理に含めます：

{
  "mcpServers": {
    "shared-api": {
      "type": "http",
      "url": "https://example.com/mcp",
      "headers": { "Authorization": "Bearer ${API_TOKEN}" },
      "timeout": 600000
    },
    "postgres": {
      "command": "npx",
      "args": ["@modelcontextprotocol/server-postgres"],
      "env": {
        "DATABASE_URL": "${DATABASE_URL}"
      }
    }
  }
}

重要なポイント：

  • ${DATABASE_URL} — 環境変数の展開。本物の秘密情報は設定ファイルに書かない。変数が未設定の可能性があるときは ${VAR:-default}（既定値付き）を使う。
  • command + args — MCP サーバーのプロセスを起動する方法（stdio 通信の場合）
  • timeout — サーバーごとのツール実行のタイムアウト（ミリ秒）。そのサーバーに限り MCP_TOOL_TIMEOUT より優先される
  • 対話型のセッションでは、Claude Code は .mcp.json にあるプロジェクト単位のサーバーを使う前に承認を求めます。一方、claude -p、Agent SDK のセッション、クラウドで動くセッションではこの確認を表示できないため、確認なしで読み込みます — 画面なし（headless）の実行で特定のサーバーを使わせたくないときは、disabledMcpjsonServers または --setting-sources で除外する
  • 一部のサーバー名は予約されています：workspace、claude-in-chrome、computer-use、Claude Preview、Claude Browser — これらの名前を使うと、警告付きで無視される
Authentication for Remote Servers — リモートサーバーの認証

HTTP と SSE のサーバーは OAuth に対応しています — セッション内で /mcp を実行する（または claude mcp add の後に認証する）と、ブラウザでのログインの流れやトークンの更新を Claude Code が自動で処理します。OAuth に対応していないサービスには、headers で固定のトークンを渡すか、認証情報の有効期限が短い場合は headersHelper（標準出力の内容がヘッダーの値になるコマンド）で接続のたびにトークンを生成します。WebSocket のサーバーは、ヘッダーによる認証のみです。

Tool Search Is On by Default in Claude Code — Claude Code では Tool Search がデフォルトで有効

MCP のツール定義は、デフォルトで読み込みが後回し（deferred）になります：セッションの開始時に読み込まれるのはツール名とサーバーの説明（server instructions）だけで、残りは必要になったときに Claude が検索します。そのため Claude Code では、サーバーごとのツール数に上限がありません — 実際の上限は、使えるコンテキストの量だけです。

ENABLE_TOOL_SEARCH挙動
（未設定）すべての MCP ツールを後回しにし、必要に応じて読み込む
true必ず後回しにする（プロキシ経由でも beta ヘッダーを送る）
auto / auto:N後回しにする定義の合計がコンテキストウィンドウの 10%（または N%）未満なら最初から読み込み、それを超えたら後回しにする
false最初からすべての MCP ツールを読み込む

Claude が毎ターンそのサーバーのツールを使う必要があるときは、サーバーのエントリに "alwaysLoad": true を設定して、後回しの対象から外します。サーバーを作る側は、分かりやすい server instructions（サーバーの説明）を書くべきです — tool search が有効なとき、Claude はこの説明を見て、あなたのサーバーを検索するかどうかを判断します。Claude Code は、ツールの説明文とサーバーの説明を、それぞれ 2 KB で切り詰めます。

Output Limits — 出力の上限

Claude Code は、MCP ツールの出力が 10,000 トークンを超えると警告し、デフォルトでは 25,000 トークンで自動的に切り詰めます。上限は MAX_MCP_OUTPUT_TOKENS で引き上げられますが、警告が出る値は固定で変えられません。これが、ツールの出力を絞ること（Domain 5）が重要な、仕組みの上での理由です — 出力の多すぎるサーバーは、自分の応答の後半を知らないうちに失っていることがあります。

MCP Resources — MCP のリソース

リソース（resources）はコンテンツの一覧を公開し、手探りのツール呼び出しの回数を減らします。Claude はあちこち検索する代わりに、使えるリソースを一覧で確認できます：

{
  "resources": [
    {
      "uri": "file:///project/docs/api-reference.md",
      "name": "API Reference",
      "mimeType": "text/markdown"
    }
  ]
}

2.6 Anthropic-Defined and Server-Side Tools — Anthropic が定義したツールと、サーバー側で動くツール

すべてのツールを自分で作るわけではありません。一部は Anthropic が定義したツール（Anthropic-defined）で、スキーマは不要です — type と name を宣言するだけで、Claude は使い方を知っています。また一部はサーバー側で動くツール（server-side）で、Anthropic のインフラ上で直接実行されます — 結果は同じ応答の中のブロックとして返ってくるので、クライアント側で実行ループを書く必要はありません。

試験や設計レビューで押さえておきたいポイント：

  • type の文字列にはバージョンがある。web_search_20260209 / web_fetch_20260209 には動的なフィルタリング機能が追加されていて、Opus 4.6 以降 / Sonnet 4.6 以降が必要です；それより古いモデルでは基本版の web_search_20250305 / web_fetch_20250910 を使います。_20260209 系と一緒に code_execution を宣言しないこと — これらは内部ですでにコードを実行しているので、実行環境が2つあるとモデルが混乱します。
  • Web fetch は、会話の中にすでに出てきた URL しか取得しない。Web 全体を巡回するクローラーではありません。
  • サーバー側ツールのエラーは例外にならない。HTTP 200 で、結果のブロックの中にエラーのオブジェクトを入れて返します（例：{"error_code": "max_uses_exceeded"}）。Web search では、成功時の content はリスト、エラー時の content はオブジェクトです — 要素にアクセスする前に、どちらなのかを確認して処理を分ける必要があります。これはまさに §2.2 の「結果が空」と「エラー」の区別の、API レベル版です。
  • pause_turn は、サーバー側ツールのループが内部の上限に達したことを知らせるものです。その応答を送り返せば処理が続きます（Domain 1 §1.1 参照）。
  • Bash と text editor にはスキーマがない。input_schema 付きで "bash" という名前の独自ツールを宣言すると、それは別のツールとして扱われます。
  • Advisor ツール：その model は、リクエストの最上位の model と同等以上の性能でなければなりません（例：実行役が claude-sonnet-5 なら、アドバイザーは claude-opus-5）。組み合わせが正しくないと 400 エラーになります。
Parallel Tool Use — ツールの並列呼び出し

デフォルトでは、Claude は1つの応答（assistant メッセージ）の中で複数の tool_use ブロックを出せます。それらを並行して実行し、すべての tool_result ブロックを1つの user メッセージにまとめて返しましょう。複数のメッセージに分けて返すと、Claude に「並列で呼ばないほうがいい」と知らず知らず教えることになってしまいます。エラーになったツールについても、is_error: true を付けて tool_result を必ず返すこと — 省略してはいけません。

Programmatic Tool Calling — コードからのツール呼び出し

Claude は、会話を経由せずに、コード実行用のサンドボックスの中から直接あなたの独自ツールを呼べます — 通常の方法だとコンテキストがあふれてしまうほど大きな結果を返すツールで便利です。{"type": "code_execution_20260120", "name": "code_execution"} を宣言し、その独自ツールに "allowed_callers": ["code_execution_20260120"] を設定します。コードからの呼び出しに応答するときの user メッセージには、tool_result ブロックだけを入れられます — テキストは入れられません。strict: true、disable_parallel_tool_use、特定ツールを強制する tool_choice、MCP ツールとは併用できません。

MCP from the API Side: the MCP Connector — API から MCP を使う：MCP Connector

Domain 2 の MCP の説明は、Claude Code（自分でクライアントを管理する host）の視点で書かれています。Messages API からも、リモートの MCP サーバーに直接接続できます。これには2つの設定の両方が必要です — mcp_servers だけを渡すと検証エラーになります：

    mcp_servers=[{"type": "url", "url": "https://mcp.example.com/mcp", "name": "example"}],
    tools=[{"type": "mcp_toolset", "mcp_server_name": "example"}],
    messages=[...],
)

defer_loading は、個々のツール定義ではなく、mcp_toolset エントリの default_config（またはツールごとの configs）で一度だけ設定します。

1. Managed Policy (org-wide, admin-controlled)
   └── /etc/claude-code/CLAUDE.md                           (Linux, WSL)
   └── /Library/Application Support/ClaudeCode/CLAUDE.md    (macOS)
   └── C:\Program Files\ClaudeCode\CLAUDE.md                (Windows)

2. User-Level (personal, NOT version-controlled)
   └── ~/.claude/CLAUDE.md

3. Project-Level (shared via version control)
   └── ./CLAUDE.md  or  ./.claude/CLAUDE.md

4. Local project (personal, gitignored)
   └── ./CLAUDE.local.md

5. Directory-Level (loaded on demand)
   └── ./src/api/CLAUDE.md (loaded when Claude reads files in src/api/)
   └── ./tests/CLAUDE.md (loaded when Claude reads files in tests/)

重要な違い：プロジェクト単位の CLAUDE.md は git にコミットされ、チーム全体で共有されます。ユーザー単位のものは個人用で、自分のパソコンにしかありません。CLAUDE.local.md はプロジェクトごとの個人用ファイルです（gitignore に入れるのを忘れずに）。ディレクトリ単位の CLAUDE.md は、Claude がそのディレクトリで作業するときに、その都度読み込まれます。

  • 相対パスは、import を書いたファイルの場所を基準に解決される

  • import されたファイルの中でも @import を使える（深さの上限を超えない範囲で）

Dynamic Context Injection — コンテキストの動的な差し込み

skill は、シェルコマンドの出力やファイルの内容を、Claude が読む前に差し込んでおけます：

!\`cmd\` と書くと、skill の内容が Claude に送られる前にコマンドが実行されます。複数行のコマンドには ```! を使います。@path によるファイルの埋め込みも同じように動きます。"disableSkillShellExecution": true で、この機能を完全に無効にできます。

Context Isolation (context: fork) — コンテキストの切り離し
  • skill を、専用のコンテキストを持つ subagent として実行する
  • agent: フィールドで実行する subagent を選ぶ（組み込みの Explore、Plan、general-purpose、または .claude/agents/* の独自の subagent）

Skill Lifecycle and Compaction — skill のライフサイクルとコンテキストの圧縮

skill が呼ばれると、その内容（コマンドの実行結果などを反映したもの）が1つのメッセージとして会話に入り、そのまま残ります。Claude Code は、以降のターンでこのファイルを読み直しません — だから、その場限りの手順ではなく、ずっと有効な指示として書きましょう。自動圧縮（auto-compaction）が行われると、最近呼ばれた skill が改めて添付されます（各 skill の先頭 5,000 トークン、全体で最大 25,000 トークン）。たくさん使っている場合は、古い skill から外されます。

  • /code-review — 作業中の変更や PR を、複数のエージェントでレビュー（ultra モードはクラウドで実行）
  • /security-review — ブランチ上の作業中の変更を、セキュリティの観点でレビュー
  • /simplify — 変更したばかりのコードを、再利用・簡素化・効率化の観点で整理
  • /dataviz — デザインのそろったグラフやダッシュボードを作成
  • /design — 複数のアートボードを持つ、デザイン用のキャンバス
  • /init — コードベースに合わせた CLAUDE.md のひな形を作成
  • /run — プロジェクトのアプリを実行し、変更が正しく動くかを確認
  • /loop — プロンプトやスラッシュコマンドを一定の間隔で繰り返し実行

Plugins — プラグイン

プラグイン（plugin）は、skill、subagent、hook、MCP サーバーをまとめた配布用のパッケージで、マーケットプレイスからインストールし、プロジェクトごとに有効にします。プラグインが提供するものには名前の接頭辞が付くので（skill は plugin-name:skill-name、MCP サーバーは plugin:<plugin>:<server>）、自分で作ったものと名前がぶつかりません。skill の優先順位では、プラグインがいちばん低くなります（Enterprise > Personal > Project > Plugin）。

プラグインは、claude plugin eval コマンドでテストする単位でもあります：プラグインの skill を対象にした評価（eval）のセットを書き、サンドボックスや CI で実行すると、JSON 形式のレポートが出力されます。これが「チームは自分たちの Claude Code の決まりごとを、どうやって配布し、変更で壊れていないか（リグレッション）を確認するのか？」という問いへの、パッケージングの面からの答えです。

3.3 Path-Specific Rules — パス指定のルール
Conditional Rule Loading — ルールを条件付きで読み込む

.claude/rules/ のルールは、YAML frontmatter に glob パターンを書くことで、どのファイルに適用するかを指定できます：

---

  - "src/api/**/*.ts"
  - "src/api/**/*.test.ts"
---

# API Development Rules

All API endpoints must:
- Use Zod for request validation
- Return standardized error responses
- Include rate limiting middleware
- Have corresponding integration tests
---
paths:
  - "**/*.test.tsx"
  - "**/*.test.ts"
  - "**/*.spec.ts"
---

# Testing Conventions

- Use React Testing Library, not Enzyme
- Test behavior, not implementation
- Mock external APIs, not internal modules
- Each test file must have a describe block matching the component/function name
When Path-Specific Rules Beat Directory CLAUDE.md — パス指定のルールが、ディレクトリ単位の CLAUDE.md より優れている場面

状況：テストの規約を、コードベース全体に散らばったテストファイルに適用したい。

ディレクトリ単位の CLAUDE.md を使う場合：

src/
  components/
    CLAUDE.md  ← Would need testing rules here
    Button.test.tsx
  api/
    CLAUDE.md  ← And here
    users.test.ts
  utils/
    CLAUDE.md  ← And here
    format.test.ts

パス指定のルールを使う場合：

.claude/
  rules/
    testing.md  ← One file with paths: ["**/*.test.*"]

パス指定のルールのほうが良い理由：

  • テストの規約を1か所で管理できる
  • テストファイルがあるすべての場所に適用される（後から作られるディレクトリも含む）
  • CLAUDE.md をあちこちのディレクトリにコピーする必要がない

3.4 Plan Mode vs Direct Execution — plan mode と直接実行
Permission Modes (Current) — 権限モード（現行）

plan mode は現在、より大きな「権限モード（permission mode）」の仕組みの中の、1つのモードという位置づけです。--permission-mode <mode> で特定のモードから始めたり、対話型のセッションで Shift+Tab を押してモードを切り替えたりできます。

モード挙動
default通常どおり、操作ごとに許可を求める
acceptEditsファイルの編集は自動で許可し、他のツールは引き続き確認する
plan調べるだけのモード：Claude は進め方を設計し、ファイルに手を加える前にそれを提示する
auto操作ごとに確認が必要かどうかを、判定器が自動で判断する — claude auto-mode defaults を参照
dontAsk事前に許可したものについては一切確認しない
bypassPermissionsすべての確認をスキップする（危険；範囲の狭い短いタスクでのみ使う）
When to Use Plan Mode — plan mode を使うべきとき
こんなとき例
複数のファイルにまたがる変更15ファイルにわたる認証処理のリファクタリング
アーキテクチャの判断が必要REST と GraphQL のどちらにするか
妥当な進め方が複数あるキャッシュの実装方法が何通りもある
影響範囲が大きい45以上のファイルに影響するライブラリの移行
要件がはっきりしない「アプリを速くして」— まず調査が必要

plan mode では、Claude は：

  1. コードベースを調べる（Glob、Grep、Read）
  2. 影響を受けるファイルやパターンを特定する
  3. 進め方を設計する
  4. 計画を示して承認を待つ
  5. ユーザーが承認してから実装を始める
When to Use Direct Execution — 直接実行すべきとき
こんなとき例
1ファイルだけの修正スタックトレースから原因が明らかなバグの修正
範囲が明確null チェックを1つ追加する
指示が明確「User モデルに createdAt フィールドを追加して」
小さな変更誤字の修正、定数の更新
Built-in Subagents — 組み込みの subagent

Claude Code には4つの subagent が最初から入っており、対話型のセッションではデフォルトで使えるようになっています：

エージェント目的ツール
Exploreファイルの検索と、コードベースのすばやい探索読み取り専用；CLAUDE.md と git status は読まない
Planplan mode で変更を提案する前の下調べ読み取り専用；CLAUDE.md と git status は読まない
general-purpose調べることと実行することの両方が必要な、複数ステップのタスクsubagent が使えるすべてのツール
claudeどのケースにも対応する、汎用の予備（fallback）subagent が使えるすべてのツール

Explore エージェントは、コンテキストをきれいに保つための定番のテクニックです：

Main conversation context is preserved
     ↓
Explore subagent runs (Glob, Grep, Read — lots of output)
     ↓
Returns concise summary to main conversation
     ↓
Main context stays clean

この仕組みがないと、コードベースを深く1回調べただけで、メインのコンテキストがファイルの中身や検索結果でいっぱいになってしまいます。

Custom Subagents (.claude/agents/) — 独自の subagent

独自の subagent は YAML frontmatter 付きの markdown ファイルで定義し、次の優先順位で解決されます：managed settings（組織の管理設定）> CLI の --agents で渡す JSON > プロジェクト（.claude/agents/）> ユーザー（~/.claude/agents/）> プラグイン。

---
name: db-reader
description: Execute read-only database queries        # how Claude decides to delegate
tools: Read, Grep, Bash                                # allowlist
disallowedTools: Write, Edit                           # denylist, applied after `tools`
model: sonnet                                          # inherit | sonnet | opus | haiku | full ID
effort: low                                            # low | medium | high | xhigh | max
permissionMode: plan                                   # default | acceptEdits | auto | dontAsk | bypassPermissions | plan
maxTurns: 10
skills: [api-conventions]                              # preloaded skill content
mcpServers: [github]
memory: project                                        # user | project | local — persistent across sessions
isolation: worktree                                    # run in its own git worktree
background: false
hooks:
  PreToolUse:
    - matcher: "Bash"
      hooks:
        - type: command
          command: ./scripts/validate-readonly-query.sh
---

Execute SELECT queries only. Never issue writes.

呼び出す3つの方法：自然な文章で名前を出す（「db-reader を使って…」）、確実にそのエージェントを動かすために @ で指定する、または claude --agent db-reader でセッション全体をそのエージェントとして始める。

新しく起動した subagent が読み込むもの：自分のシステムプロンプト、委任されたときの指示、CLAUDE.md の全階層、git status のスナップショット、事前に読み込む skill、環境の情報。引き継がれないもの：あなたとの会話履歴、メインのセッションの自動メモリ、他の subagent の結果 — これが Domain 1 §1.3 で説明した「コンテキストは引き継がれない」ルールです。

覚えておきたい制約：権限モードは上から下へ引き継がれます — 親のプロセスが bypassPermissions、acceptEdits、auto で動いていると、subagent もそのモードになり、変更することはできません。subagent の入れ子はデフォルトで最大3階層、同時に動かせるのは最大20個です。終わった subagent は、SendMessage で ID か名前を指定して再開でき、以前のコンテキストもそのまま残っています；ただし使い切りのエージェント（Explore、Plan）は再開できません。

💡 プロンプトインジェクションについての注意

Claude Code は、親のプロセスが subagent の報告を読む前に、指示のように見える文章がないかをチェックし、システムの出力になりすまそうとするテキストを無害化します。これはリスクを減らすための対策であって、権限の境界ではありません — すべてのツール呼び出しは、これまでどおりセッションの権限チェックを通る必要があります。

Combining Modes — モードの組み合わせ

plan mode で調べる → 直接実行（direct execution）で実装する：

  1. plan mode に入る
  2. コードベースを調べる
  3. 進め方を設計する
  4. ユーザーに計画を示す
  5. ユーザーが承認する
  6. plan mode を抜ける
  7. 1ファイルずつ直接実装する

3.5 Iterative Refinement Techniques — 繰り返して改善するテクニック
1. Concrete Examples — 具体例を示す

文章での指示では結果が安定しないときは、入力/出力の例を2〜3個示します：

Instead of: "Format dates consistently"

Use: "Format dates as YYYY-MM-DD. Examples:
  Input: 'January 5th, 2024' → Output: '2024-01-05'
  Input: '12/31/23' → Output: '2023-12-31'

4.1 Explicit Criteria — 明確な基準
The Problem with Vague Instructions — あいまいな指示の問題点

あいまいな指示では、モデルが実行するたびに違う解釈をしてしまうため、結果が安定しません。

悪い例（あいまい）：

"Be conservative when flagging issues."
"Only report high-confidence findings."
"Use your best judgment on severity."

良い例（明確）：

"Flag a comment as outdated ONLY when the claimed behavior directly
contradicts the actual code behavior. Do NOT flag comments that are
merely incomplete or could be more detailed."
Explicit Criteria Structure — 明確な基準の組み立て方

モデルに判断させることの種類ごとに、次の3つを定義します：

  1. What qualifies（該当するもの） — その判断をすべき具体的な条件
  2. What doesn't qualify（該当しないもの） — その判断をしてはいけない境界のケース
  3. Examples（例） — その境界を示す、具体的な入力と出力の組
Flag as SECURITY ISSUE when:
  - User input is passed to SQL queries without parameterization
  - User input is rendered in HTML without escaping
  - Credentials are hardcoded in source files

Do NOT flag:
  - ORM queries (already parameterized)
  - Rendering user input in server-side templates with auto-escaping
  - Credentials loaded from environment variables
False Positive Impact — 誤検知（false positive）の影響

あるカテゴリで誤検知が多いと、正しく機能している他のカテゴリも含め、すべてのカテゴリが信頼されなくなります。開発者は、正しい警告まで含めて、すべての警告を無視するようになってしまいます。

解決策：誤検知の多いカテゴリはいったん無効にし、そのカテゴリの判断基準（プロンプト）を改善してから、再び有効にする。ノイズの多い1つのカテゴリのせいで、正確なカテゴリの価値まで下げないこと。

4.2 Few-Shot Prompting — 例を見せるプロンプト（few-shot prompting）
When to Use Few-Shot — few-shot を使うべきとき
  • 文章の指示だけでは正確に伝えきれない、あいまいな場面
  • 出力の形式や考え方の筋道を、実例で示す必要があるタスク
  • 情報抽出（extraction）タスクで、ハルシネーション（事実と異なる出力）を減らしたいとき
  • 例外的なケース（edge case）の扱い方を示したいとき
How Many Examples — 例はいくつ用意するか

目的のはっきりした例を 2〜4個用意するのが最適です。少なすぎるとパターンを網羅できず、多すぎるとコンテキストを消費するうえ、モデルが例そのものに引きずられてしまう（過学習のような状態になる）ことがあります。

What Good Examples Include — 良い例に含めるもの

それぞれの例で示すこと：

  1. Input（入力） — モデルが受け取るもの
  2. Output（出力） — モデルが返すべきもの
  3. Reasoning（理由） — なぜその出力が正しいのか（何をするかだけでなく、その理由まで）
Example 1:
Input: "// Returns the user's full name"
Code: function getName(user) { return user.firstName; }
Output: {
  "issue": "Comment claims full name but function only returns firstName",
  "severity": "medium",
  "location": "line 1",
  "reasoning": "The comment says 'full name' but the code returns only
    firstName, not firstName + lastName. This is a factual contradiction."
}

Example 2:
Input: "// Validates the input"
Code: function validate(input) { return input.length > 0 && input.length < 100; }
Output: null
Reasoning: "The comment says 'validates input' and the function does validate
  input. The comment is vague but not wrong — it doesn't claim specific
  validation rules that contradict the implementation."
Few-Shot Enables Generalization — few-shot でモデルが応用できるようになる

良い例は、個別のケースだけでなく、パターンそのものをモデルに教えます。モデルは例を丸暗記するのではなく、それぞれの例の背景にある考え方を理解することで、初めて見る状況にも応用できるようになります。

4.3 Structured Output via tool_use — tool_use による構造化出力
The Problem — 問題

Claude に構造化データ（JSON）を返させたいとき、自由にテキストを書かせると、次のようなことが起こりえます：

  • 形式の壊れた JSON
  • 必須フィールドの抜け
  • 想定と違うフィールド名
  • 間違ったデータ型
Solution 1: tool_use with Schema — 解決策1：スキーマ付きの tool_use

欲しい出力の構造を表すツールを定義します：

{
  "name": "extract_invoice_data",
  "description": "Extract structured data from an invoice document",
  "input_schema": {
    "type": "object",
    "properties": {
      "vendor_name": {
        "type": "string",
        "description": "The company or person who issued the invoice"
      },
      "invoice_number": {
        "type": "string",
        "description": "The unique invoice identifier"
      },
      "line_items": {
        "type": "array",
        "items": {
          "type": "object",
          "properties": {
            "description": { "type": "string" },
            "quantity": { "type": "number" },
            "unit_price": { "type": "number" },
            "total": { "type": "number" }
          },
          "required": ["description", "quantity", "unit_price", "total"]
        }
      },
      "total_amount": { "type": "number" },
      "currency": {
        "type": "string",
        "enum": ["USD", "EUR", "GBP", "other"]
      }
    },
    "required": ["vendor_name", "invoice_number", "line_items", "total_amount", "currency"]
  }
}

tool_choice: {"type": "tool", "name": "extract_invoice_data"} を使って Claude にこのツールを必ず呼ばせれば、確実に構造化出力が得られます。

Solution 2: Strict Mode — 解決策2：Strict Mode

ツールの定義に "strict": true を加えると、スキーマに完全に沿った出力が保証されます：

{
  "name": "extract_invoice_data",
  "strict": true,
  "input_schema": {
    "type": "object",
    "properties": { ... },
    "required": ["vendor_name", "invoice_number", "line_items", "total_amount", "currency"],
    "additionalProperties": false
  }
}

strict mode の条件：

  • additionalProperties: false を指定する
  • すべてのプロパティを required に並べる
Solution 3: output_config (Direct JSON Output) — 解決策3：output_config（JSON を直接出力する）

tool_use を使う代わりに、JSON での出力を直接指定することもできます。使うパラメータは output_config.format です。以前のトップレベルのパラメータ output_format は非推奨（deprecated）なので、新しいコードでは使わないこと。また、以前必要だった beta ヘッダー structured-outputs-2025-11-13 も、今は不要です：

response = client.messages.create(
    model="claude-opus-5",
    messages=[{"role": "user", "content": "Extract data from this invoice: ..."}],
    output_config={
        "format": {
            "type": "json_schema",
            "schema": {
                "type": "object",
                "properties": {
                    "vendor_name": { "type": "string" },
                    "total_amount": { "type": "number" }
                },
                "required": ["vendor_name", "total_amount"],
                "additionalProperties": false
            }
        }
    }
)
💡 SDK の便利機能

client.messages.parse()（Python/TypeScript）は、この使い方をあらかじめまとめたものです — Pydantic のモデルか Zod のスキーマを渡すだけで、output_config.format を自動で送り、そのスキーマで応答を検証し、解析済みのオブジェクトを response.parsed_output で返してくれます。構造化出力を扱うときは、JSON を自分で解析するより、こちらを優先しましょう。

Schema Compliance vs Semantic Correctness — スキーマに沿っていることと、意味として正しいことの違い

試験で重要な考え方：構造化出力で保証されるのはスキーマへの準拠（schema compliance）— 正しいデータ型、必須フィールドがそろっている、有効な enum の値 — であって、意味としての正しさ（semantic correctness）は保証されません。

スキーマに準拠：✅ "total_amount": 150.00（型は正しく、フィールドもある）
意味の誤り：❌ "total_amount": 150.00 なのに、明細の合計は 175.00

こうした意味の誤りを見つけるには、別に検証のロジックが必要です。

Schema Design Patterns — スキーマ設計のパターン

Required vs Optional Fields（必須フィールドと任意フィールド）：

{
  "purchase_order_number": {
    "type": ["string", "null"],
    "description": "PO number if present on the invoice, null if not found"
  }
}

元のドキュメントにその情報がない可能性があるときは、null を許すフィールド（nullable）にします。すべてを必須にすると、Claude はデータを作り上げざるを得なくなることがあります。

"other" を含む enum：

{
  "document_type": {
    "type": "string",
    "enum": ["invoice", "receipt", "contract", "purchase_order", "other"]
  },
  "document_type_detail": {
    "type": ["string", "null"],
    "description": "If document_type is 'other', describe the document type"
  }
}

"unclear" を含む enum：

{
  "payment_status": {
    "type": "string",
    "enum": ["paid", "unpaid", "partial", "unclear"]
  }
}

選択肢に "unclear"（不明）を加えておくと、情報がはっきりしないときに Claude が当てずっぽうで答えるのを防げます。

JSON Schema Limitations in Strict Mode — Strict Mode で使える JSON Schema の制限

Strict mode で使えるのは、JSON Schema の機能の一部だけです：

使える（Supported）使えない（NOT Supported）

properties, requiredminLength, maxLength
enum, constpattern (regex), patternProperties

anyOf, allOf, $ref/$defs再帰的なスキーマ

以前の構造化出力では anyOf/allOf が使えませんでしたが、現在は使えます。Python と TypeScript の SDK は、使えない制約を送信前にスキーマから自動で取り除き、代わりにクライアント側でそれらをチェックします。

実務での意味：数値の範囲、文字列の長さ、正規表現のパターン、複雑な条件付きのスキーマのチェックは、スキーマではなく、自分の検証コードで行う必要があります。

4.4 Validation-Retry Loops — 検証してリトライするループ
The Pattern — 基本の形
max_retries = 3

for iteration in range(max_retries):
    response = extract_data(document, prompt)
    errors = validate(response)

    if not errors:
        return response  # Success

    # Append specific errors to prompt for next attempt
    prompt += f"""
    Your previous extraction had these validation errors:
    {json.dumps(errors, indent=2)}

    Please correct these specific issues and try again.
    """

raise ExtractionError(f"Failed after {max_retries} attempts: {errors}")
What Validation Catches — 検証で見つけられるもの

スキーマの検証（Schema validation）（確実に見つけられる）：

  • 必須フィールドの抜け
  • データ型の誤り
  • 無効な enum の値
  • 形式の誤った日付やメールアドレス

意味の検証（Semantic validation）（独自のロジックが必要）：

  • 明細の合計が総額と合わない
  • 未来であるはずのない日付が未来になっている
  • 参照している対象が存在しない
  • フィールドどうしの内容が矛盾している
Self-Correction Patterns — 自己修正のパターン

計算した値と記載された値（Calculated vs Stated）：

{
  "stated_total": 150.00,
  "calculated_total": 175.00,
  "conflict_detected": true,
  "conflict_note": "Stated total ($150) doesn't match sum of line items ($175)"
}

記載されている値と、自分で計算した値の両方を抽出しておけば、食い違いを自動で見つけられます。

When Retries Don't Work — リトライしても意味がないとき

情報が元のドキュメントにそもそも存在しない場合、リトライしても効果はありません。請求書に PO 番号が書かれていなければ、何回リトライしても出てきません。

解決策：リトライを繰り返すのではなく、null を許す（nullable/optional の）フィールドにして、欠けているデータは null のままにしておく。

Tracking False Positives — 誤検知の記録と分析

どんなコードの書き方が指摘を引き起こしたのかを記録するために、detected_pattern フィールドを追加します：

{
  "issue": "Potential SQL injection",
  "detected_pattern": "string concatenation in query",
  "file": "users.py",
  "line": 42
}

これで、よく却下（dismiss）されるパターンを分析できます — 開発者が「string concatenation in query（クエリでの文字列連結）」の指摘を何度も却下しているなら、そのパターンの判断基準（プロンプト）を見直す必要があるかもしれません。

When to Use Batch vs Synchronous — バッチ処理と同期処理の使い分け
同期処理（Synchronous）バッチ処理（Batch）

Failure Handling — 失敗したときの対処

一部のリクエストが失敗しただけで、バッチ全体を送り直さないこと。custom_id で失敗したリクエストだけを特定し、それだけを再送します：

failed = [r for r in results if r.status == "failed"]
resubmit = [orig for orig in original if orig.custom_id in [f.custom_id for f in failed]]
Pre-Batch Refinement — バッチ実行前の調整

大量のバッチを流す前に、必ず少数のサンプルでプロンプトを調整しましょう。1万件のドキュメントで費用を使ってしまう前に、プロンプトの問題を見つけられます。

4.6 Multi-Pass Review — 独立した複数回のレビュー
The Self-Review Problem — 自分でレビューすることの問題

Claude がコードを生成し、同じセッションでそのままレビューすると、生成したときの考えの流れ（reasoning context）がそのまま残っています。なぜそう判断したのかを「覚えている」ので、その判断自体を疑いにくくなります。

これを reasoning context bias（生成時の考えを覚えていることによる思い込み）と呼びます。

The Solution: Independent Review Instances — 解決策：独立したレビュー用インスタンスを使う
Session 1: Claude generates code
                    ↓
            (completely separate session)
                    ↓
Session 2: Claude reviews the code
           (no knowledge of why decisions were made)
Multi-Pass Architecture for Large PRs — 大きな PR 向けの複数パス構成

Pass 1 — ファイルごとの分析（local analysis）：

  • 各ファイルを1つずつ、独立してレビューする
  • どのファイルも同じ深さでレビューする
  • 見つけられるもの：バグ、コードスタイルの問題、型エラー、セキュリティの脆弱性
  • ファイルごとに別のプロンプトを使う

Pass 2 — ファイル横断の統合チェック（cross-file integration）：

  • ファイル同士のつながりをレビューする
  • 統合の問題に絞った、別のプロンプトを使う
  • 見つけられるもの：データの受け渡し（data flow）の問題、インターフェースの食い違い、モジュールの境目でのエラー処理の抜け
  • Pass 1 の結果を前提情報として受け取る
Why Not Single-Pass? — なぜ1回のレビューではダメなのか

大きな PR（10ファイル以上）を1回でまとめてレビュー（single-pass）すると、次の問題が起きます：

  1. Attention dilution（注意の分散） — モデルは最初のほうのファイルに集中し、後半のファイルへの注意が薄れる
  2. Inconsistent standards（基準のばらつき） — ファイルによってレビューの質に差が出る
  3. Missing integration issues（統合の問題の見落とし） — ファイルを順番に見ていくだけでは、ファイルをまたぐ問題に気づけない

Effort — 推論の労力（effort）

effort は正式リリース済み（GA、beta ヘッダー不要）で、トップレベルではなく output_config の中に書きます：

output_config={"effort": "xhigh"}   # low | medium | high | xhigh | max

Claude Opus 5 と Sonnet 5 のデフォルトは high です（Claude API・Claude Code 共通）。現行の最上位モデルでは、コーディングやエージェント型のタスクのほとんどで xhigh が最もバランスの良い設定です。subagent や単純作業には low を使いましょう — effort を下げるほどツール呼び出しが減り、まとめて実行されるようになり、出力も簡潔になります。費用より正確さが大事なときは max を使います。これらのモデルでは effort による差がこれまでのどの世代よりも大きいので、古い設定値をそのまま使わず、移行時に改めて調整しましょう。

Thinking Display — thinking の表示

Fable 5、Opus 5、Opus 4.8/4.7、Sonnet 5 では、display: "omitted"（thinking の内容を表示しない）がデフォルトになりました — デフォルトが "summarized" だった Opus 4.6 と Sonnet 4.6 から、目立たないうちに変わった点です。thinking 自体は行われ、課金もまったく同じで、変わるのは表示されるかどうかだけです。推論の過程をユーザーにストリーミングで見せている場合、このデフォルトのままだと出力が始まるまで長く止まっているように見えるので、display: "summarized" を明示しましょう。なお、推論の生データ（raw chain of thought）は、どのモデルでも公開されません。

Assistant Prefill Is Gone — assistant の prefill は使えなくなった

応答の形式を固定するために最後の assistant ターンを先に書いておく（prefill）と、Fable 5、Opus 5、Sonnet 5、そして 4.6/4.7/4.8 のすべてで 400 エラーになります。代わりに構造化出力（output_config.format）か、system prompt での指示を使いましょう。古いドキュメントの多くがいまだに勧めているプロンプトの技法が、1つ使えなくなったということです。

Mid-Conversation System Messages — 会話の途中に入れる system message

Claude Opus 5、Opus 4.8、Fable 5 では（Sonnet 5 は対象外、beta ヘッダー不要）、トップレベルの system フィールドを書き換える代わりに、messages 配列の中に {"role": "system", "content": "..."} を追加できます。これはプロンプトインジェクションに強い、オペレーター用の指示の経路です。キャッシュ済みの先頭部分（prefix）に触れないので、最も安く済む方法でもあります。制約：user の message（またはサーバーツールの使用で終わる assistant の message）の後に置く必要があり、messages[0] には置けず、最後の message にするか、直後に assistant のターンを続ける必要があります。

4.8 Prompt Caching — プロンプトキャッシュ

キャッシュが効くかどうかはプロンプトの構造で決まるため、運用手順ではなくこのセクションで扱います。

Prefix match（先頭部分の一致）：キャッシュは、リクエストの先頭部分（prefix）が完全に一致したときだけ使われます。先頭部分のどこか1バイトでも変わると、それ以降はすべて無効になります。組み立てられる順番は tools → system → messages なので、リクエストのたびにツール一覧の順番が変わると、system prompt とそれ以降の会話全体のキャッシュが無効になります。

設計のルール：変わらない内容（固定の system prompt、順番を固定したツール一覧）を先に置き、変わる内容（タイムスタンプ、リクエストごとの ID、実際の質問）は最後の cache_control ブレークポイントより後ろに置く。

仕組み詳細
Breakpoints（ブレークポイント）1リクエストにつき最大4つ（cache_control: {"type": "ephemeral"}）
Minimum prefix（最小の長さ）約1024トークン — これより短いと、何の通知もなくキャッシュされない
Verification（確認方法）usage.cache_read_input_tokens を見る。何回リクエストしても 0 のままなら、どこかで先頭部分が変わっている
Pre-warming（事前ウォームアップ）max_tokens: 0 で送ると、出力を生成せずにキャッシュだけを作れる

気づかないうちにキャッシュを無効にしてしまう原因 — チェックリスト：system prompt に入れた datetime.now()、キーの順番が毎回変わる JSON の書き出し、リクエストごとに変わるツールの組み合わせ、先頭部分に入れたセッション ID やユーザー名、会話の途中での speed（fast mode）の切り替え。

tool search との関係：読み込みを後回しにした（deferred）ツールは system prompt の先頭部分に含まれず、見つかったツールは会話の中に挿入されるため、defer_loading を使ってもキャッシュは壊れません。ただし、defer_loading: true のツールには cache_control を同時に付けられないので、ブレークポイントは defer していないツールに置きましょう。

Domain 5 の補強

「context rot」、Case Facts Block のパターン、データが食い違うときの対処法 — Domain 5 をさらに深く理解する。

5.1 Conversation Context Management — 会話のコンテキスト管理
The Context Window Is Finite — コンテキストウィンドウには上限がある

Claude が一度に扱える情報量（コンテキストウィンドウ）には上限があります。すべての message、ツールの結果、system prompt がトークンを消費します。会話が長くなるほど、古い情報が圧縮されたり、完全に消えたりして、品質が落ちやすくなります。

現在のサイズは次のとおりです。「100万トークン」になっても、問題の形が変わっただけで、問題そのものがなくなったわけではありません：

モデルコンテキストウィンドウ最大出力
Claude Fable 5 / Opus 5 / Sonnet 51M トークン128k
Claude Opus 4.8 / 4.7 / 4.6, Sonnet 4.61M トークン128k
Claude Haiku 4.5200k トークン64k

1M のウィンドウには、2つの落とし穴があります：

  1. ウィンドウが大きくても、タダではない。中に入っているトークンは毎ターン課金されます。さらに、後で説明する「lost in the middle」効果は、コンテキストが長いほどひどくなります。「入るから」という理由で 1M を埋め尽くすと、費用がかさむうえに品質も下がります。
  2. トークンの数え方が変わった。Opus 4.7 で新しいトークナイザーが導入され、Opus 4.8、Opus 5、Fable 5 にも引き継がれています。同じテキストでも、4.7 より前のモデルに比べてトークン数が約30%多くなります。古いモデルに合わせて決めた予算、分割（chunk）のサイズ、しきい値は、すべて messages.count_tokens で測り直す必要があります — tiktoken は使わないこと。
Progressive Summarization Risks — 要約を重ねることのリスク

コンテキストが圧縮されると（/compact や自動圧縮によって）、それまでの会話が要約されます。これには次のリスクがあります：

要約で失われやすいもの：

  • 正確な数値（$149.99 が「約 $150」になる）
  • 具体的な日付（2024-01-15 が「1月中旬」になる）
  • 正確なパーセンテージ（23.7% が「約24%」になる）
  • 注文番号、顧客 ID、参照コード
  • 正確なエラーメッセージやスタックトレース

解決策：Case Facts Block（案件の事実をまとめたブロック）

重要な取引データを、要約されずに常に残る構造化されたブロックとして取り出しておきます：

CASE FACTS (do not summarize):
- Customer ID: #12345
- Order: #67890
- Order date: 2024-01-15
- Total: $149.99
- Issue: Damaged product on arrival
- Refund requested: Full refund ($149.99)
The "Lost in the Middle" Effect — 「lost in the middle（中間の情報が埋もれる）」効果

モデルは、長い入力の最初と最後は確実に読み取れますが、中間は読み落としやすくなります。大量のコンテキストの真ん中にある情報ほど、見落とされがちです。

対策：

  1. 重要な結果の要約を、まとめた入力の冒頭に置く
  2. わかりやすい見出しを付けて、どこに何があるかを示す
  3. 重要な情報を、長いドキュメントの中間に置かない
  4. どうしても大量の内容を入れる場合は、重要な部分を最初と最後の両方に置く（「bookend」）
Tool Output Trimming — ツール出力を削る

ツールの結果は、とても長くなりがちです。顧客の注文を調べるツールが、必要なのは5項目なのに40項目も返すことがあります。

悪い例：40項目をそのまま返して、コンテキストを無駄に使う。

良い例：Claude に渡す前に、必要な項目だけに絞る：

{
  "order_id": "67890",
  "status": "delivered",
  "delivery_date": "2024-01-20",
  "total": 149.99,
  "items": ["Widget Pro (x2)"]
}
What Survives /compact — /compact の後も残るもの
残るもの失われる可能性があるもの
CLAUDE.md（ディスクから読み込み直される）それまでの会話の細かい内容
System prompt個々のツールの結果
直近の message前のターンでの細かい考えの流れ
Auto-memory（MEMORY.md）最初のコンテキストにあった正確な引用や数値

5.2 Escalation Patterns — 人間への引き継ぎ（エスカレーション）のパターン
When to Escalate Immediately — すぐにエスカレーションすべきとき
きっかけ理由対応
顧客がはっきり人間の担当者を求めているユーザー自身の選択を尊重する調査を続けず、すぐにエスカレーションする
ポリシーに定めがない、または例外にあたるケースエージェントには、ポリシーについて判断する権限がない状況を整理した情報を付けてエスカレーションする
妥当な方法を何度か試しても進まないエージェントが行き詰まっている試したことの要約を付けてエスカレーションする
When NOT to Escalate — エスカレーションすべきでないとき
誤ったきっかけなぜ誤りか
顧客の感情（sentiment）が激しい感情の強さ ≠ 問題の複雑さ。とても怒っている顧客でも、問題自体は単純なことがある。
Claude が自分で「自信が低い」と申告したClaude の自己申告の自信度（confidence）は、実際の正しさと一致しないことが多い。「自信が低い」回答が正しいこともあれば、「自信が高い」回答が間違っていることもある。
会話が長い長さはエスカレーションの必要性を示さない。解決までに多くのやりとりが必要な、正当な問題もある。
The Sentiment ≠ Complexity Distinction — 「感情の強さ」と「問題の複雑さ」は別物

試験でよく具体的に問われる考え方です：

"I'M SO FRUSTRATED WITH THIS!!!" + simple billing error
→ Agent can resolve. Don't escalate based on caps and exclamation marks.

"I have a question about the interaction between your enterprise SLA
and the new EU data residency requirements" + calm tone
→ May need escalation due to policy complexity, despite calm sentiment.

上の例：大文字や「!!!」で怒っていても、単純な請求ミスならエージェントが解決できる。一方、落ち着いた口調でも、SLA と EU のデータ保管規制が絡むようなポリシーの込み入った質問は、エスカレーションが必要になりうる。

Multiple Customer Matches — 検索で複数の顧客が見つかった場合

顧客を検索して、複数の候補が見つかったとき：

誤り：何らかの経験則（heuristic）で「いちばん可能性が高そうな」顧客を推測で選ぶ。

正解：本人を特定するための情報を、顧客に追加で尋ねる。

"I found multiple accounts matching that name. Could you provide
your email address or the last four digits of your phone number
so I can locate the right account?"
Structured Escalation Handoff — 構造化された引き継ぎ情報

エスカレーションするときは、整理されたサマリーを渡しましょう。引き継ぐ人間の担当者は、ふつう会話の履歴（transcript）を見られないからです。

ESCALATION SUMMARY
==================
Customer: Jane Doe (#12345)
Contact: jane@example.com | 555-0123
Issue type: Refund request — damaged product
Order: #67890 ($149.99, delivered 2024-01-20)

Actions taken by agent:
1. Verified customer identity
2. Confirmed order and delivery details
3. Customer provided photos of damage
4. Refund amount ($149.99) exceeds automated approval limit ($100)

Urgency: Standard (customer is frustrated but not at risk of churn)

5.3 Error Propagation — エラー情報の伝え方
Structured Error Context — 構造化されたエラー情報

エラーが起きたら、状況がわかる情報を十分に付けて上に伝えます：

{
  "failure_type": "timeout",
  "service": "knowledge_base_search",
  "attempted_query": "return policy for electronics over $500",
  "timeout_duration_ms": 30000,
  "partial_results": null,
  "alternative_approaches": [
    "Try searching with simpler terms",
    "Check the FAQ section directly",
    "Ask the customer for the specific product"
  ],
  "is_retryable": true,
  "retry_after_ms": 5000
}

これだけの情報があれば、Claude はどう立て直すか（リトライするか、別の方法を試すか）を自分で適切に判断できます。

Anti-Patterns — 避けるべきパターン

1. Generic error messages（中身のないエラーメッセージ）：

{ "error": "Operation failed" }

何が、なぜ失敗したのかがわからないので、Claude は適切に立て直せません。

2. Silent suppression（エラーを黙って握りつぶす）：

{ "results": [] }  // Returned when the search engine was actually down

本当は「検索できなかった」のに、Claude は自信を持って「該当する情報は見つかりませんでした」とユーザーに伝えてしまいます。この2つはまったく別の状況です。

3. Workflow termination（ワークフロー全体を止めてしまう）：

Step 1: Get customer info → Success
Step 2: Search knowledge base → Timeout
Step 3: ABORT ENTIRE WORKFLOW

より良い方法：取れた分の結果（partial results）で処理を続け、欠けている部分を記録し、代わりの方法を提案する。

Access Failure vs Empty Result — 「アクセスできなかった」と「結果が0件」の違い
状況HTTP ステータス意味エージェントの応答
検索は正常に動いたが、該当なし200 + 空の配列該当するコンテンツが存在しない「該当する記事は見つかりませんでした」
検索サービスが停止している503 / timeout検索そのものが実行されていない「現在検索できないため、別の方法を試します」
Subagent Error Recovery — subagent でのエラーからの立て直し

一時的なエラー（transient failure）は、subagent が自分の中で立て直す（local recovery）ようにすべきです：

Subagent: Search for "return policy"
  → Timeout
  → Retry with backoff (local recovery)
  → Success on second attempt
  → Return results to coordinator

coordinator（全体を指揮するエージェント）に伝えるのは、subagent が自力で解決できなかったエラーだけです。伝えるときは、次の情報を含めます：

  • 何を試したか
  • 途中までにどんな結果が得られたか
  • 具体的にどんなエラーだったか
  • リトライできるかどうか

5.4 Large Codebase Context Management — 大規模なコードベースでのコンテキスト管理
Context Degradation in Extended Sessions — 長いセッションでのコンテキストの劣化

セッションが長くなると、Claude の回答の信頼性が下がっていきます：

  • 前に確認した実際のコードではなく、「よくあるパターン」を持ち出して答える
  • 同じコードについて、回答が食い違う
  • 前にわかったことを忘れる
  • 確認し直さずに、推測で話を進めるようになる
Mitigation Strategies — 対策

1. Scratchpad Files（メモ用ファイル）

わかったことをファイルに書き出しておけば、コンテキストが圧縮されても失われません：

# scratchpad.md
## Auth System Findings
- Entry point: src/auth/middleware.ts:23
- Uses JWT with RS256
- Token expiry: 1 hour
- Refresh token: 7 days
- Role check: src/auth/roles.ts:45
- Known issue: No token revocation mechanism

コンテキストが圧縮された後も、Claude はこのファイルを読み直せば、わかったことを取り戻せます。

2. Subagent Delegation（subagent に任せる）

大量のファイルを読むような調査は、subagent に切り出して行わせます：

Main context: Clean, focused on the task
  ↓

5.5 Human Review Workflows — 人間によるレビューの進め方
Stratified Random Sampling — 層別ランダムサンプリング

出力全体から均等にランダムに選ぶだけでは不十分です。リスクの高さやカテゴリーごとにグループ分けして（stratify）、抜き取る割合を変えましょう：

Category A (high-risk): Sample 20% of outputs
Category B (medium-risk): Sample 10% of outputs
Category C (low-risk): Sample 5% of outputs

こうすると、人間のレビューの手間を、ミスが起きやすいところに集中させられます。

Field-Level Confidence Scores — 項目ごとの信頼度スコア

抽出結果全体に1つの信頼度（confidence）を付けるのではなく、項目（フィールド）ごとに付けます：

{
  "vendor_name": { "value": "Acme Corp", "confidence": 0.99 },
  "total_amount": { "value": 149.99, "confidence": 0.95 },
  "purchase_order": { "value": "PO-2024-001", "confidence": 0.72 },
  "tax_id": { "value": "12-3456789", "confidence": 0.45 }
}

Calibration（較正）：信頼度スコアは、正解ラベル付きの検証用データを使って、実際の正解率と合うように調整（較正）する必要があります。信頼度 0.9 なら、その項目は実際に約90%の確率で正しくなければなりません。較正していない信頼度の数値には、意味がありません。

Accuracy by Document Type — ドキュメントの種類ごとの精度

見えにくいミスのパターン：

Overall accuracy: 97% ← Looks great!

Breakdown:
  Standard invoices: 99.5% ← Excellent
  Handwritten notes: 45%  ← Terrible
  Foreign language docs: 62% ← Bad

全体の平均（集計値）だけを見ると、特定の種類のドキュメントで精度が低いことが隠れてしまいます。精度は必ず、ドキュメントの種類ごと・項目ごとに分けて確認しましょう。

Per-Document-Type Reporting — ドキュメントの種類ごとのレポート

ドキュメントの種類ごと、さらにその中の項目ごとに精度をレポートします：

Standard Invoices:
  vendor_name: 99.8%
  total_amount: 99.2%
  line_items: 97.5%
  tax_id: 94.1%

Handwritten Notes:
  vendor_name: 85.0%
  total_amount: 42.0% ← Critical failure
  line_items: 38.0% ← Critical failure

こうすれば、全体の数字に埋もれることなく、本当に改善が必要な箇所がはっきりわかります。

5.6 Information Provenance — 情報の出所（provenance）
Claim-Source Mappings — 主張と出典の対応付け

subagent が調べた結果を返すときは、それぞれの主張（claim）にどこから得た情報なのか（provenance）を構造化して付けるべきです：

{
  "claim": "Revenue increased 15% year-over-year in Q4 2024",
  "evidence": "Q4 earnings report, page 3, paragraph 2",
  "source_url": "https://example.com/earnings/q4-2024",
  "document_name": "Q4 2024 Earnings Report",
  "publication_date": "2025-01-15",
  "source_type": "primary"
}
Handling Conflicting Data — 情報源どうしが食い違うときの扱い

情報源によって値が違うときは、黙ってどちらかを選ぶのではなく、食い違いがあることを明記（annotate the conflict）します：

{
  "field": "Q4 revenue",
  "values": [
    {
      "value": "$2.3B",
      "source": "Company press release (2025-01-15)",
      "note": "Preliminary figures"
    },
    {
      "value": "$2.28B",
      "source": "SEC filing (2025-02-28)",
      "note": "Audited figures"
    }
  ],
  "resolution": "SEC filing is the authoritative source (audited)",
  "conflict_type": "minor_discrepancy"
}

避けるべきパターン：情報源の食い違いを書かずに、黙って1つの値を選ぶこと。データの品質の問題が見えなくなってしまいます。

Temporal Data — 時点のあるデータ

いつの時点の話かで混乱しないように、公開日とデータの基準日を添えましょう：

{
  "claim": "Unemployment rate is 3.7%",
  "data_as_of": "2024-11-01",
  "source_published": "2024-12-06",
  "retrieved_on": "2025-01-10"
}

日付がないと、読み手は別々の月の2つの失業率を「矛盾している」と思ってしまうかもしれません — 実際には、どちらもその時点では正しい数字なのに。

Synthesis Output Quality — 調査結果をまとめるときの品質

複数の情報源から調査結果をまとめる（research synthesis）ときは：

  1. 確かさの度合い（certainty level）を書き分ける：
    • "Well-established（確かな事実）: Revenue grew 15% (confirmed by SEC filing and two analyst reports)"
    • "Contested（見解が分かれている）: Market share estimates range from 12% to 18% depending on methodology"
    • "Single-source（情報源が1つだけ）: Only one report mentions the planned acquisition"
  2. 情報源の言い方をそのまま保つ（preserve source characterization）：
    • 情報源の主張を、ひとまとめにしたり勝手に言い換えたりしない
    • 元の主張に忠実に引用する、または意味を変えずに言い換える
    • 情報源自身が付けている注意書きや条件（caveats/qualifications）も書き残す
  3. 内容に合った見せ方を選ぶ：
    • 財務データ → 出典を明記した表
    • ニュース・出来事 → 時系列の文章
    • 技術仕様 → 構造化されたリスト
    • 見解が分かれている主張 → 並べて比較

5.8 Bounding and Recovering Long Runs — 長時間の実行に上限を設け、止まったら立て直す
Task Budgets vs max_tokens — task budget と max_tokens の違い

max_tokens はモデルからは見えない上限で、そこに達すると出力が途中で切れます。task budget（output_config.task_budget、beta task-budgets-2026-03-13、最小 20,000）はモデルに見える上限なので、モデルは残りを見ながら進め方を調整し、きりのよいところで作業を終えられます。Claude Opus 5、Fable 5、Sonnet 5、Opus 4.8/4.7 で使えます。数えるのは、そのターンで Claude が生成する量と読み込むツールの結果です — 送り返す会話履歴全体ではありません。通常のループでは remaining は指定しません。履歴を自分で書き換えたり compact したりして、サーバーがそれまでの消費量を把握できなくなったときにだけ値を渡します。

Managed Agents の session budget はまったく別のものです：プラットフォームがセッションに対して強制する、金額（ドル）での厳格な上限です。一方、task budget はあくまで目安（advisory）で、トークン数で指定します。

Refusals Are a Reliability Concern, Not Just a Safety One — 回答拒否は安全性だけでなく、信頼性の問題でもある

回答拒否（refusal）も HTTP 200 で返ってきて、stop_reason: "refusal" と stop_details.category が付きます。stop_reason を確認せずに content だけを読むコードは、回答拒否を「空だけど成功した応答」として扱ってしまいます — 失敗した検索を「結果0件」とみなすのと同じ種類のバグです（§5.3）。本番環境では、サーバー側のフォールバック（betas=["server-side-fallback-2026-07-01"]、fallbacks="default"）を有効にして、リクエストが止まったままにならず、拒否のカテゴリーに応じて別の経路に回されるようにしましょう。Domain 1 §1.1 も参照してください。

    7. エラーを黙って握りつぶす（空の結果を返して、成功として扱う）
    8. 1つのエージェントにツールを詰め込みすぎる（推奨は4〜5個なのに18個も持たせる）
    9. コードを生成したのと同じセッションに、そのコードをレビューさせる（生成したときの考えに引きずられる）
    10. 全体の精度（aggregate accuracy）だけを見て問題ないと判断し、特定のドキュメントの種類や項目でのエラー率の高さを見逃す

    🧭 すばやく判断するための対比表（Key Decision Frameworks）

    「A と B のどちらを選ぶか」という問題で使います — 問題の状況が左右どちらに当てはまるかで、答えの方向が決まります。

    ルールの守らせ方Programmatic hooks — お金や安全に関わるとき  ·  プロンプトでの指示 — 「できるだけ守れればよい」ときだけ。確実ではない
    実行モードPlan mode — 複数のファイルにまたがる変更、設計に関わる作業  ·  Direct execution — 1ファイルだけで、やることが明確
    tool_choice"any" — モデルに必ずいずれかのツールを呼ばせる  ·  ツール名を指定して強制 — 特定のツールを最初に実行させる

    エラー処理構造化されたエラー情報 — エラーの種類 + リトライできるか + 途中までの結果  ·  中身のないエラーや、エラーを隠すのは絶対にダメ

    🧩 「Building Effective Agents」の6つの基本パターン

    Anthropic の基本となるブログ記事（2024年12月）で、Domain 1 の考え方の多くはここがもとになっていると考えられます。いちばん大事な区別：Workflow = あらかじめ決めた固定の手順を、コードでたどる。Agent = 環境からの反応を見ながら、モデル自身が次の手順を決める。

    Prompt Chaining

    タスクを順番に並んだ LLM のステップに分け、前のステップの出力を次のステップが処理する。途中に確認のチェックポイント（gate）を置く。時間はかかるが、精度が上がる。

    Routing

    まず入力を分類し、それに合った専用のプロンプトやモデルに振り分ける（例：簡単な質問 → Haiku、難しい質問 → Sonnet/Opus）。

    Parallelization

    Sectioning — タスクを分けて同時に実行する。Voting — 同じタスクを何度か実行し、多数決や突き合わせで結果を決める。

    Orchestrator–Workers

    orchestrator が入力に応じてタスクをその場で分割し（手順が固定の Prompt Chaining との違い）、worker に割り振ってから結果をまとめる。coordinator–subagent パターンの原型。

    Evaluator–Optimizer

    1つの LLM が出力を作り、別の LLM が採点してフィードバックする。これを繰り返す — 評価の基準がはっきりしていて、改善する価値が本当にあるときに向いている。

    Autonomous Agents

    終わりの決まっていないループの中で、エージェントが自分で計画して行動し、ツールやコードの実行結果を「事実（ground truth）」として進み具合を自分で確かめ、停止条件に達するまで続ける。

    この記事の大原則は「複雑にするのは、それで結果が本当に良くなるときだけ」。もう1つが Agent-Computer Interface（ACI）：ツールの説明文は、新人の開発者に向けたドキュメントのように丁寧に書くこと。人間のエンジニアでもどのツールを使えばよいか迷うようなら、AI にそれ以上を期待することはできないからです。

    📐 採点方法

    Claude Agent SDK
    stop_reason

    モデルは毎ターンの最後に "tool_use" か "end_turn" を返します — エージェントのループを続けるか止めるかを判断できる、唯一の確実な手がかりです。応答の文章から推測したり、ループの回数で判断したりしないこと。

    Task tool / allowedTools

    coordinator が subagent を起動（spawn）する唯一の手段。allowedTools に "Task" が入っていないと、coordinator は subagent を1つも呼べません。

    Hooks (PostToolUse, tool call interception)

    ルールを100%確実に（deterministic に）守らせる唯一の方法 — データの形式をそろえたり、ポリシーに反するツール呼び出しを止めたりするのに使います。プロンプトでの指示は「たいてい守られる」だけで、絶対ではありません。

    Coordinator–subagent (hub-and-spoke)

    coordinator がすべてのやりとりの中継点（ハブ）となり、全体の調整、結果の取りまとめ、エラー処理を担います。subagent のコンテキストは独立していて、親の情報を自動では引き継ぎません。

    fork_session / --resume

    fork は、共通の出発点から別々の方向を並行して試すためのもの。名前付きの resume は、以前のセッションをそのまま再開するためのもの。resume したら、その間に変わったファイルを必ず伝えましょう — エージェントが古い情報のまま作業しないようにするためです。

    MCP · Tool Design
    ツールの説明文 (tool description)

    LLM がどのツールを使うかを決める、唯一の手がかり。説明文が雑だと、似たツールの間で選び間違えます。ツールの選び間違いが起きているとき、まず最初に直すべきは、ほぼ必ずここです。

    isError flag

    ツールのエラーをエージェントに伝えるための MCP の仕組み。エラーの種類（transient/validation/business/permission）と、リトライできるかどうかを付ける必要があります — 「Operation failed」とだけ返しても役に立ちません。

    .mcp.json / MCP resources

    プロジェクト単位の MCP サーバーの設定ファイル。${GITHUB_TOKEN} のような環境変数を使えるので、秘密情報をファイルに直接書かずに済みます。MCP resources はコンテンツの一覧を公開し、手探りのツール呼び出しを減らします。

    tool_choice

    "auto"（モデルはツールを使わず文章で答えることもある）、"any"（必ずいずれかのツールを呼ぶ。どれを呼ぶかはモデルが選ぶ）、または特定のツールを1つ指定して強制。構造化出力を確実に得たいときや、抽出の順番を固定したいときに使います。

    Claude Code Configuration
    CLAUDE.md の階層

    3つの階層：ユーザー単位（自分だけに適用、共有されない）、プロジェクト単位（git で共有され、チーム全員に適用）、ディレクトリ単位。よくあるミス：指示をユーザー単位に書いてしまい、なぜチームメイトには効かないのかと悩む。

    .claude/rules/

    YAML frontmatter の paths（glob パターン）で対象を指定するルールファイル — 一致するファイルを編集するときだけ読み込まれます。同じ規約があちこちのフォルダーに関係する場合（例：テストファイル）は、フォルダーごとに CLAUDE.md を置くよりずっと便利です。

    .claude/commands/ vs .claude/skills/

    プロジェクト単位の command は、バージョン管理を通じてチーム全員で共有されます。Skill は context: fork（独立した環境で実行し、メインのコンテキストを汚さない）、allowed-tools、argument-hint に対応しています。

    Plan mode vs direct execution

    Plan mode は、大規模で設計に関わる作業や、進め方が何通りも考えられる場合に使います。Direct execution は、やることが明確で範囲の小さい作業に。Explore subagent を使うと、長い調査の過程をメインのコンテキストから切り離せます。

    /memory / /compact

    /memory は、どの memory ファイルが読み込まれているかを確認するコマンド（おかしな動きの原因を調べるときに使う）。/compact は、長い調査でコンテキストがいっぱいになってきたときに圧縮するコマンド。

    CI/CD · Claude Code CLI
    -p / --print

    Claude Code を対話なし（non-interactive）で実行します。CI/CD パイプラインでは必須 — このフラグがないと、入力待ちのままジョブが止まり続けます。

    --output-format json / --json-schema

    CI で、プログラムが読み取れる形式の出力を強制します。自由な文章を解析しなくても、PR にインラインコメントを自動で投稿できるようになります。

    Structured Output · Batch
    JSON Schema (nullable, enum + other)

    ドキュメントに情報がないときにモデルが値をでっち上げないよう、任意（optional）・null 可（nullable）のフィールドにします。今後増えるかもしれない分類には、enum + "other" + 詳細を書く文字列フィールドを用意します。

    Message Batches API / custom_id

    費用は50%安いものの、処理に最大24時間かかり、応答時間の保証（SLA）もありません — 結果をすぐに待つ必要のない処理にだけ向いています。リクエストと結果は custom_id で対応付けます。

    Validation-retry loop

    検証エラーの内容を具体的に伝えてリトライすれば、モデルは自分で直せます — ただし、情報が元の資料にそもそも存在しない場合は、何度リトライしても無駄です（形式・構造のエラーとは別の問題）。

    Few-shot prompting

    出力を安定させ、あいまいなケースを正しく扱わせるための最も強力な手段。与えた例に機械的に合わせるだけでなく、判断の「コツ」をつかんで、初めて見るケースにも応用できるようになります。

    明確な基準 (誤検知 = false positive を減らす)

    具体的な基準は、「慎重に」のようなあいまいな指示に必ず勝ります。「誤検知を減らす最も効果的な方法は？」と問われたら、たいていこれが正解です。

    Multi-pass review

    大きなレビューを、ファイルごとのレビュー（local pass）と、ファイルをまたぐ統合チェック（cross-file pass）に分けます。注意が分散したり、指摘どうしが矛盾したりするのを防げます。

    Context Management · Reliability
    "Lost in the middle"

    モデルは長い入力の最初と最後はしっかり読み取れますが、中間にある情報は見落としがちです。重要な要約を冒頭に置き、わかりやすい見出しを付けることで、この影響を減らせます。

    エスカレーションの基準

    エスカレーションするのは、顧客が人間の担当者を求めたとき、ポリシーに定めがない・例外にあたるとき、エージェントが行き詰まったとき。顧客の感情（sentiment）も、自己申告の自信度（confidence）も、案件の難しさを測る当てにはなりません。

    Structured error context

    エラーには、エラーの種類 + 試したこと + 途中までの結果 + 代わりの方法を付けます。エラーを握りつぶしたり（空の結果を成功扱いにする）、1つのエラーでワークフロー全体を止めたりしないこと。

    Confidence calibration

    全体の精度が高くても、特定の項目やドキュメントの種類で精度が低いことが隠れている場合があります。完全に自動化する前に、グループごとに精度を確認する必要があります。

    Claim-source mapping (provenance)

    複数の情報源をまとめるときは、どの主張がどの出典によるものかを最後まで保ちます。数値が食い違う場合は、勝手に1つを選ばず、出典を添えて両方を明記します。

    発展（公式 Exam Guide の範囲外）
    MCP — Tools / Resources / Prompts

    MCP の仕様にある3つの基本要素で、「誰が使うタイミングを決めるか」で区別されます：Tools = モデルが自分で呼ぶ、Resources = アプリが読み込むかどうかを決める、Prompts = ユーザーが自分で呼び出したときだけ使われる。

    「Building Effective Agents」の6つのパターン

    Prompt Chaining、Routing、Parallelization、Orchestrator-Workers、Evaluator-Optimizer、Autonomous Agents — Domain 1 の考え方の多くは、この記事がもとになっていると考えられます。

    "Context rot" & Case Facts Block

    コンテキストが長くなるほど、正確に思い出す力は少しずつ落ちていきます — だからこそ「必要最小限のトークンで、最大限の情報を」が原則です。Case Facts Block は、重要な数値を要約の対象から外しておくためのパターンです。

    CLAUDE.md — 上書きではなく連結される

    4つの階層（managed → user → project → local）は、すべて連結（concatenate）されます。後の階層が前の階層を上書きするわけではありません。また、system prompt の中ではなく、system prompt の後に user message として送られます。
